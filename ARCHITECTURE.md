# Архитектура Системы Учета Рабочего Времени и Расчета Заработной Платы "Tessera"

Этот документ описывает высокоуровневую архитектуру и основные сценарии использования (use cases) системы "Tessera". Архитектура спроектирована так, чтобы быть понятной для человека и легко реализуемой с помощью ИИ-агентов.

## 1. Обзор Системы "Tessera"

Система "Tessera" предназначена для автоматизации процессов учета рабочего времени сотрудников и расчета их заработной платы на основе этих данных. Название "Tessera" (тессера — маленький кубик камня, из которых складывается мозаика) символизирует, как отдельные рабочие события и часы сотрудников складываются в общую картину их вклада и формируют основу для расчета заработной платы.

**Основные цели:**
- Точный учет отработанных часов - с точностью до секунды.
- Автоматический расчет заработной платы.
- Прозрачность данных для сотрудников и администрации.
- Минимизация ручного труда и ошибок.

## 2. Предположения и Ограничения

Этот раздел описывает ключевые предположения, сделанные в процессе проектирования архитектуры, а также ограничения, которые могут повлиять на разработку и эксплуатацию системы.

**Предположения:**
*   Система предназначена для использования в рамках одного маленького предприятия.
*   Количество сотрудников не превышает сотни.
*   Объем данных логов (файлы `.dat`) является умеренным и не требует распределенных систем хранения или обработки.
*   Основной источник данных о приходе/уходе — файлы `.dat` из СКУД.
*   Пользователи системы (администратор и работники) имеют базовые навыки работы с десктопными приложениями.
*   Расчет заработной платы производится на основе почасовой ставки и фиксированных правил, без учета сложных налоговых систем или индивидуальных договоренностей, выходящих за рамки описанных правил.

**Ограничения:**
*   Система будет реализована как **десктопное приложение** (на базе Python и QT), без веб-интерфейса.
*   В качестве базы данных используется **SQLite**, что подразумевает локальное хранение данных и отсутствие необходимости в клиент-серверной архитектуре БД.
*   Системы не предусматривает интеграцию с внешними бухгалтерскими системами или ERP.
*   Безопасность данных ориентирована на защиту от несанкционированного доступа на уровне приложения (пароль администратора), но не включает комплексные меры сетевой безопасности или защиты от продвинутых атак.
*   Система не предназначена для работы в режиме реального времени (например, мгновенное отображение приходов/уходов).

## 3. Программная архитектура

Система будет построена на основе слоистой архитектуры (Layered Architecture), чтобы обеспечить четкое разделение ответственности, упростить тестирование и сопровождение.

```
┌─────────────────────────────────────────┐
│         Presentation Layer              │
│  (Qt Views, Controllers, ViewModels)    │
└──────────────────┬──────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│       Application Layer                 │
│  (Use Cases, Application Services)      │
└──────────────────┬──────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│         Domain Layer                    │
│  (Entities, Domain Services, Rules)     │
└──────────────────┬──────────────────────┘
                   ↓
┌─────────────────────────────────────────┐
│      Infrastructure Layer               │
│  (SQLite, File Parsers, Security)       │
└─────────────────────────────────────────┘
```

### 3.1. Слои Архитектуры

*   **Presentation Layer (Слой представления):**
    *   **Ответственность:** Отображение информации пользователю и обработка его ввода.
    *   **Состав:** Окна, виджеты, контроллеры, реализованные на PyQt. Этот слой не содержит бизнес-логики. Он только делегирует вызовы слою приложения и отображает результат.

*   **Application Layer (Слой приложения):**
    *   **Ответственность:** Координация выполнения бизнес-сценариев (Use Cases). Этот слой является точкой входа для UI.
    *   **Состав:** Сервисы приложений (`PayrollService`, `EmployeeService`), которые оперируют DTO (Data Transfer Objects) для взаимодействия с UI и вызывают методы доменного слоя для выполнения бизнес-правил. Сервисы, отвечающие за импорт данных (например, `IngestionService`), также являются частью этого слоя, так как они координируют процесс парсинга (Infrastructure) и сохранения данных через репозитории.

*   **Domain Layer (Доменный слой):**
    *   **Ответственность:** Содержит всю бизнес-логику и бизнес-правила. Это ядро системы.
    *   **Состав:** Сущности (`Employee`, `WorkSession`), объекты-значения, доменные сервисы и репозитории (в виде интерфейсов). Этот слой не зависит ни от каких других слоев.

*   **Infrastructure Layer (Инфраструктурный слой):**
    *   **Ответственность:** Реализация технических деталей: работа с базой данных, файловой системой, внешними API.
    *   **Состав:** Реализации репозиториев для работы с SQLite, парсеры `.dat` файлов, модули для шифрования и логирования. Этот слой зависит от доменного слоя (реализует его интерфейсы), но не наоборот.

### 3.2. Поток зависимостей (Dependency Rule)

Главное правило: **зависимости направлены только вниз**. Слой может взаимодействовать только со слоями, находящимися под ним. Это гарантирует, что бизнес-логика (Domain) ничего не знает о базе данных или UI, что позволяет легко заменять эти компоненты.

## 4. Компоненты Архитектуры

Система будет состоять из следующих модульных компонентов:

### 3.1. Модуль Импорта Данных (Data Ingestion Layer)

Этот компонент отвечает исключительно за получение и первичную обработку данных о событиях прихода и ухода сотрудников из внешних файлов.

- **Источник данных:** Файлы логов `.dat` из систем контроля доступа (СКУД).
- **Парсер данных:** Будет реализован парсер для формата файла `1_attlog.dat`. На основе анализа файла, каждая строка содержит следующие поля, разделенные пробелами или табуляцией:
    1.  **ID сотрудника:** Целое число, уникальный идентификатор сотрудника.
    2.  **Дата:** В формате `YYYY-MM-DD`.
    3.  **Время:** В формате `HH:MM:SS`.
    4.  **Дополнительное поле 1:** Целое число (в образце всегда `1`). Данное поле не нужно
    5.  **Дополнительное поле 2:** Целое число (в образце всегда `255`). Данное поле не нужно
    6.  **Дополнительное поле 3:** Целое число (в образце всегда `1`). Данное поле не нужно
    7.  **Дополнительное поле 4:** Целое число (в образце всегда `0`). Данное поле не нужно
    Модуль должен извлекать ID сотрудника, дату и время, игнорируя  остальные поля. Модуль будет расширяемым для поддержки других форматов в будущем.
- **Валидация:** Проверка данных на полноту и корректность (например, наличие ID, корректность формата даты/времени).

Ручной ввод данных, их автоматическая генерация по правилам и редактирование записей являются функциями **Ядра Системы** и **Пользовательского Интерфейса**, а не модуля импорта.

### 3.2. Ядро Системы (Core Business Logic)

Центральный компонент, содержащий всю бизнес-логику.

- **Управление Сотрудниками:**
    - Хранение информации о сотрудниках (ID, имя, должность, ставка оплаты).
    - CRUD-операции (создание, чтение, обновление, удаление) для профилей сотрудников.
- **Обработка Рабочего Времени:**
    - Агрегация "сырых" данных о входе/выходе в полноценные рабочие сессии.
    - Расчет отработанных часов за день, неделю, месяц.
    - Учет  опозданий и переработок, отпусков, прогулов
- **Расчет Заработной Платы:**
    - Модуль расчета ЗП на основе отработанных часов и ставки сотрудника.
    - Учет бонусов, премий и вычетов.
    - Гибкая настройка правил расчета.

### 3.3. Хранилище Данных (Data Storage)

Компонент для надежного хранения всей информации системы.

- **База данных:** SQLite - идеально подходит по задачу и объем данных

### 3.4. Пользовательский Интерфейс (User Interface)

Интерфейс для взаимодействия с системой будет реализован как десктопное приложение с графическим интерфейсом (GUI). При запуске приложение предложит ввести пароль. В зависимости от ввода пароля, система будет работать в одном из двух режимов.

- **Режим Администратора (вход с паролем):**
  - При вводе корректного пароля предоставляется полный доступ ко всем функциям системы.
  - **Функционал:**
    - Управление сотрудниками (добавление, редактирование, деактивация).
    - Управление должностями и правилами расчета.
    - Запуск импорта данных из `.dat` файлов.
    - Полный доступ к редактированию табелей: ручной ввод данных, генерация по правилам, корректировка любых записей.
    - Запуск и подтверждение расчета заработной платы.
    - Генерация всех видов отчетов, включая финансовые (расчетные листки).

- **Режим Просмотра (вход с пустым паролем):**
  - Если пароль не введен, система запускается в режиме ограниченного доступа.
  - **Функционал:**
    - Просмотр табелей учета рабочего времени по сотрудникам.
    - Генерация отчетов по отработанным часам **без отображения финансовой информации** (ставки, суммы зарплаты).
    - Редактирование и расчет ЗП недоступны.

### 3.5. Модуль Отчетности (Reporting)

Генерация отчетов для администрации и сотрудников.

- **Табель учета рабочего времени конкретного сотрудника.**
- **Расчетный листок по заработной плате для каждого сотрудника.**
- **Общая таблица-отчет со всеми сотрудниками, временем работы и зарплатой.**

## 4. Модель Данных (Схемы БД)

Для хранения данных будет использоваться SQLite со следующими таблицами:

**Таблица `employees` (Сотрудники)**
*   `id` (INTEGER, PRIMARY KEY): Уникальный ID сотрудника, соответствует ID из лог-файла.
*   `full_name` (TEXT, NOT NULL): Полное имя сотрудника.
*   `position_id` (INTEGER, NOT NULL, FOREIGN KEY to `positions.id`): Ссылка на должность сотрудника.
*   `payment_type` (TEXT, NOT NULL, DEFAULT 'hourly'): Тип оплаты ('hourly' - почасовая, 'fixed' - фиксированная за выход).
*   `hourly_rate` (REAL, NOT NULL, DEFAULT 0): Базовая почасовая ставка (используется, если `payment_type` = 'hourly').
*   `fixed_rate` (REAL, NOT NULL, DEFAULT 0): Фиксированная ставка за выход (используется, если `payment_type` = 'fixed').
*   `is_active` (BOOLEAN, DEFAULT TRUE): Флаг, активен ли сотрудник.

**Таблица `positions` (Должности)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT)
*   `name` (TEXT, UNIQUE, NOT NULL): Название должности (например, "Инженер", "Бухгалтер").
*   `standard_workday_hours` (REAL, NOT NULL, DEFAULT 8): Норма часов в день для этой должности.
*   `weekday_overtime_multiplier` (REAL, NOT NULL, DEFAULT 1.5): Множитель для переработок в будни для этой должности.
*   `holiday_rate_multiplier` (REAL, NOT NULL, DEFAULT 1.5): Множитель для обычной работы в выходные/праздники для этой должности.
*   `holiday_overtime_rate_multiplier` (REAL, NOT NULL, DEFAULT 2.0): Множитель для переработок в выходные/праздники для этой должности.
*   `fixed_rate_pays_multipliers` (BOOLEAN, NOT NULL, DEFAULT FALSE): Учитывать ли множители (`holiday_rate_multiplier`) для сотрудников с фиксированной ставкой.

**Таблица `import_batches` (Партии импорта)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID партии.
*   `import_timestamp` (DATETIME, NOT NULL): Время начала импорта.
*   `source_file_name` (TEXT, NOT NULL): Имя исходного файла.
*   `status` (TEXT, NOT NULL): Статус импорта ('success', 'partial', 'failed').
*   `total_rows` (INTEGER): Общее количество строк в файле.
*   `processed_rows` (INTEGER): Количество успешно обработанных строк.
*   `error_rows` (INTEGER): Количество строк с ошибками.

**Таблица `raw_log_data` (Сырые данные логов)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID записи в БД.
*   `import_batch_id` (INTEGER, NOT NULL, FOREIGN KEY to `import_batches.id`): Ссылка на партию импорта.
*   `raw_line_content` (TEXT, NOT NULL): Полная, неизмененная строка из файла `1_attlog.dat`.
*   `imported_at` (DATETIME, NOT NULL): Точное время, когда эта строка была добавлена в базу данных.

**Таблица `time_entries` (События входа/выхода)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID записи.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `timestamp` (DATETIME, NOT NULL): Точное время события.

**Таблица `work_sessions` (Рабочие сессии)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID сессии.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `start_time` (DATETIME, NOT NULL): Время начала сессии.
*   `end_time` (DATETIME, NULLABLE): Время окончания сессии.
*   `duration_hours` (REAL): Длительность сессии в часах.
*   `status` (TEXT, NOT NULL): Статус сессии. Возможные значения: `completed` (завершено, найдена пара вход/выход), `incomplete` (незавершено, нет парной метки), `manual_edit` (отредактировано вручную администратором), `auto_generated` (сгенерировано автоматически системой).
*   `session_type` (TEXT, NOT NULL): Тип дня, к которому относится сессия. Возможные значения: `standard` (обычный рабочий день), `weekend` (выходной день), `holiday` (праздничный день).

**Таблица `payrolls` (Расчеты заработной платы)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID расчета.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `period_start` (DATE, NOT NULL): Начало расчетного периода.
*   `period_end` (DATE, NOT NULL): Конец расчетного периода.
*   `work_days_count` (INTEGER): Количество отработанных дней (для фиксированной оплаты).
*   `weekday_standard_hours` (REAL): Сумма обычных часов в будни (для почасовой оплаты).
*   `weekday_overtime_hours` (REAL): Сумма часов переработки в будни (для почасовой оплаты).
*   `holiday_standard_hours` (REAL): Сумма обычных часов в выходные/праздники (для почасовой оплаты).
*   `holiday_overtime_hours` (REAL): Сумма часов переработки в выходные/праздники (для почасовой оплаты).
*   `base_pay` (REAL): Сумма базовой оплаты (по часам или по дням).
*   `bonus_pay` (REAL): Сумма всех бонусов и компенсаций.
*   `paid_absence_days` (REAL): Количество оплачиваемых дней отсутствия (например, отпуск).
*   `paid_absence_amount` (REAL): Сумма, начисленная за оплачиваемые отсутствия.
*   `total_gross_pay` (REAL): Итоговая начисленная сумма (до вычетов).
*   `net_pay` (REAL): Заработная плата после вычетов (зарезервировано для будущего использования).
*   `calculation_date` (DATETIME, NOT NULL): Дата выполнения расчета.
*   `confirmed_at` (DATETIME, NULLABLE): Метка времени, когда расчет был подтвержден. `NULL` означает, что расчет является черновиком.
*   `supersedes_payroll_id` (INTEGER, NULLABLE, FOREIGN KEY to `payrolls.id`): Ссылка на `id` расчета, который был заменен этой корректировкой.

**Таблица `payroll_bonuses` (Бонусы и компенсации в расчете)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID.
*   `payroll_id` (INTEGER, NOT NULL, FOREIGN KEY to `payrolls.id`): Ссылка на расчет ЗП.
*   `name` (TEXT, NOT NULL): Название бонуса/компенсации (например, "Премия руководителя", "За молоко").
*   `amount` (REAL, NOT NULL): Сумма.
*   `comment` (TEXT): Комментарий.

**Таблица `absence_types` (Типы отсутствий)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID.
*   `name` (TEXT, UNIQUE, NOT NULL): Название типа отсутствия (например, "Больничный", "Отпуск", "Прогул").
*   `is_paid` (BOOLEAN, NOT NULL, DEFAULT 0): Флаг, является ли отсутствие оплачиваемым.
*   `payment_multiplier` (REAL, NOT NULL, DEFAULT 0.0): Множитель для расчета оплаты (например, 1.0 для отпуска, 0.0 для прогула).

**Таблица `absences` (Периоды отсутствий)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID.
*   `employee_id` (INTEGER, NOT NULL, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `absence_type_id` (INTEGER, NOT NULL, FOREIGN KEY to `absence_types.id`): Ссылка на тип отсутствия.
*   `start_date` (DATE, NOT NULL): Дата начала отсутствия.
*   `end_date` (DATE, NOT NULL): Дата окончания отсутствия.
*   `reason` (TEXT): Комментарий или причина (например, номер больничного листа).

**Таблица `app_config` (Настройки приложения)**
*   `key` (TEXT, PRIMARY KEY): Ключ настройки (например, 'workday_start_hour', 'overtime_multiplier').
*   `value` (TEXT): Значение настройки.

### 4.1. Дополнения к Схеме БД

#### 4.1.1. Индексы

Для оптимизации производительности запросов, особенно при выборке данных по сотрудникам и временным диапазонам, будут добавлены следующие индексы:

*   `time_entries`:
    *   `CREATE INDEX idx_time_entries_employee_timestamp ON time_entries(employee_id, timestamp);`
*   `work_sessions`:
    *   `CREATE INDEX idx_work_sessions_employee_start_time ON work_sessions(employee_id, start_time);`
    *   `CREATE INDEX idx_work_sessions_employee_end_time ON work_sessions(employee_id, end_time);`
*   `payrolls`:
    *   `CREATE INDEX idx_payrolls_employee_period ON payrolls(employee_id, period_start, period_end);`

#### 4.1.2. Ограничения (Constraints)

Для обеспечения целостности и корректности данных будут использоваться следующие ограничения:

*   **Общие:**
    *   Для сохранения исторической целостности данных, физическое удаление сотрудников (`employees`) запрещено. Вместо этого используется "мягкое удаление" путем установки флага `is_active = false`. Это гарантирует, что все связанные записи (`payrolls`, `work_sessions`, `raw_log_data` и т.д.) останутся в базе данных для аудита и истории.
*   **Таблица `positions`:**
    *   `standard_workday_hours` `CHECK (standard_workday_hours > 2)` — Норма рабочего дня должна быть больше 2 часов, так как сессии меньшей длительности считаются неполными.
    *   `weekday_overtime_multiplier` `CHECK (weekday_overtime_multiplier >= 1.0)`
    *   `holiday_rate_multiplier` `CHECK (holiday_rate_multiplier >= 1.0)`
    *   `holiday_overtime_rate_multiplier` `CHECK (holiday_overtime_rate_multiplier >= 1.0)`
*   **Таблица `work_sessions`:**
    *   `CHECK (start_time <= end_time)` (если `end_time` не NULL)
    *   `CHECK (duration_hours >= 0)`
    *   `status` `CHECK (status IN ('completed', 'incomplete', 'manual_edit', 'auto_generated'))`
    *   `session_type` `CHECK (session_type IN ('standard', 'weekend', 'holiday'))`

#### 4.1.3. Представления (Views)

Для упрощения запросов и генерации отчетов будут созданы представления:

*   `view_employee_work_summary`: Агрегированные данные по рабочему времени сотрудников за период.
*   `view_payroll_details`: Детализированные данные по расчету заработной платы.

#### 4.1.6. Версионирование Схемы БД (Schema Versioning)

Для управления изменениями в схеме базы данных будет использоваться механизм миграций (например, с помощью библиотеки `Alembic` для Python, если будет использоваться ORM, или кастомный скрипт). Каждая миграция будет представлять собой скрипт, который обновляет схему БД с одной версии на другую.

## 5. Модель Времени и Часовых Поясов (Time and Timezone Model)

Для обеспечения целостности и предсказуемости данных, связанных со временем, в системе принята следующая модель:

*   **Хранение в БД:** Все значения типа `DATETIME` в базе данных (например, `time_entries.timestamp`, `work_sessions.start_time`) хранятся в формате **UTC**.
*   **Работа в приложении:** Приложение на всех уровнях (UI, Application, Domain) оперирует временем в **локальном часовом поясе компьютера пользователя**.
*   **Преобразование:**
    *   **При записи в БД:** Любая метка времени перед сохранением в базу данных преобразуется из локального времени в UTC.
    *   **При чтении из БД:** Любая метка времени, полученная из базы данных, преобразуется из UTC в локальное время перед отображением в UI или использованием в расчетах.

Этот подход гарантирует корректную обработку данных вне зависимости от местоположения пользователя и автоматически обрабатывает переходы на летнее/зимнее время (DST).

## 6. Бизнес-Правила и Обработка Граничных Случаев

Этот раздел описывает ключевые бизнес-правила, алгоритмы расчета и подходы к обработке нестандартных ситуаций в системе.

### 5.1. Обработка Граничных Случаев

Этот раздел определяет, как система должна реагировать на нестандартные ситуации.

1.  **Неполные данные за день (сессия < 2 часов):**
    *   **Проблема:** За день у сотрудника либо одна метка, либо несколько, но итоговая длительность рабочей сессии (разница между самой ранней и самой поздней меткой) составляет менее 2 часов.
    *   **Решение:** Система автоматически помечает такую сессию как `incomplete` ("незавершенная"). В интерфейсе такой день будет подсвечен как "требующий внимания", чтобы администратор мог вручную проверить данные, исправить их или подтвердить.

2.  **Отсутствие меток за рабочий день:**
    *   **Проблема:** Сотрудник должен был работать (согласно его графику, если он будет реализован) или это стандартный рабочий день, но отметок нет.
    *   **Решение:** Система помечает такой день как "требующий внимания". Администратору будет предложено либо создать запись в таблице `absences`, выбрав тип отсутствия ("Прогул", "Больничный", "Отпуск", "Командировка"), либо вручную ввести часы за этот день (например, для выездной работы).

3.  **Работа в ночное время / Переход через полночь:**
    *   **Проблема:** Смена начинается в один день, а заканчивается в другой.
    *   **Решение:** Согласно требованиям бизнеса, автоматическая обработка таких смен не требуется. Ручной контроль над этими редкими случаями (не чаще 1-2 раз в год) является приоритетом для обеспечения дополнительной проверки. Поэтому, если система обнаруживает метки для одного сотрудника, которые пересекают полночь, она помечает эти дни как "требующие внимания". Администратор должен будет вручную разобрать такой случай и при необходимости скорректировать рабочие сессии. Это решение является осознанным компромиссом, отражающим бизнес-требования.

4.  **Множественные короткие выходы/входы:**
    *   **Проблема:** Сотрудник выходит на короткие перерывы.
    *   **Решение:** Эта проблема неактуальна. Согласно требованиям, сотрудники отмечают только начало и конец рабочего дня. Промежуточные выходы не фиксируются.

### 5.2. Гибкая Тарификация и Расчет Часов

Система поддерживает несколько типов расчета базовой оплаты труда, а также ручные доначисления.

*   **Задача:** Гибко рассчитывать заработную плату на основе типа оплаты сотрудника и отработанного времени.

*   **Решение:**
    1.  **Типы оплаты:** Каждый сотрудник в таблице `employees` имеет поле `payment_type`, которое определяет логику расчета:
        *   **Почасовая (`hourly`):** Стандартный расчет на основе отработанных часов и ставки. Система рассчитывает 4 типа времени (будни норма, будни переработка, выходные норма, выходные переработка) на основе `hourly_rate` сотрудника и множителей из его должности (`positions`).
        *   **Фиксированная (`fixed`):** Сотрудник получает фиксированную сумму (`fixed_rate`) за каждый отработанный день. Поведение при работе в выходные и праздники является настраиваемым:
            *   **По умолчанию:** (`positions.fixed_rate_pays_multipliers` = `FALSE`): Сумма оплаты не зависит от типа дня (будний, выходной или праздник).
            *   **С включенными множителями:** (`positions.fixed_rate_pays_multipliers` = `TRUE`): За работу в выходной или праздничный день сотрудник получит оплату `fixed_rate * holiday_rate_multiplier`.
            *   В любом из этих случаев оплата не зависит от длительности сессии. Любая дополнительная компенсация (например, за переработку по часам) должна производиться через систему бонусов (`payroll_bonuses`).

    2.  **Бонусы и компенсации:** Помимо базовой оплаты, система позволяет администратору добавлять разовые начисления в расчетный лист.
        *   **Реализация:** В режиме Администратора можно добавить записи в таблицу `payroll_bonuses`, связав их с конкретным расчетом (`payrolls`). Это позволяет учитывать премии, компенсации (например, "за молоко") и другие выплаты, которые не зависят от отработанного времени.
        *   Сумма этих начислений будет добавлена в поле `bonus_pay` и учтена в `total_gross_pay`.

### 5.3. Управление Выходными и Праздниками

*   **Задача:** Определять, является ли день рабочим, выходным или праздничным.
*   **Решение:**
    1.  **Выходные:** Дни, у которых `datetime.weekday()` возвращает 5 (суббота) или 6 (воскресенье), всегда считаются выходными (`weekend`).
    2.  **Праздники:** При запуске приложение читает файл `holidays.toml` (или аналогичный), в котором перечислены все официальные праздники и дни переносов.

        **Пример `holidays.toml`:**
        ```toml
        # Список официальных праздничных дней.
        # Система будет считать эти дни нерабочими и применять для них
        # множители 'holiday_rate_multiplier' и 'holiday_overtime_rate_multiplier'.

        [holidays.2025]
        dates = [
          "2025-01-01",  # Новый год
          "2025-01-07",  # Рождество Христово
          "2025-02-23",  # День защитника Отечества
          "2025-03-08",  # Международный женский день
          "2025-05-01",  # Праздник Весны и Труда
          "2025-05-09",  # День Победы
          "2025-06-12",  # День России
          "2025-11-04",  # День народного единства
        ]

        # Пример переноса выходного дня.
        # В данном примере, если 4 января 2025 является выходным (суббота),
        # то он становится рабочим днем, а 2 мая 2025 (пятница) становится выходным.
        [transferred_days.2025]
        "2025-01-04" = "2025-05-02"
        ```

    3.  **Интеграция (будущее):** В будущем "Модуль Импорта Данных" может быть расширен функцией парсинга производственного календаря с внешнего ресурса (например, Консультант Плюс), чтобы автоматически обновлять `holidays.toml`.

### 5.4. Подтверждение Расчета ("Заморозка")

*   **Задача:** Дать администратору возможность проверить итоговые цифры перед окончательным сохранением расчета.
*   **Решение:**
    1.  Администратор выбирает сотрудника и период, запускает расчет.
    2.  Система выполняет все вычисления и создает или перезаписывает в таблице `payrolls` запись-черновик (с `confirmed_at = NULL`).
    3.  На экране отображается **окно предварительного просмотра** на основе данных из этого черновика: "Иванов И.И., период 01.11-30.11. Итого к начислению: X руб. ...".
    4.  **При нажатии кнопки "Подтвердить"** система устанавливает метку времени в поле `confirmed_at` для данного расчета. С этого момента расчет считается официальным и "замороженным".
    5.  Если администратор отменяет операцию или закрывает окно, запись-черновик остается в системе для последующего просмотра или перезаписи при следующем расчете.

### 5.5. Алгоритмы

#### 6.5.1. Алгоритм агрегации событий в рабочие сессии (time_entries -> work_sessions)

Алгоритм основан на простом правиле: рабочая сессия за день определяется самой ранней и самой поздней меткой времени для сотрудника.

**Вход:** Список `time_entries` для одного сотрудника за определенный период.
**Выход:** Список `work_sessions`.

**Шаги:**
1.  **Группировка:** Сгруппировать все `time_entries` по `employee_id` и по дате (`YYYY-MM-DD` из `timestamp`).
2.  **Итерация по группам:** Для каждой группы (т.е. для каждого сотрудника за каждый день):
    *   **Проверка `manual_edit`:** Перед обработкой проверить, существует ли уже для этого дня `work_session` со статусом `manual_edit`. **Если существует, этот день пропускается**, чтобы сохранить ручные изменения администратора.
    *   Если в группе есть записи:
        *   Найти `min_timestamp` (самая ранняя метка) и `max_timestamp` (самая поздняя метка) в группе.
        *   Создать или обновить одну запись `work_session`.
        *   Установить `start_time = min_timestamp`.
        *   Установить `end_time = max_timestamp`.
        *   Рассчитать `duration_hours = (end_time - start_time)`.
        *   **Проверка статуса:**
            *   Если `duration_hours < 2`, установить `status = 'incomplete'`.
            *   Иначе, установить `status = 'completed'`.
        *   **Определение типа дня:** Определить `session_type` (`standard`, `weekend`, `holiday`) на основе даты сессии и списка праздников.
        *   Добавить созданную `work_session` в итоговый список.
3.  **Возврат:** Вернуть список `work_sessions`.

Этот подход не требует определения типа метки ("вход" или "выход"), а также исключает сложную обработку перерывов и ночных смен, которые, согласно требованиям, обрабатываются администратором вручную.

#### 5.5.2. Алгоритм расчета заработной платы (work_sessions -> payrolls)

**Вход:** `employee_id`, `period_start`, `period_end`.
**Выход:** Объект `payroll` для сотрудника за период.

**Шаги:**
1.  **Получение данных о сотруднике:** Получить `payment_type`, `hourly_rate`, `fixed_rate` и `position_id` из таблицы `employees`. Получить `standard_workday_hours` и множители из связанной таблицы `positions`.
2.  **Инициализация:**
    *   `base_pay = 0`, `bonus_pay = 0`, `paid_absence_amount = 0`, `unpaid_deduction = 0`.
    *   Инициализировать переменные для хранения часов и дней (`weekday_standard_hours`, `work_days_count` и т.д.) нулями.
3.  **Получение рабочих сессий:** Получить все `work_sessions` для сотрудника за период.
4.  **Расчет отсутствий и вычетов:**
    *   Найти все записи в `absences` для сотрудника, пересекающиеся с расчетным периодом.
    *   Для каждого дня в периоде отсутствия:
        *   **Правило приоритета:** Если на этот день существует `work_session`, запись об отсутствии за этот день **игнорируется** для избежания двойной оплаты.
        *   Если `work_session` нет:
            *   Если `absence.is_paid == TRUE`:
                *   **Для `hourly`:** `paid_absence_amount += standard_workday_hours * hourly_rate * absence.payment_multiplier`.
                *   **Для `fixed`:** Оплачиваемые отсутствия не меняют итоговую сумму, поэтому `paid_absence_amount` не увеличивается.
            *   Если `absence.is_paid == FALSE`:
                *   **Для `hourly`:** Ничего не происходит.
                *   **Для `fixed`:** Рассчитывается вычет. `unpaid_deduction += fixed_rate / <кол-во рабочих дней в месяце>`.
5.  **Проверка типа оплаты (расчет `base_pay`):**
    *   **ЕСЛИ `payment_type` == 'hourly':**
        *   Для каждой `work_session`:
            *   Определить `session_type` (`standard`, `weekend`, `holiday`).
            *   **Правило расчета сверхурочных:** Все часы, отработанные в `standard` день сверх нормы `standard_workday_hours`, считаются сверхурочными (`overtime`).
            *   Распределить `duration_hours` сессии на `standard` и `overtime` часы.
            *   Накопить часы в `weekday_standard_hours`, `weekday_overtime_hours` и т.д.
        *   Рассчитать `base_pay` путем суммирования оплаты по всем категориям часов с учетом множителей.
    *   **ЕСЛИ `payment_type` == 'fixed':**
        *   Получить флаг `fixed_rate_pays_multipliers` из должности сотрудника.
        *   Получить все `work_sessions` для сотрудника за `period_start` и `period_end`.
        *   Отфильтровать сессии, оставив только те, у которых статус `completed`, `manual_edit` или `auto_generated`.
        *   Сгруппировать отфильтрованные сессии по уникальным дням.
        *   **ЕСЛИ `fixed_rate_pays_multipliers` == FALSE:**
            *   `work_days_count` = количество уникальных дней.
            *   Рассчитать `base_pay = work_days_count * fixed_rate`.
        *   **ЕСЛИ `fixed_rate_pays_multipliers` == TRUE:**
            *   `base_pay = 0`.
            *   Для каждого уникального дня:
                *   Определить `session_type` этого дня (`standard`, `weekend`, `holiday`).
                *   Если `session_type` == 'standard', то `base_pay += fixed_rate`.
                *   Если `session_type` == 'weekend' или 'holiday', то `base_pay += fixed_rate * holiday_rate_multiplier`.
            *   `work_days_count` = количество уникальных дней (для информации).
6.  **Расчет бонусов:**
    *   Найти все `payroll_bonuses` для данного расчета и просуммировать их в `bonus_pay`.
7.  **Расчет итоговой суммы:**
    *   `total_gross_pay = base_pay + bonus_pay + paid_absence_amount - unpaid_deduction`
8.  **Создание/Обновление объекта `payroll`:**
    *   Сохранить все рассчитанные значения в соответствующей записи `payrolls`.
9.  **Возврат:** Объект `payroll`.

### 5.6. Примеры расчетов заработной платы

Чтобы продемонстрировать логику алгоритма, рассмотрим несколько примеров.

---

#### Пример 1: Сотрудник с почасовой оплатой (`hourly`)

**Входные данные:**
*   **Сотрудник:** Иванов Иван Иванович, `payment_type` = 'hourly', `hourly_rate` = 500.00 руб/час.
*   **Должность:** "Инженер", `standard_workday_hours` = 8.0, `weekday_overtime_multiplier` = 1.5, `holiday_rate_multiplier` = 2.0.
*   **Период:** Ноябрь 2025.
*   **Агрегированные данные:**
    *   `weekday_standard_hours`: 160 часов
    *   `weekday_overtime_hours`: 10 часов
    *   `holiday_standard_hours`: 8 часов (1 смена в праздник)

**Расчет `base_pay`:**
1.  **Оплата за стандартные часы в будни:**
    *   `160 часов * 500.00 руб/час = 80,000.00 руб.`
2.  **Оплата за переработку в будни:**
    *   `10 часов * 500.00 руб/час * 1.5 = 7,500.00 руб.`
3.  **Оплата за работу в праздник:**
    *   `8 часов * 500.00 руб/час * 2.0 = 8,000.00 руб.`
4.  **Итого `base_pay`:**
    *   `80000 + 7500 + 8000 = 95,500.00 руб.`

**Итоговая сумма (`total_gross_pay`):** `95,500.00 руб.` (без бонусов и отсутствий).

---

#### Пример 2: Сотрудник с фиксированной оплатой (`fixed`)

**Входные данные:**
*   **Сотрудник:** Петров Петр Петрович, `payment_type` = 'fixed', `fixed_rate` = 2500.00 руб/день.
*   **Период:** Ноябрь 2025.
*   **Агрегированные данные:** За период найдено 22 дня, в которые были `completed` рабочие сессии.

**Расчет `base_pay`:**
1.  **Оплата за отработанные дни:**
    *   `22 дня * 2500.00 руб/день = 55,000.00 руб.`
2.  **Итого `base_pay`:** `55,000.00 руб.`

**Итоговая сумма (`total_gross_pay`):** `55,000.00 руб.` (вне зависимости от часов и переработок).

---

#### Пример 3: Почасовая оплата + Оплачиваемый отпуск + Бонус

**Входные данные:**
*   **Сотрудник:** Сидорова Анна Сергеевна, `payment_type` = 'hourly', `hourly_rate` = 400.00 руб/час.
*   **Должность:** "Бухгалтер", `standard_workday_hours` = 8.0.
*   **Период:** Ноябрь 2025.
*   **Агрегированные данные:**
    *   `weekday_standard_hours`: 120 часов.
    *   `weekday_overtime_hours`: 0 часов.
    *   **Отсутствие:** 5 рабочих дней в отпуске (`absence_type.is_paid` = TRUE, `payment_multiplier` = 1.0).
    *   **Бонус:** В `payroll_bonuses` добавлена запись: `name`="Квартальная премия", `amount`=15000.00.

**Расчет:**
1.  **Расчет `base_pay` (за отработанное время):**
    *   `120 часов * 400.00 руб/час = 48,000.00 руб.`
2.  **Расчет `paid_absence_amount` (за отпуск):**
    *   Оплата за день отпуска рассчитывается по среднему заработку, но для упрощения примем его равным стандартному дню.
    *   `5 дней * 8 часов/день * 400.00 руб/час * 1.0 = 16,000.00 руб.`
3.  **Расчет `bonus_pay` (бонусы):**
    *   `bonus_pay = 15,000.00 руб.`

**Итоговая сумма к начислению (`total_gross_pay`):**
*   `48,000.00 (base) + 16,000.00 (absence) + 15,000.00 (bonus) = 79,000.00 руб.`

Эти примеры будут использоваться как эталонные тесты для проверки корректности реализации модуля расчета заработной платы.

### 5.7. Жизненный цикл расчета и корректировки (Прагматичный подход)

Для обеспечения целостности финансовых данных и наличия полного аудиторского следа, в системе принят упрощенный, но надежный жизненный цикл для расчетов ЗП (`payrolls`).

*   **Черновики и Подтвержденные расчеты:**
    *   Любой расчет, у которого поле `confirmed_at` равно `NULL`, считается **черновиком**.
    *   Расчет, у которого поле `confirmed_at` имеет метку времени, считается **подтвержденным** и является официальным документом. Подтвержденные расчеты неизменяемы.

*   **Политика для черновиков:**
    *   Для одной пары "сотрудник-период" может существовать только один активный расчет (черновик или подтвержденный, который не был скорректирован).
    *   При каждом запуске расчета или пересчете система находит существующий черновик для данного сотрудника и периода и **полностью перезаписывает** его новыми данными. Если черновика нет, он создается.

*   **Процесс подтверждения:**
    1.  Администратор проверяет данные черновика в окне предварительного просмотра.
    2.  При нажатии кнопки "Подтвердить" система устанавливает текущую метку времени в поле `confirmed_at` для данного расчета. С этого момента расчет "заморожен" и не может быть изменен или удален.

*   **Процесс корректировки:**
    1.  Администратор находит в системе **подтвержденный** расчет, который нужно исправить.
    2.  Он инициирует действие "Создать корректировку".
    3.  Система позволяет вносить изменения в исходные данные за этот период (`time_entries`, `absences`, `payroll_bonuses`).
    4.  После внесения правок администратор заново запускает расчет ЗП.
    5.  Система создает **новую** запись в `payrolls` (новый черновик). В поле `supersedes_payroll_id` этого нового расчета записывается `id` старого, подтвержденного расчета, который он должен заменить.
    6.  Когда администратор подтверждает этот новый черновик (устанавливается его `confirmed_at`), он становится новым официальным расчетом за период. Старый расчет при этом не изменяется, но при построении отчетов система будет знать, что он был заменен.

Этот механизм гарантирует, что история всех начислений сохраняется, и всегда можно отследить, какой расчет является актуальным, а какой был скорректирован, без усложненной системы статусов.

## 7. Сценарии Использования (Use Cases)

### 6.1. Режим Администратор: Добавление нового сотрудника

*   **Актер:** Администратор
*   **Предусловия:** Введен пароль Администратора.
*   **Основной поток:**
    1.  Администратор открывает раздел "Управление сотрудниками".
    2.  Нажимает кнопку "Добавить нового сотрудника".
    3.  Система отображает форму для ввода данных: Полное имя, Должность, Тип оплаты (`hourly` или `fixed`), Почасовая ставка, Фиксированная ставка.
    4.  Администратор заполняет поля. В зависимости от выбранного типа оплаты, соответствующее поле ставки становится обязательным.
    5.  Нажимает "Сохранить".
    6.  Система валидирует данные и создает новую запись в `employees`.
    7.  Система отображает сообщение об успехе.
*   **Правила валидации:**
    *   `payment_type` = 'hourly' требует `hourly_rate` > 0.
    *   `payment_type` = 'fixed' требует `fixed_rate` > 0.

### 6.2. Режим Администратор: Изменение данных сотрудника

*   **Актер:** Администратор
*   **Предусловия:** Введен пароль Администратора.
*   **Основной поток:**
    1.  Администратор выбирает сотрудника для редактирования.
    2.  Система отображает форму с текущими данными сотрудника.
    3.  Администратор изменяет необходимые поля (должность, тип оплаты, ставки).
    4.  Нажимает "Сохранить".
    5.  Система валидирует и обновляет запись в `employees`.
    6.  Система отображает сообщение об успехе.

### 6.3. Режим Администратор: Обработка логов и расчет ЗП

*   **Актер:** Администратор
*   **Предусловия:** Введен пароль Администратора.
*   **Основной поток:**
    1.  Администратор открывает раздел "Импорт и Расчет".
    2.  Выбирает файл `1_attlog.dat` и указывает расчетный период.
    3.  Нажимает "Запустить обработку".
    4.  **Система выполняет импорт данных:**
        *   Для каждой строки в файле система проверяет, существует ли уже такая строка в `raw_log_data` (по полному содержанию `raw_line_content`). **Если строка уже существует, она пропускается.**
        *   Новые уникальные строки парсятся, валидируются и сохраняются в `raw_log_data` и `time_entries`.
    5.  **Система агрегирует `time_entries` в `work_sessions`** для указанного периода согласно алгоритму 5.5.1.
    6.  **Система выполняет предварительный расчет ЗП** для всех сотрудников согласно алгоритму 5.5.2 и создает/перезаписывает записи-черновики `payrolls` (`confirmed_at = NULL`).
    7.  Система отображает **окно предварительного просмотра**, где видны все расчеты-черновики и подсвечены проблемные сессии (`incomplete`).
    8.  Администратор может перейти к редактированию (UC 6.4, 6.5, 6.6) или нажать "Подтвердить".
    9.  При подтверждении система устанавливает метку времени в поле `confirmed_at` для соответствующих расчетов.
    10. Система отображает сообщение об успешном завершении.
*   **Альтернативные потоки:**
    *   **6.3a. Ошибки парсинга:** Некорректные строки в лог-файле пропускаются, информация о них выводится в лог ошибок.

### 6.4. Режим Администратор: Ручная корректировка данных

*   **Актер:** Администратор
*   **Предусловия:** Введен пароль Администратора. Существует расчет-черновик (`confirmed_at` IS NULL).
*   **Основной поток:**
    1.  Из окна предварительного просмотра (UC 6.3) администратор выбирает день сотрудника, требующий внимания.
    2.  Система открывает интерфейс редактирования, где администратор может:
        *   **Добавить/изменить/удалить метки времени** (`time_entries`).
        *   **Создать запись об отсутствии** (`absences`) для этого дня.
        *   **Добавить бонус/компенсацию** (`payroll_bonuses`).
    3.  После внесения изменений администратор нажимает "Пересчитать".
    4.  Система обновляет `work_sessions` и перезаписывает черновик `payrolls` и возвращает администратора к обновленному окну предварительного просмотра.

### 6.5. Режим Администратор: Автоматическая генерация данных

*   **Актер:** Администратор
*   **Предусловия:** Введен пароль Администратора. Расчет находится в статусе `draft`.
*   **Основной поток:**
    1.  В окне предварительного просмотра администратор нажимает "Автоматически исправить".
    2.  Система для всех `incomplete` сессий применяет заранее заданные правила (например, для сессии с одной меткой добавляет вторую через `standard_workday_hours`).
    3.  Сгенерированные сессии помечаются статусом `auto_generated`.
    4.  Система автоматически запускает перерасчет и обновляет окно предварительного просмотра.
    5.  Администратор может просмотреть изменения и при необходимости откорректировать их вручную (UC 6.4).

### 6.6. Режим просмотра: Просмотр рабочего времени

*   **Актер:** Любой сотрудник
*   **Предусловия:** Осуществлен вход с пустым паролем (активирован Режим Просмотра).
*   **Основной поток:**
    1.  Пользователь открывает раздел "Отчеты по рабочему времени".
    2.  Выбирает сотрудника (или всех) и указывает период.
    3.  Нажимает "Показать отчет".
    4.  Система отображает отчет по `work_sessions`, включающий:
        *   Даты и длительность рабочих сессий.
        *   Статусы сессий (`completed`, `incomplete` и т.д.).
        *   Общее количество отработанных часов за период.
    5.  **Вся финансовая информация (ставки, зарплата) скрыта.**
*   **Пост-условия:** Пользователь просмотрел отчет. Состояние системы не изменилось.

Этот раздел описывает жизненный цикл ключевых сущностей системы.

#### 8.3.1. Диаграмма состояний для `payroll` (Расчет ЗП)

```stateDiagram-v2
    [*] --> Draft: Создание/Пересчет
    Draft --> Confirmed: Подтверждение
    Confirmed --> Superseded: Создание корректировки
    Superseded --> [*]: (конечное состояние)
    Draft --> [*]: Отмена
```
*   **Draft (Черновик):** Расчет создан (`confirmed_at` IS NULL). Может быть изменен или удален.
*   **Confirmed (Подтвержден):** Расчет подтвержден (`confirmed_at` IS NOT NULL). Является официальным и неизменяемым.
*   **Superseded (Замещен):** Это не статус, а свойство. Когда для `Confirmed` расчета создается корректировка, он логически становится замещенным, уступая место новому расчету. Физически старый расчет не меняется, сохраняясь для истории.

#### 8.3.2. Диаграмма состояний для `work_session` (Рабочая сессия)

```stateDiagram-v2
    [*] --> incomplete: Длительность < 2ч
    [*] --> completed: Длительность >= 2ч

    incomplete --> manual_edit: Ручная правка
    completed --> manual_edit: Ручная правка

    incomplete --> auto_generated: Авто-генерация
    auto_generated --> manual_edit: Ручная правка
    manual_edit --> manual_edit: Ручная правка
```
*   **incomplete/completed:** Начальные статусы, присваиваемые после автоматической агрегации.
*   **auto_generated:** Статус присваивается сессии, если она была создана или изменена автоматическим правилом (например, добавление второй метки).
*   **manual_edit:** Статус присваивается после любого ручного вмешательства администратора.

## 10. Безопасность

Этот раздел описывает прагматичный подход к безопасности, соответствующий масштабу и рискам для локального десктоп-приложения.

### 9.1. Аутентификация и Авторизация

Система использует простую, но эффективную модель разграничения доступа, основанную на двух режимах работы.

*   **Аутентификация:**
    *   При запуске приложения пользователю предлагается ввести пароль.
    *   **Пароль Администратора:** В системе будет храниться один хешированный пароль для доступа к режиму Администратора. Пароль задается при первоначальной настройке программы. Для хеширования будет использоваться стойкий и проверенный временем алгоритм **`bcrypt`**. Этот пароль также используется как ключ для расшифровки файла базы данных.
    *   **Пароль для Просмотра:** Для режима просмотра будет использоваться отдельный, менее привилегированный пароль. Он также будет храниться в хешированном виде.
    *   **Вход:** Ввод правильного пароля Администратора активирует "Режим Администратора" и позволяет расшифровать БД с полными правами. Ввод правильного пароля для Просмотра активирует "Режим Просмотра" и позволяет расшифровать БД с доступом только на чтение.

*   **Авторизация (Разделение по режимам):**
    *   **Режим Администратора:** Предоставляет полный доступ ко всем функциям системы, включая редактирование данных и расчет заработной платы.
    *   **Режим Просмотра:** Предоставляет доступ только на чтение к неконфиденциальным данным (табели учета времени без финансовой информации). Любые операции записи или изменения данных будут запрещены на уровне приложения.

### 9.2. Защита Данных

*   **Основной принцип:** Защита данных строится на **шифровании файла базы данных**. Это обеспечивает надежную защиту конфиденциальной информации даже в случае несанкционированного доступа к файлу БД.
*   **Шифрование файла БД:** Файл `tessera.db` будет зашифрован с использованием **SQLCipher** (через библиотеку `pysqlcipher3` или аналогичную). Пароль, вводимый пользователем при входе, будет использоваться как ключ для расшифровки базы данных в оперативной памяти. Таким образом, данные на диске всегда остаются зашифрованными.
*   **Защита от SQL-инъекций:** Все запросы к базе данных будут формироваться с использованием параметризованных запросов (prepared statements) или через ORM/Core-инструментарий SQLAlchemy, что исключает риск SQL-инъекций.

### 9.3. Аудит Действий

*   **Стратегия:** Вместо сложной системы аудита на основе триггеров в БД, аудит ключевых действий будет производиться через **стандартный механизм логирования** (`logging`) на уровне сервисов приложения (Application Layer).
*   **Что логируется:**
    *   `INFO`: Вход пользователя в режиме Администратора.
    *   `INFO`: Запуск и завершение импорта данных.
    *   `INFO`: Запуск и подтверждение расчета ЗП (`payroll.id`, `employee_id`, `period`).
    *   `INFO`: Создание, изменение или деактивация сотрудника (`employee.id`).
    *   `INFO`: Ручное изменение рабочих сессий или отметок времени.
*   **Преимущества:**
    *   **Простота:** Не требует поддержки сложной логики триггеров в БД.
    *   **Надежность:** Логика аудита находится в коде приложения и версионируется вместе с ним.
    *   **Достаточность:** Для локального приложения с одним администратором детального логирования в файл достаточно для разбора инцидентов.

## 11. Обработка ошибок и логирование

### 10.1. Иерархия Исключений

Для предсказуемой обработки ошибок вводится базовая иерархия исключений.

```python
class TesseraError(Exception):
    """Базовое исключение для всех ошибок приложения."""
    pass

class ValidationError(TesseraError):
    """Ошибка валидации данных (например, неверный формат ID)."""
    pass

class BusinessRuleError(TesseraError):
    """Нарушение бизнес-правила (например, попытка рассчитать ЗП без данных)."""
    pass

class InfrastructureError(TesseraError):
    """Ошибка инфраструктурного слоя (например, файл БД не найден)."""
    pass
```

### 10.2. Стратегия обработки ошибок

*   **Presentation Layer:** Отвечает за перехват всех исключений, унаследованных от `TesseraError`. Он не должен пропускать "сырые" исключения пользователю.
*   **Application & Domain Layers:** Генерируют специфичные исключения (`ValidationError`, `BusinessRuleError`).
*   **Infrastructure Layer:** Генерирует `InfrastructureError` при проблемах с доступом к ресурсам.
*   **Пользовательские сообщения:** На основе типа перехваченного исключения, UI показывает пользователю понятное сообщение об ошибке, предлагая возможное решение. Технические детали при этом логируются, но не отображаются.

### 10.3. Стратегия Логирования

*   **Библиотека:** Стандартный модуль `logging` в Python.
*   **Уровни логирования:**
    *   `DEBUG`: Детальная информация для отладки (трассировки вызовов, значения переменных). Включается только в режиме разработки.
    *   `INFO`: Ключевые бизнес-события (запуск импорта, завершение расчета ЗП, вход пользователя).
    *   `WARNING`: Нештатные, но не критичные ситуации (пропуск некорректной строки в лог-файле, незавершенная сессия).
    *   `ERROR`: Серьезные ошибки, которые не привели к падению приложения, но требуют внимания (ошибка доступа к файлу, нарушение целостности БД).
    *   `CRITICAL`: Ошибки, приводящие к аварийному завершению работы.
*   **Формат логов:** Структурированный текстовый формат, включающий `timestamp`, `level`, `module_name` и `message`.
*   **Хранение и Ротация:**
    *   Логи пишутся в файл `tessera.log` в папке с приложением.
    *   Реализована ротация по размеру: при достижении 10 МБ создается новый файл. Хранится до 5 архивных файлов.

## 12. Структура Проекта

Этот раздел описывает предлагаемую структуру каталогов и файлов проекта, которая строго соответствует слоистой архитектуре (Domain, Application, Infrastructure, Presentation) для обеспечения максимальной модульности и чистоты кода.

### 12.1. Общая Структура Каталогов
```
tessera/

│   └── integration/
│
└── main.py                   # Точка входа в приложение
```

### 12.2. Описание Модулей

*   **`application/`**: Определяет, *что* система может делать (Use Cases).
    *   `services.py`: Формальные "контракты" или интерфейсы для сервисов (`PayrollService`, `EmployeeService`), которые будет использовать слой представления.
    *   `dto.py`: Структуры данных для обмена информацией между слоями, чтобы UI не зависел от доменных моделей.
*   **`domain/`**: Ядро системы, содержит всю бизнес-логику. **Не зависит ни от какого другого слоя.**
    *   `entities.py`: Чистые бизнес-сущности (`Employee`, `WorkSession`) и их логика.
    *   `repositories.py`: Абстрактные интерфейсы для хранения и извлечения сущностей (`EmployeeRepository`, `WorkSessionRepository`).
    *   `services.py`: Сервисы, инкапсулирующие сложную бизнес-логику, которая не помещается в одну сущность (например, `PayrollCalculationService`).
*   **`infrastructure/`**: Реализует "как" система выполняет задачи, определенные в `application` и `domain`.
    *   `database/`: Конкретная реализация хранения данных с помощью SQLAlchemy. `repositories.py` здесь реализует интерфейсы из `domain.repositories`.
    *   `parsers/`: Реализация парсеров для `.dat` файлов.
    *   `services/`: Конкретные реализации сервисов из `application.services`, которые координируют работу доменных объектов и репозиториев.
*   **`presentation/`**: Пользовательский интерфейс. Взаимодействует только со слоем `application`.
*   **`reporting/`**: Модуль для генерации отчетов. Он действует как клиент для `application` сервисов, запрашивая у них данные и форматируя их в файлы.
*   **`main.py`**: Точка входа. Собирает все вместе: создает экземпляры реализаций из `infrastructure`, передает их в `presentation` (Dependency Injection) и запускает приложение.

## 13. Стратегия Тестирования

Этот раздел описывает подход к тестированию системы для обеспечения ее качества, надежности и соответствия требованиям.

### 12.1. Типы Тестирования

*   **Модульное тестирование (Unit Tests):**
    *   **Цель:** Проверка корректности работы отдельных функций, методов и классов в изоляции.
    *   **Покрытие:** Минимум 80% покрытия кода для критически важных модулей (бизнес-логика, алгоритмы расчета, парсеры).
    *   **Примеры:** Тесты для функций расчета часов, валидаторов, методов репозиториев.
*   **Интеграционное тестирование (Integration Tests):**
    *   **Цель:** Проверка взаимодействия между различными компонентами системы (например, Core Service с Repository и БД, Ingestion с Core).
    *   **Примеры:** Тестирование полного цикла импорта данных из файла в БД, тестирование расчета ЗП с использованием реальных данных из БД.
*   **Функциональное/Системное тестирование (Functional/System Tests):**
    *   **Цель:** Проверка соответствия системы функциональным требованиям, описанным в Use Cases.
    *   **Примеры:** Тестирование полного сценария добавления сотрудника через UI, запуск расчета ЗП и генерация отчета.
*   **Приемочное тестирование (Acceptance Tests):**
    *   **Цель:** Проверка системы конечными пользователями или представителями бизнеса на соответствие их ожиданиям.
*   **Тестирование пользовательского интерфейса (UI/E2E Tests):**
    *   **Цель:** Автоматизированная проверка взаимодействия пользователя с UI и корректности отображения данных.
    *   **Инструменты:** Могут использоваться фреймворки для автоматизации UI (например, `PyQt` имеет свои инструменты для тестирования, или сторонние библиотеки).

### 12.2. Инструменты и Подходы

*   **Фреймворк для тестирования:** `pytest` (для Python) как основной фреймворк для модульных и интеграционных тестов.
*   **Тестовые данные (Test Data Fixtures):** Использование фикстур для создания контролируемых и воспроизводимых тестовых данных.
*   **Мокирование (Mocking):** Использование моков и стабов для изоляции тестируемых компонентов и имитации внешних зависимостей (например, БД, файловой системы).
*   **Непрерывная интеграция (CI):** Интеграция тестов в процесс CI для автоматического запуска при каждом изменении кода.

### 12.3. Покрытие Кода (Code Coverage)

*   **Цель:** Поддержание высокого уровня покрытия кода тестами, особенно для критически важных частей системы.
*   **Инструменты:** `coverage.py` для измерения покрытия.
*   **Желаемая цель:** Стремиться к покрытию не менее 80% для модулей `core/services`, `core/validators`, `ingestion/parsers`. Однако, приоритетом является не достижение конкретной цифры, а полное покрытие критических бизнес-сценариев.

### 12.4. Критически важные сценарии для тестирования

Следующие сценарии должны быть в обязательном порядке покрыты автоматическими тестами (модульными и интеграционными) для обеспечения корректности бизнес-логики:

*   **Расчет ЗП для `hourly` сотрудника:**
    *   Корректное разделение часов на стандартные и сверхурочные.
    *   Правильное применение множителей для будних, выходных и праздничных дней.
*   **Расчет ЗП для `fixed` сотрудника:**
    *   Корректный расчет на основе количества отработанных дней.
    *   Правильное применение вычетов за неоплачиваемые отсутствия.
*   **Обработка отсутствий:**
    *   Расчет оплаты для `hourly` сотрудника в оплачиваемом отпуске/больничном.
    *   Игнорирование записи об отсутствии, если в тот же день есть рабочая сессия.
*   **Граничные случаи в логах:**
    *   Обработка лог-файла с отсутствием меток для сотрудника.
    *   Обработка смен, переходящих через полночь (ручной режим).
    *   Игнорирование записей с неправдоподобной датой (например, 2000 год).
*   **Жизненный цикл расчета:**
    *   Проверка корректности создания `draft` расчета.
    *   Проверка перезаписи `draft` расчета при повторном вычислении.
    *   Проверка смены статусов `draft` -> `confirmed` -> `archived` при корректировке.

## 14. Производственная эксплуатация

Этот раздел описывает, как приложение будет развертываться, обслуживаться и мониториться в производственной среде, с учетом лучших практик для Windows-приложений.

### 13.1. Развертывание (Deployment)

*   **Формат поставки:** Приложение будет распространяться в виде установщика (`Tessera_Setup_vX.Y.Z.exe`), созданного с помощью **NSIS** или **Inno Setup**.
*   **Структура каталогов:**
    *   **Каталог установки (Install Dir):** `C:\Program Files\Tessera\`
        *   **Содержимое:** Только **read-only** файлы приложения: исполняемый файл `.exe`, библиотеки, ресурсы, скрипты миграций. Приложение не будет пытаться записывать данные в этот каталог.
    *   **Каталог данных (Data Dir):** `%LOCALAPPDATA%\Tessera\` (например, `C:\Users\<Username>\AppData\Local\Tessera\`)
        *   **Содержимое:** Все изменяемые данные: файл базы данных (`tessera.db`), логи (`tessera.log`), резервные копии (`backups/`), конфигурационные файлы.
*   **Процесс установки:**
    1.  Пользователь запускает установщик.
    2.  Установщик копирует файлы приложения в **Install Dir**.
    3.  Создается ярлык на рабочем столе.
    4.  При первом запуске приложение проверяет наличие **Data Dir**. Если его нет, оно создается.
    5.  Система предлагает создать пароль администратора и выполняет инициализацию базы данных в **Data Dir**.
*   **Процесс обновления:**
    1.  Перед установкой новой версии будет автоматически создаваться резервная копия текущей базы данных в **Data Dir**.
    2.  Новый установщик заменяет файлы приложения в **Install Dir**.
    3.  При первом запуске новой версии автоматически применяются миграции базы данных (см. раздел 13.4).

### 13.2. Резервное копирование и восстановление

*   **Стратегия резервного копирования:**
    *   **Автоматически:** Приложение создает резервную копию файла БД при каждом закрытии.
    *   **Вручную:** Администратор может создать бэкап в любой момент через UI.
    *   **Хранение:** Бэкапы хранятся в подпапке `backups` внутри **Data Dir** в формате `tessera_backup_YYYY-MM-DD_HH-MM-SS.db.zip`.
*   **Стратегия восстановления:**
    *   Администратор выбирает файл бэкапа через UI.
    *   Система показывает предупреждение о полной замене текущих данных.
    *   После подтверждения происходит замена файла БД в **Data Dir** и перезапуск соединения.

### 13.3. Мониторинг

*   **Лог-файлы:** Основной инструмент мониторинга. Лог-файл `tessera.log` находится в **Data Dir**. Администратор должен периодически проверять его на наличие записей уровня `ERROR` и `CRITICAL`.
*   **Состояние системы:** В UI будет предусмотрен раздел "О системе", где будет отображаться:
    *   Версия приложения.
    *   Путь к каталогу данных (**Data Dir**).
    *   Текущий размер базы данных.
    *   Время последнего успешного бэкапа.
*   **Оповещения:** В будущих версиях могут быть добавлены email-оповещения для критических ошибок или неудачных бэкапов.

### 13.4. Механизм Миграций Базы Данных

Для обеспечения автоматического и надежного обновления схемы БД при выпуске новых версий приложения будет использоваться следующий механизм:

*   **Включение миграций в сборку:** Каталог `migrations/` со всеми скриптами Alembic будет включен в состав исполняемого файла `.exe` как ресурс (data file) при сборке с помощью PyInstaller.
*   **Процесс при запуске приложения:**
    1.  При каждом запуске, до инициализации основного UI, приложение выполняет следующую процедуру.
    2.  Программно создается конфигурация Alembic, указывающая путь к каталогу миграций (внутри временной директории, куда PyInstaller распаковывает ресурсы) и путь к файлу базы данных в **Data Dir**.
    3.  Выполняется команда `alembic.command.current` для получения текущей версии схемы из таблицы `alembic_version` в БД.
    4.  Эта версия сравнивается с последней доступной версией в коде миграций.
    5.  Если версия БД устарела, программно выполняется команда `alembic.command.upgrade(config, 'head')` для обновления схемы до последней версии.
*   **Обработка ошибок:**
    *   Любая ошибка в процессе миграции является критической, так как может оставить БД в неконсистентном состоянии.
    *   В случае сбоя миграции, приложение запишет в лог ошибку уровня `CRITICAL`, покажет пользователю фатальное сообщение об ошибке с предложением восстановить БД из резервной копии и завершит свою работу.

## 15. Риски и их митигация

Этот раздел описывает потенциальные технические и операционные риски, а также стратегии их предотвращения или смягчения последствий.

### 14.1. Большой объем файла логов

*   **Риск:** Обработка файла `1_attlog.dat` очень большого размера (например, несколько гигабайт, содержащих логи за много лет) может привести к чрезмерному потреблению оперативной памяти и сбою приложения (OutOfMemory).
*   **Митигация:** Модуль импорта данных (`Ingestion Layer`) должен быть реализован с использованием потоковой обработки (stream processing). Парсер должен читать файл строка за строкой, а не загружать его целиком в память.

### 14.2. Повреждение файла базы данных

*   **Риск:** Будучи единым файлом, база данных SQLite подвержена риску повреждения из-за сбоев системы, некорректного завершения работы приложения или проблем с диском. Это может привести к полной потере данных.
*   **Митигация:**
    1.  **Резервное копирование:** Основной мерой является строгая стратегия резервного копирования, описанная в разделе 13.1.
    2.  **WAL-режим:** Для повышения отказоустойчивости рекомендуется использовать для SQLite режим [Write-Ahead Logging (WAL)](https://www.sqlite.org/wal.html). Он снижает вероятность повреждения БД при сбоях.

### 14.3. Сложные или непредусмотренные паттерны работы

*   **Риск:** Алгоритм агрегации `work_sessions` может не покрыть все возможные реальные сценарии работы сотрудников (например, несколько смен с большими перерывами в один день, которые не должны объединяться).
*   **Митигация:**
    1.  **Ручное редактирование:** Система предоставляет администратору полный контроль над `time_entries` и `work_sessions` (Use Case 6.6), что позволяет вручную исправить любую ситуацию, некорректно обработанную алгоритмом.
    2.  **Аудит:** Все ручные изменения логируются с уровнем `INFO` через стандартный механизм логирования, обеспечивая прозрачность.

### 14.4. Ошибки при ручном вводе данных

*   **Риск:** Администратор может допустить ошибку при ручном вводе недостающих меток, корректировке сессий или создании записей об отсутствии, что приведет к неверному расчету ЗП.
*   **Митигация:**
    1.  **Валидация на уровне UI:** Все формы ввода должны иметь строгую валидацию (например, проверка, что время окончания позже времени начала; проверка корректности форматов).
    2.  **Жизненный цикл расчета:** Процесс `draft` -> `confirmed` (раздел 5.7) дает администратору возможность проверить все цифры перед окончательным утверждением расчета.

## 17. Интерфейсы Сервисного Слоя (Application Service Interfaces)

Этот раздел формализует контракты между слоем представления (UI) и слоем приложения (Application). Он определяет структуры данных (DTO) и публичные методы сервисов.

### 17.1. Объекты Передачи Данных (Data Transfer Objects - DTOs)

DTO используются для передачи данных между слоями, чтобы избежать прямой зависимости UI от доменных моделей.

```python
from dataclasses import dataclass
from datetime import date, datetime
from decimal import Decimal

# --- DTO для Сотрудников ---
@dataclass
class EmployeeDTO:
    id: int
    full_name: str
    position_name: str
    payment_type: str  # 'hourly' или 'fixed'
    is_active: bool

@dataclass
class EmployeeDetailsDTO(EmployeeDTO):
    hourly_rate: Decimal
    fixed_rate: Decimal

# --- DTO для Рабочего Времени ---
@dataclass
class WorkSessionDTO:
    id: int
    employee_id: int
    start_time: datetime
    end_time: datetime | None
    duration_hours: Decimal
    status: str  # 'completed', 'incomplete', 'manual_edit', 'auto_generated'
    session_type: str # 'standard', 'weekend', 'holiday'

# --- DTO для Расчета ЗП ---
@dataclass
class PayrollPreviewDTO:
    id: int
    employee_id: int
    period_start: date
    period_end: date
    total_gross_pay: Decimal
    is_confirmed: bool
    is_superseded: bool # Является ли расчет замененным более новым

@dataclass
class PayrollDetailsDTO(PayrollPreviewDTO):
    work_days_count: int | None
    weekday_standard_hours: Decimal | None
    # ... и другие поля из таблицы payrolls
    base_pay: Decimal
    bonus_pay: Decimal
    paid_absence_amount: Decimal

# --- DTO для Результатов Операций ---
@dataclass
class ImportResultDTO:
    new_entries_count: int
    duplicate_entries_count: int
    invalid_entries_count: int
```

### 17.2. Интерфейсы Сервисов (Service Protocols)

Интерфейсы определяют публичные методы, доступные для вызова из слоя представления.

```python
from typing import Protocol, List

class EmployeeService(Protocol):
    def get_all_employees(self) -> List[EmployeeDTO]: ...
    def get_employee_details(self, employee_id: int) -> EmployeeDetailsDTO: ...
    def create_employee(self, details: EmployeeDetailsDTO) -> EmployeeDTO: ...
    def update_employee(self, employee_id: int, details: EmployeeDetailsDTO) -> EmployeeDTO: ...

class IngestionService(Protocol):
    def import_from_file(self, file_path: str) -> ImportResultDTO: ...

class SessionService(Protocol):
    def get_sessions_for_period(self, employee_id: int, start: date, end: date) -> List[WorkSessionDTO]: ...
    def build_sessions_for_period(self, start: date, end: date) -> None: ...
    def update_session(self, session_id: int, details: WorkSessionDTO) -> WorkSessionDTO: ...

class PayrollService(Protocol):
    def calculate_payroll_for_period(self, start: date, end: date) -> List[PayrollPreviewDTO]: ...
    def get_payroll_details(self, payroll_id: int) -> PayrollDetailsDTO: ...
    def confirm_payroll(self, payroll_id: int) -> None: ...
    def create_correction(self, confirmed_payroll_id: int) -> PayrollPreviewDTO: ...
```

## 18. Журнал архитектурных решений (Architectural Decision Log - ADR)

Этот раздел документирует ключевые архитектурные решения, принятые в ходе проектирования системы, их контекст и обоснование.

### 15.1. Выбор базы данных: SQLite

*   **Вопрос:** Почему в качестве базы данных выбрана SQLite, а не клиент-серверная СУБД (например, PostgreSQL)?
*   **Решение:** Использовать SQLite.
*   **Обоснование:**
    *   **Простота:** Система является десктопным приложением для одной организации. SQLite не требует установки и администрирования отдельного серверного процесса.
    *   **Портативность:** Вся база данных хранится в одном файле, что значительно упрощает развертывание, резервное копирование и восстановление.
    *   **Достаточная производительность:** Для предполагаемого количества пользователей (несколько сотен) и объема данных производительности SQLite более чем достаточно.
    *   **Соответствие ограничениям:** Это решение полностью соответствует ограничению "отсутствие необходимости в клиент-серверной архитектуре БД" (раздел 2).

### 15.2. Хранение сырых логов в `raw_log_data`

*   **Вопрос:** Зачем хранить в базе данных полные, необработанные строки из `.dat` файла, если они уже распарсены в `time_entries`?
*   **Решение:** Создать таблицу `raw_log_data` для хранения каждой импортированной строки.
*   **Обоснование:**
    *   **Аудит и доказательная база:** Сохранение неизменной исходной строки является доказательством того, какие именно данные поступили в систему. Это критически важно при разрешении споров о рабочем времени.
    *   **Возможность переобработки:** Если в будущем в логике парсинга будет обнаружена ошибка, можно будет заново обработать все исторические данные, не требуя наличия исходных `.dat` файлов, которые могут быть утеряны.
    *   **Недостаток (приемлемый):** Увеличение размера базы данных. Учитывая масштаб системы, этот недостаток считается незначительным по сравнению с получаемыми преимуществами.

### 15.3. Разделение сущностей `employees` и `positions`

*   **Вопрос:** Почему бы не хранить настройки рабочего дня и множители переработок непосредственно в таблице `employees`?
*   **Решение:** Вынести общие атрибуты группы сотрудников в отдельную таблицу `positions`.
*   **Обоснование:**
    *   **Гибкость и массовые обновления:** Если в компании изменятся правила для определенной должности (например, изменится множитель переработки для всех "Инженеров"), потребуется обновить только одну запись в таблице `positions`, а не каждую запись сотрудника этой должности.
    *   **Снижение ошибок:** Централизация этих правил уменьшает вероятность ошибки при ручном обновлении данных для множества сотрудников.
    *   **Логическая целостность:** Это лучше отражает реальную структуру организации, где должность определяет набор правил, общих для группы людей.

### 15.4. Игнорирование логов с неправдоподобной датой

*   **Вопрос:** Как система должна обрабатывать записи в `1_attlog.dat`, у которых дата датируется 2000-м годом или ранее?
*   **Решение:** Игнорировать такие записи при импорте.
*   **Обоснование:**
    *   **Сбой оборудования:** Такие даты, как правило, являются следствием сброса часов на оборудовании СКУД после отключения электроэнергии. Они не несут реальной информации о времени прихода/ухода.
    *   **Снижение шума:** Игнорирование этих записей на этапе импорта избавляет администратора от необходимости вручную удалять бессмысленные данные и снижает "шум" в системе.
    *   **Простота реализации:** Простая проверка года (`IF year <= 2000`) на этапе парсинга является эффективным и не ресурсозатратным решением.

### 15.5. Шифрование базы данных: SQLCipher

*   **Вопрос:** Как обеспечить надежную защиту конфиденциальных данных (зарплаты, личные данные) в файле базы данных на диске?
*   **Решение:** Использовать SQLCipher для шифрования файла `tessera.db`.
*   **Обоснование:**
    *   **Надежная защита данных at rest:** SQLCipher обеспечивает прозрачное шифрование всего файла базы данных с использованием стойких алгоритмов (AES-256). Это гарантирует, что даже при несанкционированном доступе к файлу БД, данные останутся недоступными без правильного ключа.
    *   **Прагматичность:** Интеграция SQLCipher минимально влияет на остальную часть приложения. Изменения в основном касаются инициализации соединения с БД, где пароль пользователя передается как ключ шифрования. Бизнес-логика и ORM (SQLAlchemy) продолжают работать без изменений.
    *   **Использование существующего механизма аутентификации:** Пароль, вводимый пользователем при входе в приложение, используется не только для аутентификации в приложении, но и как ключ для расшифровки базы данных. Это упрощает управление ключами и пользовательский опыт.
    *   **Изменение режима просмотра:** В связи с шифрованием, "Режим Просмотра" больше не может быть активирован без пароля. Вместо этого вводится отдельный, менее привилегированный пароль для доступа к БД в режиме "только чтение". Это повышает общую безопасность, требуя явной аутентификации для любого доступа к данным.
