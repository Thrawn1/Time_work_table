# Архитектура Системы Учета Рабочего Времени и Расчета Заработной Платы "Tessera"

Этот документ описывает высокоуровневую архитектуру и основные сценарии использования (use cases) системы "Tessera". Архитектура спроектирована так, чтобы быть понятной для человека и легко реализуемой с помощью ИИ-агентов.

## 1. Обзор Системы "Tessera"

Система "Tessera" предназначена для автоматизации процессов учета рабочего времени сотрудников и расчета их заработной платы на основе этих данных. Название "Tessera" (тессера — маленький кубик камня, из которых складывается мозаика) символизирует, как отдельные рабочие события и часы сотрудников складываются в общую картину их вклада и формируют основу для расчета заработной платы.

**Основные цели:**
- Точный учет отработанных часов - с точностью до секунды.
- Автоматический расчет заработной платы.
- Прозрачность данных для сотрудников и администрации.
- Минимизация ручного труда и ошибок.

## 2. Предположения и Ограничения

Этот раздел описывает ключевые предположения, сделанные в процессе проектирования архитектуры, а также ограничения, которые могут повлиять на разработку и эксплуатацию системы.

**Предположения:**
*   Система предназначена для использования в рамках одного маленького предприятия.
*   Количество сотрудников не превышает сотни.
*   Объем данных логов (файлы `.dat`) является умеренным и не требует распределенных систем хранения или обработки.
*   Основной источник данных о приходе/уходе — файлы `.dat` из СКУД.
*   Пользователи системы (администратор и работники) имеют базовые навыки работы с десктопными приложениями.
*   Расчет заработной платы производится на основе почасовой ставки и фиксированных правил, без учета сложных налоговых систем или индивидуальных договоренностей, выходящих за рамки описанных правил.

**Ограничения:**
*   Система будет реализована как **десктопное приложение** (на базе Python и QT), без веб-интерфейса.
*   В качестве базы данных используется **SQLite**, что подразумевает локальное хранение данных и отсутствие необходимости в клиент-серверной архитектуре БД.
*   Системы не предусматривает интеграцию с внешними бухгалтерскими системами или ERP.
*   Безопасность данных ориентирована на защиту от несанкционированного доступа на уровне приложения (пароль администратора), но не включает комплексные меры сетевой безопасности или защиты от продвинутых атак.
*   Система не предназначена для работы в режиме реального времени (например, мгновенное отображение приходов/уходов).

## 3. Компоненты Архитектуры

Система будет состоять из следующих модульных компонентов:

### 3.1. Модуль Импорта Данных (Data Ingestion Layer)


|| Я думаю что в модуле Импорта данных должен быть только импорт данных из `.dat` файла. В свою очередь нужен еще один модуль, который будет отвечать за ручной ввод, модуль для автоматической генерации по правилам и ввод для редактирования записей за месяц для конкретного работника.
Этот компонент отвечает за получение и первичную обработку данных о событиях прихода и ухода сотрудников.

- **Источник данных:** Файлы логов `.dat` из систем контроля доступа (СКУД)
- **Парсер данных:** Будет реализован парсер для формата файла `1_attlog.dat`. На основе анализа файла, каждая строка содержит следующие поля, разделенные пробелами или табуляцией:
    1.  **ID сотрудника:** Целое число, уникальный идентификатор сотрудника.
    2.  **Дата:** В формате `YYYY-MM-DD`.
    3.  **Время:** В формате `HH:MM:SS`.
    4.  **Дополнительное поле 1:** Целое число (в образце всегда `1`). Данное поле не нужно
    5.  **Дополнительное поле 2:** Целое число (в образце всегда `255`). Данное поле не нужно
    6.  **Дополнительное поле 3:** Целое число (в образце всегда `1`). Данное поле не нужно
    7.  **Дополнительное поле 4:** Целое число (в образце всегда `0`). Данное поле не нужно
    Модуль должен извлекать ID сотрудника, дату и время, игнорируя  остальные поля для возможного будущего использования. Модуль будет расширяемым для поддержки других форматов в будущем.
- **Валидация:** Проверка данных на полноту и корректность (например, наличие ID, корректность формата даты/времени).

## 4. Модель Данных (Схемы БД)

Для хранения данных будет использоваться SQLite со следующими таблицами:

**Таблица `employees` (Сотрудники)**
||Есть сотрудники,у которых считается по времени рабочая сессия, а есть сотрудники, у которых определяется хотя бы одна метка и им платят фиксированную сумму просто за выход вне зависимости сколько времени они были на производстве и какой день - будний или праздничный. Надо это учесть.
*   `id` (INTEGER, PRIMARY KEY): Уникальный ID сотрудника, соответствует ID из лог-файла.
*   `full_name` (TEXT, NOT NULL): Полное имя сотрудника.
*   `position_id` (INTEGER, NOT NULL, FOREIGN KEY to `positions.id`): Ссылка на должность сотрудника.
*   `hourly_rate` (REAL, NOT NULL): Базовая почасовая ставка сотрудника.
*   `is_active` (BOOLEAN, DEFAULT TRUE): Флаг, активен ли сотрудник.

**Таблица `positions` (Должности)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT)
*   `name` (TEXT, UNIQUE, NOT NULL): Название должности (например, "Инженер", "Бухгалтер").
*   `standard_workday_hours` (REAL, NOT NULL, DEFAULT 8): Норма часов в день для этой должности.
*   `weekday_overtime_multiplier` (REAL, NOT NULL, DEFAULT 1.5): Множитель для переработок в будни для этой должности.
*   `holiday_rate_multiplier` (REAL, NOT NULL, DEFAULT 1.5): Множитель для обычной работы в выходные/праздники для этой должности.
*   `holiday_overtime_rate_multiplier` (REAL, NOT NULL, DEFAULT 2.0): Множитель для переработок в выходные/праздники для этой должности.

**Таблица `raw_log_data` (Сырые данные логов)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID записи в БД.
*   `raw_line_content` (TEXT, NOT NULL): Полная, неизмененная строка из файла `1_attlog.dat`.
*   `import_batch_id` (INTEGER, NOT NULL): Идентификатор "партии" импорта.
*   `imported_at` (DATETIME, NOT NULL): Точное время, когда эта строка была добавлена в базу данных.

**Таблица `time_entries` (События входа/выхода)**
||Немного не то место, но я напишу как вижу логику определения начала и конца сессии.Мы читаем файл `1_attlog.dat`, разбираем запись - если для id сотрудника записей за этот день нет, то создаем запись сессии, где начало и конец - одна и та же метка. Дальше мы смотрим следующую запись. Когда за эту дату находится новая метка - она сравнивается с той, что уже есть и записывается в зависимости от сравнения - если больше - то out, если меньше то in. Таким образом после парсинга файла получаться сессии, в которых из имеющихся данных будет самая ранняя метка прихода и самая поздняя метка ухода. Детектировать нехватку данных о метках будет просто - Если рабочее время сессии равно 0(метка прихода и ухода совпадают) или меньше 2 часов то значит данных не хватает.
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID записи.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `timestamp` (DATETIME, NOT NULL): Точное время события (приход или уход).
*   `entry_type` (TEXT): Тип события ('in' или 'out'), определяется логикой.

**Таблица `work_sessions` (Рабочие сессии)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID сессии.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `start_time` (DATETIME, NOT NULL): Время начала сессии.
*   `end_time` (DATETIME, NULLABLE): Время окончания сессии.
*   `duration_hours` (REAL): Длительность сессии в часах.

*   `session_type` (TEXT, NOT NULL): Тип дня, к которому относится сессия. Возможные значения: `standard` (обычный рабочий день), `weekend` (выходной день), `holiday` (праздничный день).

**Таблица `payrolls` (Расчеты заработной платы)**

*   `weekday_overtime_hours` (REAL): Сумма часов переработки в будни.

*   `holiday_overtime_hours` (REAL): Сумма часов переработки в выходные/праздники.

*   `net_pay` (REAL): Заработная плата после вычетов.
*   `calculation_date` (DATETIME, NOT NULL): Дата выполнения расчета.
*   `status` (TEXT, NOT NULL, DEFAULT 'draft'): Статус расчета ('draft', 'confirmed', 'corrected', 'archived').

#### 4.1.3. Таблица Журнала Аудита (`audit_log`)

Как упоминалось в разделе "9.3. Аудит и Логирование", для отслеживания критически важных действий администраторов будет использоваться следующая таблица:
|| Логирование надо делать без user_id, так как фактически у нас есть два режима, один из которых работает с паролем. Поэтому логировать нужно по режимам - в случае Просмотра - дата и время а так же период запроса. Для режима Администратора - все то что описано ниже в таблице. но без user_id
```sql
CREATE TABLE audit_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER, -- ID администратора, выполнившего действие
    action TEXT NOT NULL, -- Описание действия (e.g., 'EMPLOYEE_ADDED', 'PAYROLL_CALCULATED')
    table_name TEXT, -- Имя таблицы, к которой относится действие
    record_id INTEGER, -- ID записи в таблице, если применимо
    old_values TEXT, -- JSON строка со старыми значениями (для UPDATE)
    new_values TEXT, -- JSON строка с новыми значениями (для INSERT/UPDATE)
    timestamp DATETIME DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

#### 4.1.4. Триггеры (Triggers)

Для автоматической записи изменений в `audit_log` могут быть использованы триггеры на таблицах `employees`, `positions`, `time_entries`, `work_sessions`, `payrolls` для операций `INSERT`, `UPDATE`, `DELETE`.

*   **Пример триггера для `employees` (INSERT):**
    ```sql
    CREATE TRIGGER trg_employees_insert
    AFTER INSERT ON employees
    FOR EACH ROW
    BEGIN
        INSERT INTO audit_log (user_id, action, table_name, record_id, new_values)
        VALUES (CURRENT_USER_ID(), 'EMPLOYEE_ADDED', 'employees', NEW.id, JSON_OBJECT(
            'id', NEW.id,
            'full_name', NEW.full_name,
            'position_id', NEW.position_id,
            'hourly_rate', NEW.hourly_rate,
            'is_active', NEW.is_active
        ));
    END;
    ```
|| плейсхолдер видимо не нужен, если у нас не авторизация пользователей с правами Администратора,а два режима.
    (Примечание: `CURRENT_USER_ID()` - это плейсхолдер для функции, которая будет возвращать ID текущего авторизованного пользователя).

## 5. Бизнес-Правила и Обработка Граничных Случаев

Этот раздел описывает ключевые бизнес-правила, алгоритмы расчета и подходы к обработке нестандартных ситуаций в системе.

### 5.1. Обработка Граничных Случаев

Этот раздел определяет, как система должна реагировать на нестандартные ситуации.

1.  **Одна метка за день:**
    *   **Проблема:** У сотрудника есть одна метка за день (невозможно точно определить приход это или уход)
    *   **Решение:** Система должна пометить такой день как "требующий внимания" и предложить администратору вручную ввести недостающую метку и выбрать какой тип метки(приход или уход) он вводит  или сгенерировать данные согласно выбранной стратегии для конкретного пользователя.

2.  **Отсутствие меток за рабочий день:**
    *   **Проблема:** Сотрудник должен был работать, но отметок нет.
    *   **Решение:** Система помечает такой день как "требующий внимания" и предлагает администратору или создать запись в таблице `absences`, выбрав тип отсутствия ("Прогул", "Больничный", "Отпуск") и указав период или ввести данные за обычный рабочий день. Это формализует причину отсутствия и позволяет корректно учесть ее при расчете ЗП или посчитать корректно рабочие дни.



||Проблемы с множественными короткими входами и выходами нет - сотрудники фиксируют начало и конец рабочего дня, на перерывы они выходят не отмечаясь.
3.  **Множественные короткие выходы/входы:**
    *   **Проблема:** Сотрудник вышел на 5 минут и вернулся.
    *   **Решение:** Ввести в `app_config` настройку `min_break_duration` (например, 15 минут). Если перерыв между выходом и входом меньше этого значения, он не прерывает рабочую сессию и считается рабочим временем.



||Так как датчик отмечающий сотрудников один -и на вход и на выход, то решение этой задачи очень сложное. Данные кейс нужно опустить, предположив, что рабочий день находится в рамках одних суток. В случае если есть переход в другие сутки- Администратор в ручную будет разбирать такой случай.
4.  **Работа в ночное время / Переход через полночь:**
    *   **Проблема:** Смена начинается в один день, а заканчивается в другой.
    *   **Решение:** Рабочая сессия (`work_sessions`) должна быть привязана к дате её начала. Расчет отработанных часов должен корректно обрабатывать переход через 00:00.

### 5.2. Гибкая Тарификация и Расчет Часов


||Необходимо учесть, описанное выше. Есть сотрудники, у которых фиксируется факт выхода на работу и оплата фиксированная вне зависимости от времени(даже если есть только одна метка) и типа дня(будний день или выходные)
||Кроме зарплаты есть еще премия руководителей, которая вводится в ручную и стоимость за молоко(из за вредности)
*   **Задача:** Система должна гибко рассчитывать 4 типа отработанного времени (будни норма, будни переработка, выходные норма, выходные переработка) на основе индивидуальных настроек сотрудника.
*   **Решение:**
    1.  При расчете ЗП для каждого сотрудника система определяет его должность через `position_id` и использует настройки из связанной таблицы `positions`: `standard_workday_hours`, `weekday_overtime_multiplier`, `holiday_rate_multiplier`, `holiday_overtime_rate_multiplier`.
    2.  Для каждого дня в расчетном периоде система анализирует `work_sessions`:
        *   Определяется тип дня (`standard`, `weekend`, `holiday`) с помощью `session_type`.
        *   Суммируются все часы за этот день.
        *   Если сумма часов превышает `standard_workday_hours` должности, излишек классифицируется как "часы переработки" (`overtime_hours`), остальное — как "стандартные часы" (`standard_hours`).
    3.  В зависимости от типа дня, эти часы добавляются к соответствующим полям в таблице `payrolls` (`weekday_standard_hours`, `holiday_overtime_hours` и т.д.).
    4.  Итоговая сумма `total_gross_pay` рассчитывается путем сложения оплаты по всем четырем категориям часов, каждая со своим множителем, умноженным на `hourly_rate` сотрудника.

### 5.3. Управление Выходными и Праздниками

*   **Задача:** Определять, является ли день рабочим, выходным или праздничным.
*   **Решение:**
    1.  **Выходные:** Дни, у которых `datetime.weekday()` возвращает 5 (суббота) или 6 (воскресенье), всегда считаются выходными (`weekend`).
    2.  **Праздники:** При запуске приложение читает файл `holidays.toml` (или аналогичный), в котором перечислены все официальные праздники и дни переносов.

        **Пример `holidays.toml`:**
        ```toml
        # Список официальных праздничных дней.
        # Система будет считать эти дни нерабочими и применять для них
        # множители 'holiday_rate_multiplier' и 'holiday_overtime_rate_multiplier'.

        [holidays.2025]
        dates = [
          "2025-01-01",  # Новый год
          "2025-01-07",  # Рождество Христово
          "2025-02-23",  # День защитника Отечества
          "2025-03-08",  # Международный женский день
          "2025-05-01",  # Праздник Весны и Труда
          "2025-05-09",  # День Победы
          "2025-06-12",  # День России
          "2025-11-04",  # День народного единства
        ]

        # Пример переноса выходного дня.
        # В данном примере, если 4 января 2025 является выходным (суббота),
        # то он становится рабочим днем, а 2 мая 2025 (пятница) становится выходным.
        [transferred_days.2025]
        "2025-01-04" = "2025-05-02"
        ```

    3.  **Интеграция (будущее):** В будущем "Модуль Импорта Данных" может быть расширен функцией парсинга производственного календаря с внешнего ресурса (например, Консультант Плюс), чтобы автоматически обновлять `holidays.toml`.

### 5.4. Подтверждение Расчета ("Заморозка")

*   **Задача:** Дать администратору возможность проверить итоговые цифры перед окончательным сохранением расчета.
*   **Решение:**
    1.  Администратор выбирает сотрудника и период, запускает расчет.
    2.  Система выполняет все вычисления и создает в таблице `payrolls` запись со статусом `draft`. Эта запись является "черновиком".
    3.  На экране отображается **окно предварительного просмотра** на основе данных из `draft`-расчета: "Иванов И.И., период 01.11-30.11. Итого к начислению: X руб. ...".
    4.  **При нажатии кнопки "Подтвердить"** система меняет статус `draft`-записи на `confirmed`. С этого момента расчет считается официальным.
    5.  Если администратор отменяет операцию или закрывает окно, `draft`-запись может быть удалена или оставлена для последующего просмотра.

### 5.5. Алгоритмы

#### 5.5.1. Алгоритм агрегации событий в рабочие сессии (time_entries -> work_sessions)
||Доработать алгоритм согласно правилу описанному выше - ищем самую раннюю и самую позднюю метку, они являются границей сессии. У меток нет признака входа и выхода! Не нужна обработка перерывов и обработка времени преходящего за полночь
**Вход:** Список `time_entries` для одного сотрудника за определенный период, `min_break_duration` (из `app_config`).
**Выход:** Список `work_sessions`.

**Шаги:**
1.  **Сортировка:** Отсортировать все `time_entries` для данного сотрудника по `timestamp` по возрастанию.
2.  **Инициализация:** Создать пустой список `work_sessions`.
3.  **Итерация по событиям:**
    *   Инициализировать `current_session_start = None`.
    *   Для каждого `entry` в отсортированном списке:
        *   Если `entry.entry_type == 'in'`:
            *   Если `current_session_start` уже установлен (т.е. был предыдущий 'in' без 'out'), это означает пропущенную метку 'out'. Завершить предыдущую сессию как `incomplete` (или сгенерировать 'out' по правилам, например, через `standard_workday_hours` от `current_session_start`). Добавить ее в `work_sessions`.
            *   Установить `current_session_start = entry.timestamp`.
        *   Если `entry.entry_type == 'out'`:
            *   Если `current_session_start` не установлен (т.е. был 'out' без предыдущего 'in'), это означает пропущенную метку 'in'. Проигнорировать или пометить как ошибку.
            *   Если `current_session_start` установлен:
                *   Рассчитать `session_end = entry.timestamp`.
                *   Рассчитать `duration = session_end - current_session_start`.
                *   **Обработка коротких перерывов:**
                    *   Если это не первая сессия за день и предыдущая `work_session.end_time` существует:
                        *   Рассчитать `break_duration = current_session_start - previous_work_session.end_time`.
                        *   Если `break_duration < min_break_duration`:
                            *   Объединить текущую сессию с предыдущей: обновить `previous_work_session.end_time = session_end` и `previous_work_session.duration_hours += duration`.
                            *   Сбросить `current_session_start = None`.
                            *   Продолжить к следующему `entry`.
                *   **Обработка перехода через полночь:**
                    *   Если `session_end.date() > current_session_start.date()`:
                        *   Разбить сессию на две:
                            *   Первая сессия: `start = current_session_start`, `end = current_session_start.end_of_day()`. Добавить в `work_sessions`.
                            *   Вторая сессия: `start = session_end.start_of_day()`, `end = session_end`. Добавить в `work_sessions`.
                            *   (Примечание: более сложная логика может потребоваться для точного распределения часов по дням, если смена длится несколько дней).
                    *   Иначе (сессия в пределах одного дня):
                        *   Создать `work_session` с `start_time = current_session_start`, `end_time = session_end`, `duration_hours = duration`. Добавить в `work_sessions`.
                *   Сбросить `current_session_start = None`.
4.  **Завершение незакрытых сессий:** После итерации по всем `entry`:
    *   Если `current_session_start` все еще установлен, это означает незакрытую сессию. Создать `work_session` с `start_time = current_session_start`, `end_time = None`, `status = 'incomplete'`. Добавить в `work_sessions`.
5.  **Определение типа дня:** Для каждой `work_session` определить `session_type` (`standard`, `weekend`, `holiday`) на основе даты сессии и списка праздников.
6.  **Возврат:** Вернуть список `work_sessions`.

#### 5.5.2. Алгоритм расчета заработной платы (work_sessions -> payrolls)

||Доработать алгоритм с учетом сотрудников, которые получают ЗП по факту выхода, а не по времени. Они описаны были выше.

**Вход:** `employee_id`, `period_start`, `period_end`, `hourly_rate` сотрудника, настройки должности и доступ к таблицам `work_sessions` и `absences`.
**Выход:** Объект `payroll` для сотрудника за период.

**Шаги:**
1.  **Инициализация:**
    *   `total_weekday_standard_hours = 0`
    *   `total_weekday_overtime_hours = 0`
    *   `total_holiday_standard_hours = 0`
    *   `total_holiday_overtime_hours = 0`
    *   `total_paid_absence_days = 0`
    *   `total_paid_absence_amount = 0`
    *   `total_gross_pay = 0`
2.  **Итерация по дням в расчетном периоде:**
    *   Для каждого дня `current_date` от `period_start` до `period_end`:
        *   **Проверка на отсутствие:** В первую очередь проверить, попадает ли `current_date` в какой-либо период из таблицы `absences` для данного сотрудника.
            *   Если да (найдена запись об отсутствии `absence_record`):
                *   Получить `absence_type` из `absence_types` по `absence_record.absence_type_id`.
                *   Если `absence_type.is_paid == TRUE`:
                    *   Рассчитать оплату за день. Например: `daily_payment = standard_workday_hours * hourly_rate * absence_type.payment_multiplier`.
                    *   `total_paid_absence_amount += daily_payment`.
                    *   `total_paid_absence_days += 1`.
                *   Перейти к следующему дню в цикле (пропустить расчет отработанных часов для этого дня).
        *   **Расчет отработанных часов (если отсутствия не было):**
        *   Получить все `work_sessions` для `employee_id` и `current_date`.
        *   Если сессий нет, перейти к следующему дню.
        *   Суммировать `duration_hours` всех сессий за `current_date` в `daily_total_hours`.
        *   Определить `day_type` для `current_date` (`standard`, `weekend`, `holiday`) на основе `datetime.weekday()` и списка праздников.
        *   **Распределение часов:**
            *   `standard_hours_for_day = min(daily_total_hours, standard_workday_hours)`
            *   `overtime_hours_for_day = daily_total_hours - standard_hours_for_day`
        *   **Накопление по категориям:**
            *   Если `day_type == 'standard'` (будний день, не праздник):
                *   `total_weekday_standard_hours += standard_hours_for_day`
                *   `total_weekday_overtime_hours += overtime_hours_for_day`
            *   Если `day_type == 'weekend'` или `day_type == 'holiday'` (выходной или праздничный день):
                *   `total_holiday_standard_hours += standard_hours_for_day`
                *   `total_holiday_overtime_hours += overtime_hours_for_day`
3.  **Расчет общей заработной платы:**
    *   `pay_weekday_standard = total_weekday_standard_hours * hourly_rate`
    *   `pay_weekday_overtime = total_weekday_overtime_hours * hourly_rate * weekday_overtime_multiplier`
    *   `pay_holiday_standard = total_holiday_standard_hours * hourly_rate * holiday_rate_multiplier`
    *   `pay_holiday_overtime = total_holiday_overtime_hours * hourly_rate * holiday_overtime_rate_multiplier`
    *   `total_gross_pay = pay_weekday_standard + pay_weekday_overtime + pay_holiday_standard + pay_holiday_overtime + total_paid_absence_amount`
4.  **Применение вычетов/бонусов (placeholder):**
    *   `net_pay = total_gross_pay - (вычеты) + (бонусы)` (Детализировать в будущем)
5.  **Создание объекта `payroll`:**
    *   `payroll = {`
    *   `employee_id: employee_id,`
    *   `period_start: period_start,`
    *   `period_end: period_end,`
    *   `weekday_standard_hours: total_weekday_standard_hours,`
    *   `weekday_overtime_hours: total_weekday_overtime_hours,`
    *   `holiday_standard_hours: total_holiday_standard_hours,`
    *   `holiday_overtime_hours: total_holiday_overtime_hours,`
    *   `paid_absence_days: total_paid_absence_days,`
    *   `paid_absence_amount: total_paid_absence_amount,`
    *   `total_gross_pay: total_gross_pay,`
    *   `net_pay: net_pay,`
    *   `calculation_date: current_timestamp`
    *   `}`
6.  **Возврат:** Объект `payroll`.

### 5.6. Пример расчета заработной платы

||Добавить еще примеры с другим типом расчетов для сотрудников с оплатой по факту выхода. А так же добавить примеры с больничным, административным и отпуском.
Чтобы продемонстрировать логику алгоритма, рассмотрим пример расчета для вымышленного сотрудника за один месяц.

**Входные данные:**

1.  **Сотрудник:**
    *   `full_name`: "Иванов Иван Иванович"
    *   `hourly_rate`: 500.00 руб/час

2.  **Должность:** "Инженер"
    *   `standard_workday_hours`: 8.0 часов
    *   `weekday_overtime_multiplier`: 1.5
    *   `holiday_rate_multiplier`: 1.5
    *   `holiday_overtime_rate_multiplier`: 2.0

3.  **Расчетный период:** 1 ноября 2025 г. - 30 ноября 2025 г.

**Агрегированные данные о работе за месяц (выходные данные из `work_sessions`):**

*   **Отработано в будние дни:**
    *   `weekday_standard_hours`: 160 часов (20 дней * 8 часов)
    *   `weekday_overtime_hours`: 10 часов
*   **Отработано в выходные/праздничные дни:**
    *   `holiday_standard_hours`: 16 часов (2 смены по 8 часов)
    *   `holiday_overtime_hours`: 5 часов

**Пошаговый расчет `total_gross_pay`:**

1.  **Оплата за стандартные часы в будни:**
    *   `160 часов * 500.00 руб/час = 80,000.00 руб.`

2.  **Оплата за переработку в будни:**
    *   `10 часов * 500.00 руб/час * 1.5 (weekday_overtime_multiplier) = 7,500.00 руб.`

3.  **Оплата за стандартные часы в выходные/праздники:**
    *   `16 часов * 500.00 руб/час * 1.5 (holiday_rate_multiplier) = 12,000.00 руб.`

4.  **Оплата за переработку в выходные/праздники:**
    *   `5 часов * 500.00 руб/час * 2.0 (holiday_overtime_rate_multiplier) = 5,000.00 руб.`

**Итоговая сумма к начислению (`total_gross_pay`):**

*   `80,000.00 + 7,500.00 + 12,000.00 + 5,000.00 = 104,500.00 руб.`

Этот пример будет использоваться как эталонный тест для проверки корректности реализации модуля расчета заработной платы.

### 5.7. Жизненный цикл расчета и корректировки

Для обеспечения целостности финансовых данных и наличия полного аудиторского следа, расчеты ЗП (`payrolls`) проходят через определенный жизненный цикл, управляемый статусами.

*   **Статусы:**
    *   `draft`: Черновик расчета. Создается при каждом новом вычислении. Может быть удален или изменен путем нового расчета. Не является официальным документом.
    *   `confirmed`: Подтвержденный расчет. Является официальным итогом за период. Не может быть изменен или удален напрямую.
    *   `archived`: Архивная версия расчета. Этот статус присваивается `confirmed`-расчету, который был исправлен. Хранится для истории.
    *   `corrected`: Исправленный расчет. Новый `confirmed`-расчет, созданный для замены `archived`-расчета.

*   **Процесс корректировки подтвержденного расчета:**

|| Администратор может исправить `draft` и `confirmed`. Драфт правится на этапе предпросмотра.
    1.  Администратор находит в системе `confirmed`-расчет, который нужно исправить.
    2.  Он инициирует действие "Создать корректировку".
    3.  Система позволяет вносить изменения в исходные данные за этот период (`time_entries`, `absences`).
    4.  После внесения правок администратор заново запускает расчет ЗП.
    5.  Система создает **новую** запись в `payrolls` с результатами перерасчета и статусом `corrected`. В поле `corrected_payroll_id` этой записи указывается `id` исходного, теперь уже неверного, расчета.
    6.  Исходный `confirmed`-расчет атомарно меняет свой статус на `archived`.
    7.  Новый `corrected`-расчет после подтверждения администратором получает статус `confirmed`.

Этот механизм гарантирует, что история всех начислений сохраняется, и всегда можно отследить, на каком основании была сделана корректировка.

### 6.1. Режим Администратор: Добавление нового сотрудника

*   **Актер:** Администратор
*   **Предусловия:** Введен пароль Администратора

    *   **6.6b. Некорректные данные:** Если внесенные вручную данные некорректны (например, время ухода раньше прихода, пересекающиеся сессии), система отображает ошибку и требует исправления.
*   **Пост-условия:** `time_entries` и/или `work_sessions` обновлены в соответствии с действиями администратора. Расчет заработной платы для затронутого периода пересчитан.
*   **Правила валидации:**
    *   `timestamp` для `time_entry` должен быть корректной датой/временем.
    *   `start_time` < `end_time` для `work_session`.
    *   `work_sessions` не должны пересекаться для одного сотрудника.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Ошибки при записи в БД.
    *   **Ошибка расчета:** Непредвиденные ошибки в логике пересчета.

### 6.7. Режим просмотра: Просмотр рабочего времени сотрудников

*   **Актер:** Любой сотрудник
*   **Предусловия:** Осуществлен вход с пустым паролем. В системе существуют данные о `work_sessions` для сотрудников.
*   **Основной поток:**
    1.  Сотрудник открывает раздел "Просмотр рабочего времени" или "Отчеты по рабочему времени".
    2.  Сотрудник выбирает сотрудника (или всех сотрудников) и указывает период для просмотра.
    3.  Сотрудник нажимает кнопку "Показать отчет".
    4.  Система извлекает данные о `work_sessions` для выбранных сотрудников и периода.
    5.  Система отображает агрегированный отчет по рабочему времени, который может включать:
        *   Общее количество отработанных часов за период.
        *   Разбивку по дням/неделям.
        *   Информацию о статусе сессий (завершенные, незавершенные, сгенерированные).
        *   (Важно: без информации о заработной плате в этом режиме).
*   **Альтернативные потоки:**
    *   **6.7a. Нет данных:** Если для выбранного сотрудника/периода нет данных о `work_sessions`, система отображает соответствующее сообщение.
    *   **6.7b. Фильтрация/Сортировка:** Сотрудник может применить фильтры (например, по типу сессии) или сортировку к отображаемым данным.
*   **Пост-условия:** Сотрудник просмотрел отчет по рабочему времени. Состояние системы не изменилось.
*   **Правила валидации:**
    *   Выбранный период должен быть корректным.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Ошибки при извлечении данных из БД.

## 9. Безопасность

Этот раздел описывает меры безопасности, применяемые в системе для защиты данных и контроля доступа.

### 9.1. Аутентификация и Авторизация
|| Я вижу что есть один безликий Администратор, который активируется вводом пароля, который задается при инициализации программы. И есть безликий Сотрудник, который активируется путем входа с пустым паролем.
*   **Аутентификация:**
    *   **Хеширование паролей:** Пароли пользователей (администраторов) не хранятся в открытом виде. Используется криптографически стойкий алгоритм хеширования (например, `bcrypt` или `argon2`) с солью для защиты от атак по словарю и радужных таблиц.
    *   **Хранение:** Хеши паролей хранятся в базе данных.
*   **Авторизация (Управление доступом на основе ролей - RBAC):**
    *   **Роли:** Система поддерживает как минимум две роли: "Администратор" и "Просмотрщик".
    *   **Разграничение доступа:**
        *   **Администратор:** Полный доступ ко всем функциям системы, включая управление сотрудниками, импорт данных, расчет ЗП, редактирование данных.
        *   **Просмотрщик:** Доступ только к просмотру отчетов по рабочему времени (без данных о ЗП) и, возможно, к просмотру списка сотрудников без возможности редактирования.
    *   **Реализация:** Проверки прав доступа выполняются на уровне бизнес-логики перед выполнением операций.

|| Информацию про ставки и зарплаты уже рассчитанные хорошо было бы шифровать, но без уровня ОС.
*   **Защита от SQL-инъекций:** Все запросы к базе данных формируются с использованием параметризованных запросов (prepared statements) или ORM, что предотвращает возможность SQL-инъекций.

## 10. Обработка Ошибок и Логирование

Этот раздел описывает общую стратегию системы по обработке ошибок и ведению логов для обеспечения стабильности, отладки и мониторинга.

### 10.1. Стратегия Обработки Ошибок

*   **Типы ошибок:**
    *   **Ошибки валидации:** Возникают при некорректном вводе данных пользователем или при импорте. Обрабатываются путем предоставления обратной связи пользователю (сообщения об ошибках в UI).
    *   **Ошибки бизнес-логики:** Возникают при нарушении бизнес-правил (например, попытка сохранить пересекающиеся рабочие сессии). Обрабатываются путем предотвращения операции и информирования пользователя.
    *   **Ошибки данных/БД:** Возникают при проблемах с доступом к БД, повреждении данных, нарушении ограничений БД. Обрабатываются путем перехвата исключений, логирования и информирования пользователя о необходимости обратиться в поддержку.
    *   **Системные/Внутренние ошибки:** Непредвиденные ошибки в коде. Перехватываются, логируются с полным стеком вызовов, пользователю отображается общее сообщение об ошибке.
*   **Механизмы обработки:**
    *   **Исключения (Exceptions):** Использование стандартного механизма исключений Python для сигнализации об ошибках.
    *   **Централизованный обработчик:** Единая точка входа для обработки неперехваченных исключений, обеспечивающая корректное логирование и отображение сообщений пользователю.
    *   **Обратная связь пользователю:** Четкие и понятные сообщения об ошибках в пользовательском интерфейсе.
*   **Стратегии восстановления:**
    *   **Откат (Rollback):** Для операций, изменяющих состояние БД (например, импорт данных, сохранение расчета ЗП), в случае ошибки выполняется откат транзакции для сохранения целостности данных.
    *   **Повторная попытка (Retry):** Для временных ошибок (например, блокировка БД) может быть реализована ограниченная логика повторных попыток.

### 10.2. Стратегия Логирования

*   **Уровни логирования:** Используются стандартные уровни логирования (DEBUG, INFO, WARNING, ERROR, CRITICAL) для категоризации сообщений.
*   **Что логировать:**
    *   **Действия пользователя:** (См. 9.3 Аудит и Логирование).
    *   **Начало/завершение ключевых операций:** Импорт файлов, расчет ЗП.
    *   **Предупреждения:** Некорректные данные в файлах импорта, которые были пропущены.
    *   **Ошибки:** Все перехваченные исключения, ошибки БД, ошибки валидации с детальной информацией (сообщение, стек вызовов, контекст).
    *   **Производительность:** Время выполнения критических операций (опционально).
*   **Формат логов:** Логи форматируются для удобства чтения и парсинга (например, JSON или структурированный текст).
*   **Место хранения:** Логи хранятся в файле рядом с исполняемым файлом приложения
*   **Ротация логов:** Реализована ротация логов по размеру или по времени для предотвращения переполнения диска. Величина log-файла не более 700 МБ
*   **Конфигурация:** Уровень логирования и параметры ротации настраиваются через конфигурационный файл.

    *   **Цель:** Проверка взаимодействия между различными компонентами системы (например, Core Service с Repository и БД, Ingestion с Core).
    *   **Примеры:** Тестирование полного цикла импорта данных из файла в БД, тестирование расчета ЗП с использованием реальных данных из БД.
*   **Функциональное/Системное тестирование (Functional/System Tests):**
    *   **Цель:** Проверка соответствия системы функциональным требованиям, описанным в Use Cases.
    *   **Примеры:** Тестирование полного сценария добавления сотрудника через UI, запуск расчета ЗП и генерация отчета.
*   **Приемочное тестирование (Acceptance Tests):**
    *   **Цель:** Проверка системы конечными пользователями или представителями бизнеса на соответствие их ожиданиям.
*   **Тестирование пользовательского интерфейса (UI/E2E Tests):**
    *   **Цель:** Автоматизированная проверка взаимодействия пользователя с UI и корректности отображения данных.
    *   **Инструменты:** Могут использоваться фреймворки для автоматизации UI (например, `PyQt` имеет свои инструменты для тестирования, или сторонние библиотеки).

### 12.2. Инструменты и Подходы

*   **Фреймворк для тестирования:** `pytest` (для Python) как основной фреймворк для модульных и интеграционных тестов.
*   **Тестовые данные (Test Data Fixtures):** Использование фикстур для создания контролируемых и воспроизводимых тестовых данных.
*   **Мокирование (Mocking):** Использование моков и стабов для изоляции тестируемых компонентов и имитации внешних зависимостей (например, БД, файловой системы).
*   **Непрерывная интеграция (CI):** Интеграция тестов в процесс CI для автоматического запуска при каждом изменении кода.

### 12.3. Покрытие Кода (Code Coverage)

*   **Цель:** Поддержание высокого уровня покрытия кода тестами, особенно для критически важных частей системы.
*   **Инструменты:** `coverage.py` для измерения покрытия.
*   **Требование:** Минимум 80% покрытия для модулей `core/services`, `core/validators`, `ingestion/parsers`.

## 13. Эксплуатация и Обслуживание

Этот раздел описывает аспекты, связанные с долгосрочной эксплуатацией и обслуживанием системы.

### 13.1. Резервное копирование и восстановление

Учитывая, что вся база данных SQLite хранится в одном файле, обеспечение ее сохранности является критически важной задачей.

**Стратегия резервного копирования:**


||Достаточно будет хранить бэкап `.zip` рядом с исполняемым файлом.

*   **Автоматическое резервное копирование:** Приложение будет иметь встроенную функцию для создания автоматических резервных копий. Копирование может выполняться при закрытии приложения или по расписанию (например, раз в день).
*   **Ручное резервное копирование:** Администратор должен иметь возможность в любой момент создать резервную копию через пользовательский интерфейс.
*   **Местоположение бэкапов:** Путь для сохранения резервных копий должен настраиваться в `app_config`. Рекомендуется использовать отдельный физический диск или сетевую папку для защиты от сбоя основного диска.
*   **Именование и формат:** Резервные копии будут сохраняться в формате `.zip` для экономии места и будут включать в имя файла дату и время создания, например: `tessera_backup_2025-11-15_21-30-00.db.zip`.

**Стратегия восстановления:**

*   **Процесс:** Администратор сможет выбрать файл резервной копии из интерфейса приложения для восстановления.
*   **Предупреждение:** Перед восстановлением система должна отобразить четкое и недвусмысленное предупреждение о том, что **все текущие данные будут безвозвратно заменены данными из резервной копии**.
*   **Реализация:** Процесс восстановления включает в себя закрытие текущего соединения с БД, замену файла базы данных файлом из архива и повторное подключение к восстановленной БД.

## 14. Риски и их митигация

Этот раздел описывает потенциальные технические и операционные риски, а также стратегии их предотвращения или смягчения последствий.

### 14.1. Большой объем файла логов

*   **Риск:** Обработка файла `1_attlog.dat` очень большого размера (например, несколько гигабайт, содержащих логи за много лет) может привести к чрезмерному потреблению оперативной памяти и сбою приложения (OutOfMemory).
*   **Митигация:** Модуль импорта данных (`Ingestion Layer`) должен быть реализован с использованием потоковой обработки (stream processing). Парсер должен читать файл строка за строкой, а не загружать его целиком в память.

### 14.2. Повреждение файла базы данных

*   **Риск:** Будучи единым файлом, база данных SQLite подвержена риску повреждения из-за сбоев системы, некорректного завершения работы приложения или проблем с диском. Это может привести к полной потере данных.
*   **Митигация:**
    1.  **Резервное копирование:** Основной мерой является строгая стратегия резервного копирования, описанная в разделе 13.1.
    2.  **WAL-режим:** Для повышения отказоустойчивости рекомендуется использовать для SQLite режим [Write-Ahead Logging (WAL)](https://www.sqlite.org/wal.html). Он снижает вероятность повреждения БД при сбоях.

### 14.3. Сложные или непредусмотренные паттерны работы

*   **Риск:** Алгоритм агрегации `work_sessions` может не покрыть все возможные реальные сценарии работы сотрудников (например, несколько смен с большими перерывами в один день, которые не должны объединяться).
*   **Митигация:**
    1.  **Ручное редактирование:** Система предоставляет администратору полный контроль над `time_entries` и `work_sessions` (Use Case 6.6), что позволяет вручную исправить любую ситуацию, некорректно обработанную алгоритмом.
    2.  **Аудит:** Все ручные изменения логируются в `audit_log`, обеспечивая прозрачность.

### 14.4. Ошибки при ручном вводе данных

*   **Риск:** Администратор может допустить ошибку при ручном вводе недостающих меток, корректировке сессий или создании записей об отсутствии, что приведет к неверному расчету ЗП.
*   **Митигация:**
    1.  **Валидация на уровне UI:** Все формы ввода должны иметь строгую валидацию (например, проверка, что время окончания позже времени начала; проверка корректности форматов).
    2.  **Жизненный цикл расчета:** Процесс `draft` -> `confirmed` (раздел 5.7) дает администратору возможность проверить все цифры перед окончательным утверждением расчета.

## 15. Журнал архитектурных решений (Architectural Decision Log - ADR)

Этот раздел документирует ключевые архитектурные решения, принятые в ходе проектирования системы, их контекст и обоснование.

### 15.1. Выбор базы данных: SQLite

*   **Вопрос:** Почему в качестве базы данных выбрана SQLite, а не клиент-серверная СУБД (например, PostgreSQL)?
*   **Решение:** Использовать SQLite.
*   **Обоснование:**
    *   **Простота:** Система является десктопным приложением для одной организации. SQLite не требует установки и администрирования отдельного серверного процесса.
    *   **Портативность:** Вся база данных хранится в одном файле, что значительно упрощает развертывание, резервное копирование и восстановление.
    *   **Достаточная производительность:** Для предполагаемого количества пользователей (несколько сотен) и объема данных производительности SQLite более чем достаточно.
    *   **Соответствие ограничениям:** Это решение полностью соответствует ограничению "отсутствие необходимости в клиент-серверной архитектуре БД" (раздел 2).

### 15.2. Хранение сырых логов в `raw_log_data`

*   **Вопрос:** Зачем хранить в базе данных полные, необработанные строки из `.dat` файла, если они уже распарсены в `time_entries`?
*   **Решение:** Создать таблицу `raw_log_data` для хранения каждой импортированной строки.
*   **Обоснование:**
    *   **Аудит и доказательная база:** Сохранение неизменной исходной строки является доказательством того, какие именно данные поступили в систему. Это критически важно при разрешении споров о рабочем времени.
    *   **Возможность переобработки:** Если в будущем в логике парсинга будет обнаружена ошибка, можно будет заново обработать все исторические данные, не требуя наличия исходных `.dat` файлов, которые могут быть утеряны.
    *   **Недостаток (приемлемый):** Увеличение размера базы данных. Учитывая масштаб системы, этот недостаток считается незначительным по сравнению с получаемыми преимуществами.

### 15.3. Разделение сущностей `employees` и `positions`

*   **Вопрос:** Почему бы не хранить настройки рабочего дня и множители переработок непосредственно в таблице `employees`?
*   **Решение:** Вынести общие атрибуты группы сотрудников в отдельную таблицу `positions`.
*   **Обоснование:**
    *   **Гибкость и массовые обновления:** Если в компании изменятся правила для определенной должности (например, изменится множитель переработки для всех "Инженеров"), потребуется обновить только одну запись в таблице `positions`, а не каждую запись сотрудника этой должности.
    *   **Снижение ошибок:** Централизация этих правил уменьшает вероятность ошибки при ручном обновлении данных для множества сотрудников.
    *   **Логическая целостность:** Это лучше отражает реальную структуру организации, где должность определяет набор правил, общих для группы людей.


    || В файле `1_attlog.dat` могут быть ошибки, при которых дата отметки будет датироваться 2000 годом или ранее. Это связано с тем, что при отключении электричества сбрасывается дата и время. Подобные метки нужно игнорировать.
