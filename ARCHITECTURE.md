# Архитектура Системы Учета Рабочего Времени и Расчета Заработной Платы "Tessera"

Этот документ описывает высокоуровневую архитектуру и основные сценарии использования (use cases) системы "Tessera". Архитектура спроектирована так, чтобы быть понятной для человека и легко реализуемой с помощью ИИ-агентов.

## 1. Обзор Системы "Tessera"

Система "Tessera" предназначена для автоматизации процессов учета рабочего времени сотрудников и расчета их заработной платы на основе этих данных. Название "Tessera" (тессера — маленький кубик камня, из которых складывается мозаика) символизирует, как отдельные рабочие события и часы сотрудников складываются в общую картину их вклада и формируют основу для расчета заработной платы.

**Основные цели:**
- Точный учет отработанных часов - с точностью до секунды.
- Автоматический расчет заработной платы.
- Прозрачность данных для сотрудников и администрации.
- Минимизация ручного труда и ошибок.

## 2. Предположения и Ограничения

Этот раздел описывает ключевые предположения, сделанные в процессе проектирования архитектуры, а также ограничения, которые могут повлиять на разработку и эксплуатацию системы.

**Предположения:**
*   Система предназначена для использования в рамках одной организации или небольшого предприятия.
*   Количество сотрудников не превышает нескольких сотен.
*   Объем данных логов (файлы `.dat`) является умеренным и не требует распределенных систем хранения или обработки.
*   Основной источник данных о приходе/уходе — файлы `.dat` из СКУД.
*   Пользователи системы (администраторы) имеют базовые навыки работы с десктопными приложениями.
*   Расчет заработной платы производится на основе почасовой ставки и фиксированных правил, без учета сложных налоговых систем или индивидуальных договоренностей, выходящих за рамки описанных правил.

**Ограничения:**
*   Система будет реализована как **десктопное приложение** (на базе Python и QT), без веб-интерфейса.
*   В качестве базы данных используется **SQLite**, что подразумевает локальное хранение данных и отсутствие необходимости в клиент-серверной архитектуре БД.
*   Первоначальная версия системы не предусматривает интеграцию с внешними бухгалтерскими системами или ERP.
*   Безопасность данных ориентирована на защиту от несанкционированного доступа на уровне приложения (пароль администратора), но не включает комплексные меры сетевой безопасности или защиты от продвинутых атак.
*   Система не предназначена для работы в режиме реального времени (например, мгновенное отображение приходов/уходов).

## 3. Компоненты Архитектуры

Система будет состоять из следующих модульных компонентов:

### 3.1. Модуль Импорта Данных (Data Ingestion Layer)

Этот компонент отвечает за получение и первичную обработку данных о событиях прихода и ухода сотрудников.

- **Источник данных:** Файлы логов `.dat` из систем контроля доступа (СКУД), а так же возможность генерации недостающих данных и ввод в ручную.
- **Парсер данных:** Будет реализован парсер для формата файла `1_attlog.dat`. На основе анализа файла, каждая строка содержит следующие поля, разделенные пробелами или табуляцией:
    1.  **ID сотрудника:** Целое число, уникальный идентификатор сотрудника.
    2.  **Дата:** В формате `YYYY-MM-DD`.
    3.  **Время:** В формате `HH:MM:SS`.
    4.  **Дополнительное поле 1:** Целое число (в образце всегда `1`). Данное поле не нужно
    5.  **Дополнительное поле 2:** Целое число (в образце всегда `255`). Данное поле не нужно
    6.  **Дополнительное поле 3:** Целое число (в образце всегда `1`). Данное поле не нужно
    7.  **Дополнительное поле 4:** Целое число (в образце всегда `0`). Данное поле не нужно
    Модуль должен извлекать ID сотрудника, дату и время, игнорируя  остальные поля для возможного будущего использования. Модуль будет расширяемым для поддержки других форматов в будущем.
- **Валидация:** Проверка данных на полноту и корректность (например, наличие ID, корректность формата даты/времени).

### 3.2. Ядро Системы (Core Business Logic)

Центральный компонент, содержащий всю бизнес-логику.

- **Управление Сотрудниками:**
    - Хранение информации о сотрудниках (ID, имя, должность, ставка оплаты).
    - CRUD-операции (создание, чтение, обновление, удаление) для профилей сотрудников.
- **Обработка Рабочего Времени:**
    - Агрегация "сырых" данных о входе/выходе в полноценные рабочие сессии.
    - Расчет отработанных часов за день, неделю, месяц.
    - Учет  опозданий и переработок, отпусков, прогулов
- **Расчет Заработной Платы:**
    - Модуль расчета ЗП на основе отработанных часов и ставки сотрудника.
    - Учет бонусов, премий и вычетов.
    - Гибкая настройка правил расчета.

### 3.3. Хранилище Данных (Data Storage)

Компонент для надежного хранения всей информации системы.

- **База данных:** SQLite - идеально подходит по задачу и объем данных

### 3.4. Пользовательский Интерфейс (User Interface)

Интерфейс для взаимодействия с системой должен быть разработан как десктоп приложение и графическим интерфейсом.

- **Режим Администратора:**
    - Обязательный ввод пароля
    - Управление сотрудниками.
    - Запуск импорта данных и расчета ЗП.
    - Просмотр и редактирование табелей учета рабочего времени.
    - Генерация отчетов.
- **Режим просмотра:**
    - Генерация расчета рабочего времени
    - Просмотр результата(но без ЗП)

### 3.5. Модуль Отчетности (Reporting)

Генерация отчетов для администрации и сотрудников.

- **Табель учета рабочего времени конкретного сотрудника.**
- **Расчетный листок по заработной плате для каждого сотрудника.**
- **Общая таблица-отчет со всеми сотрудниками, временем работы и зарплатой.**

## 4. Модель Данных (Схемы БД)

Для хранения данных будет использоваться SQLite со следующими таблицами:

**Таблица `employees` (Сотрудники)**
*   `id` (INTEGER, PRIMARY KEY): Уникальный ID сотрудника, соответствует ID из лог-файла.
*   `full_name` (TEXT, NOT NULL): Полное имя сотрудника.
*   `position_id` (INTEGER, NOT NULL, FOREIGN KEY to `positions.id`): Ссылка на должность сотрудника.
*   `hourly_rate` (REAL, NOT NULL): Базовая почасовая ставка сотрудника.
*   `is_active` (BOOLEAN, DEFAULT TRUE): Флаг, активен ли сотрудник.

**Таблица `positions` (Должности)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT)
*   `name` (TEXT, UNIQUE, NOT NULL): Название должности (например, "Инженер", "Бухгалтер").
*   `standard_workday_hours` (REAL, NOT NULL, DEFAULT 8): Норма часов в день для этой должности.
*   `weekday_overtime_multiplier` (REAL, NOT NULL, DEFAULT 1.5): Множитель для переработок в будни для этой должности.
*   `holiday_rate_multiplier` (REAL, NOT NULL, DEFAULT 1.5): Множитель для обычной работы в выходные/праздники для этой должности.
*   `holiday_overtime_rate_multiplier` (REAL, NOT NULL, DEFAULT 2.0): Множитель для переработок в выходные/праздники для этой должности.

**Таблица `raw_log_data` (Сырые данные логов)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID записи в БД.
*   `raw_line_content` (TEXT, NOT NULL): Полная, неизмененная строка из файла `1_attlog.dat`.
*   `import_batch_id` (INTEGER, NOT NULL): Идентификатор "партии" импорта.
*   `imported_at` (DATETIME, NOT NULL): Точное время, когда эта строка была добавлена в базу данных.

**Таблица `time_entries` (События входа/выхода)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID записи.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `timestamp` (DATETIME, NOT NULL): Точное время события (приход или уход).
*   `entry_type` (TEXT): Тип события ('in' или 'out'), определяется логикой.

**Таблица `work_sessions` (Рабочие сессии)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID сессии.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
*   `start_time` (DATETIME, NOT NULL): Время начала сессии.
*   `end_time` (DATETIME, NULLABLE): Время окончания сессии.
*   `duration_hours` (REAL): Длительность сессии в часах.
*   `status` (TEXT, NOT NULL): Статус сессии. Возможные значения: `completed` (завершено, найдена пара вход/выход), `incomplete` (незавершено, нет парной метки), `manual_edit` (отредактировано вручную администратором), `auto_generated` (сгенерировано автоматически системой).
*   `session_type` (TEXT, NOT NULL): Тип дня, к которому относится сессия. Возможные значения: `standard` (обычный рабочий день), `weekend` (выходной день), `holiday` (праздничный день).

**Таблица `payrolls` (Расчеты заработной платы)**
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT): Уникальный ID расчета.
*   `employee_id` (INTEGER, FOREIGN KEY to `employees.id`): ID сотрудника.
    *   `period_start` (DATE, NOT NULL): Начало расчетного периода.
*   `period_end` (DATE, NOT NULL): Конец расчетного периода.
*   `weekday_standard_hours` (REAL): Сумма обычных часов в будни.
*   `weekday_overtime_hours` (REAL): Сумма часов переработки в будни.
*   `holiday_standard_hours` (REAL): Сумма обычных часов в выходные/праздники.
*   `holiday_overtime_hours` (REAL): Сумма часов переработки в выходные/праздники.
*   `total_gross_pay` (REAL): Итоговая начисленная сумма (до вычетов).
*   `net_pay` (REAL): Заработная плата после вычетов.
*   `calculation_date` (DATETIME, NOT NULL): Дата выполнения расчета.

**Таблица `app_config` (Настройки приложения)**
*   `key` (TEXT, PRIMARY KEY): Ключ настройки (например, 'workday_start_hour', 'overtime_multiplier').
*   `value` (TEXT): Значение настройки.

### 4.1. Дополнения к Схеме БД

#### 4.1.1. Индексы

Для оптимизации производительности запросов, особенно при выборке данных по сотрудникам и временным диапазонам, будут добавлены следующие индексы:

*   `time_entries`:
    *   `CREATE INDEX idx_time_entries_employee_timestamp ON time_entries(employee_id, timestamp);`
*   `work_sessions`:
    *   `CREATE INDEX idx_work_sessions_employee_start_time ON work_sessions(employee_id, start_time);`
    *   `CREATE INDEX idx_work_sessions_employee_end_time ON work_sessions(employee_id, end_time);`
*   `payrolls`:
    *   `CREATE INDEX idx_payrolls_employee_period ON payrolls(employee_id, period_start, period_end);`

#### 4.1.2. Ограничения (Constraints)

Для обеспечения целостности и корректности данных будут использоваться следующие ограничения:

*   **Общие:**
    *   Все `FOREIGN KEY` будут с `ON DELETE CASCADE` или `ON DELETE SET NULL` в зависимости от логики (например, удаление сотрудника должно каскадно удалять его `time_entries` и `work_sessions`, но `payrolls` могут оставаться для истории).
*   **Таблица `positions`:**
    *   `standard_workday_hours` `CHECK (standard_workday_hours > 0)`
    *   `weekday_overtime_multiplier` `CHECK (weekday_overtime_multiplier >= 1.0)`
    *   `holiday_rate_multiplier` `CHECK (holiday_rate_multiplier >= 1.0)`
    *   `holiday_overtime_rate_multiplier` `CHECK (holiday_overtime_rate_multiplier >= 1.0)`
*   **Таблица `work_sessions`:**
    *   `CHECK (start_time < end_time)` (если `end_time` не NULL)
    *   `CHECK (duration_hours >= 0)`
    *   `status` `CHECK (status IN ('completed', 'incomplete', 'manual_edit', 'auto_generated'))`
    *   `session_type` `CHECK (session_type IN ('standard', 'weekend', 'holiday'))`

#### 4.1.3. Таблица Журнала Аудита (`audit_log`)

Как упоминалось в разделе "9.3. Аудит и Логирование", для отслеживания критически важных действий администраторов будет использоваться следующая таблица:

```sql
CREATE TABLE audit_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER, -- ID администратора, выполнившего действие
    action TEXT NOT NULL, -- Описание действия (e.g., 'EMPLOYEE_ADDED', 'PAYROLL_CALCULATED')
    table_name TEXT, -- Имя таблицы, к которой относится действие
    record_id INTEGER, -- ID записи в таблице, если применимо
    old_values TEXT, -- JSON строка со старыми значениями (для UPDATE)
    new_values TEXT, -- JSON строка с новыми значениями (для INSERT/UPDATE)
    timestamp DATETIME DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

#### 4.1.4. Триггеры (Triggers)

Для автоматической записи изменений в `audit_log` могут быть использованы триггеры на таблицах `employees`, `positions`, `time_entries`, `work_sessions`, `payrolls` для операций `INSERT`, `UPDATE`, `DELETE`.

*   **Пример триггера для `employees` (INSERT):**
    ```sql
    CREATE TRIGGER trg_employees_insert
    AFTER INSERT ON employees
    FOR EACH ROW
    BEGIN
        INSERT INTO audit_log (user_id, action, table_name, record_id, new_values)
        VALUES (CURRENT_USER_ID(), 'EMPLOYEE_ADDED', 'employees', NEW.id, JSON_OBJECT(
            'id', NEW.id,
            'full_name', NEW.full_name,
            'position_id', NEW.position_id,
            'hourly_rate', NEW.hourly_rate,
            'is_active', NEW.is_active
        ));
    END;
    ```
    (Примечание: `CURRENT_USER_ID()` - это плейсхолдер для функции, которая будет возвращать ID текущего авторизованного пользователя).

#### 4.1.5. Представления (Views)

Для упрощения запросов и генерации отчетов будут созданы представления:

*   `view_employee_work_summary`: Агрегированные данные по рабочему времени сотрудников за период.
*   `view_payroll_details`: Детализированные данные по расчету заработной платы.

#### 4.1.6. Версионирование Схемы БД (Schema Versioning)

Для управления изменениями в схеме базы данных будет использоваться механизм миграций (например, с помощью библиотеки `Alembic` для Python, если будет использоваться ORM, или кастомный скрипт). Каждая миграция будет представлять собой скрипт, который обновляет схему БД с одной версии на другую.

## 5. Бизнес-Правила и Обработка Граничных Случаев

Этот раздел описывает ключевые бизнес-правила, алгоритмы расчета и подходы к обработке нестандартных ситуаций в системе.

### 5.1. Обработка Граничных Случаев

Этот раздел определяет, как система должна реагировать на нестандартные ситуации.

1.  **Одна метка за день:**
    *   **Проблема:** Сотрудник отметил приход, но не отметил уход (или наоборот).
    *   **Решение:** Система должна пометить такой день как "требующий внимания" и предложить администратору вручную ввести недостающую метку или подтвердить смену (например, задав стандартную длительность рабочего дня).

2.  **Отсутствие меток за рабочий день:**
    *   **Проблема:** Сотрудник должен был работать, но отметок нет.
    *   **Решение:** Система предлагает администратору указать причину отсутствия: "Прогул", "Больничный", "Отпуск", "Административный". Каждый из этих статусов по-своему влияет на расчет ЗП.

3.  **Множественные короткие выходы/входы:**
    *   **Проблема:** Сотрудник вышел на 5 минут и вернулся.
    *   **Решение:** Ввести в `app_config` настройку `min_break_duration` (например, 15 минут). Если перерыв между выходом и входом меньше этого значения, он не прерывает рабочую сессию и считается рабочим временем.

4.  **Работа в ночное время / Переход через полночь:**
    *   **Проблема:** Смена начинается в один день, а заканчивается в другой.
    *   **Решение:** Рабочая сессия (`work_sessions`) должна быть привязана к дате её начала. Расчет отработанных часов должен корректно обрабатывать переход через 00:00.

### 5.2. Гибкая Тарификация и Расчет Часов

*   **Задача:** Система должна гибко рассчитывать 4 типа отработанного времени (будни норма, будни переработка, выходные норма, выходные переработка) на основе индивидуальных настроек сотрудника.
*   **Решение:**
    1.  При расчете ЗП для каждого сотрудника система определяет его должность через `position_id` и использует настройки из связанной таблицы `positions`: `standard_workday_hours`, `weekday_overtime_multiplier`, `holiday_rate_multiplier`, `holiday_overtime_rate_multiplier`.
    2.  Для каждого дня в расчетном периоде система анализирует `work_sessions`:
        *   Определяется тип дня (`standard`, `weekend`, `holiday`) с помощью `session_type`.
        *   Суммируются все часы за этот день.
        *   Если сумма часов превышает `standard_workday_hours` должности, излишек классифицируется как "часы переработки" (`overtime_hours`), остальное — как "стандартные часы" (`standard_hours`).
    3.  В зависимости от типа дня, эти часы добавляются к соответствующим полям в таблице `payrolls` (`weekday_standard_hours`, `holiday_overtime_hours` и т.д.).
    4.  Итоговая сумма `total_gross_pay` рассчитывается путем сложения оплаты по всем четырем категориям часов, каждая со своим множителем, умноженным на `hourly_rate` сотрудника.

### 5.3. Управление Выходными и Праздниками

*   **Задача:** Определять, является ли день рабочим, выходным или праздничным.
*   **Решение:**
    1.  **Выходные:** Дни, у которых `datetime.weekday()` возвращает 5 (суббота) или 6 (воскресенье), всегда считаются выходными (`weekend`).
    2.  **Праздники:** При запуске приложение читает файл `holidays.toml` (или аналогичный), в котором перечислены все официальные праздники и дни переносов.
    3.  **Интеграция (будущее):** В будущем "Модуль Импорта Данных" может быть расширен функцией парсинга производственного календаря с внешнего ресурса (например, Консультант Плюс), чтобы автоматически обновлять `holidays.toml`.

### 5.4. Подтверждение Расчета ("Заморозка")

*   **Задача:** Дать администратору возможность проверить итоговые цифры перед окончательным сохранением расчета.
*   **Решение:**
    1.  Администратор выбирает сотрудника и период, запускает расчет.
    2.  Система выполняет все вычисления "в памяти", не записывая ничего в таблицу `payrolls`.
    3.  На экране отображается **окно предварительного просмотра**: "Иванов И.И., период 01.11-30.11. Итого к начислению: X руб. (Стандартные часы: Y, Переработка: Z, ...). Сформировать отчет?"
    4.  **Только после нажатия кнопки "Подтвердить" / "Сохранить"** система создает новую запись в таблице `payrolls` и генерирует все необходимые файлы отчетов. Если администратор отменяет операцию, никаких следов в БД не остается.

### 5.5. Алгоритмы

#### 5.5.1. Алгоритм агрегации событий в рабочие сессии (time_entries -> work_sessions)

**Вход:** Список `time_entries` для одного сотрудника за определенный период, `min_break_duration` (из `app_config`).
**Выход:** Список `work_sessions`.

**Шаги:**
1.  **Сортировка:** Отсортировать все `time_entries` для данного сотрудника по `timestamp` по возрастанию.
2.  **Инициализация:** Создать пустой список `work_sessions`.
3.  **Итерация по событиям:**
    *   Инициализировать `current_session_start = None`.
    *   Для каждого `entry` в отсортированном списке:
        *   Если `entry.entry_type == 'in'`:
            *   Если `current_session_start` уже установлен (т.е. был предыдущий 'in' без 'out'), это означает пропущенную метку 'out'. Завершить предыдущую сессию как `incomplete` (или сгенерировать 'out' по правилам, например, через `standard_workday_hours` от `current_session_start`). Добавить ее в `work_sessions`.
            *   Установить `current_session_start = entry.timestamp`.
        *   Если `entry.entry_type == 'out'`:
            *   Если `current_session_start` не установлен (т.е. был 'out' без предыдущего 'in'), это означает пропущенную метку 'in'. Проигнорировать или пометить как ошибку.
            *   Если `current_session_start` установлен:
                *   Рассчитать `session_end = entry.timestamp`.
                *   Рассчитать `duration = session_end - current_session_start`.
                *   **Обработка коротких перерывов:**
                    *   Если это не первая сессия за день и предыдущая `work_session.end_time` существует:
                        *   Рассчитать `break_duration = current_session_start - previous_work_session.end_time`.
                        *   Если `break_duration < min_break_duration`:
                            *   Объединить текущую сессию с предыдущей: обновить `previous_work_session.end_time = session_end` и `previous_work_session.duration_hours += duration`.
                            *   Сбросить `current_session_start = None`.
                            *   Продолжить к следующему `entry`.
                *   **Обработка перехода через полночь:**
                    *   Если `session_end.date() > current_session_start.date()`:
                        *   Разбить сессию на две:
                            *   Первая сессия: `start = current_session_start`, `end = current_session_start.end_of_day()`. Добавить в `work_sessions`.
                            *   Вторая сессия: `start = session_end.start_of_day()`, `end = session_end`. Добавить в `work_sessions`.
                            *   (Примечание: более сложная логика может потребоваться для точного распределения часов по дням, если смена длится несколько дней).
                    *   Иначе (сессия в пределах одного дня):
                        *   Создать `work_session` с `start_time = current_session_start`, `end_time = session_end`, `duration_hours = duration`. Добавить в `work_sessions`.
                *   Сбросить `current_session_start = None`.
4.  **Завершение незакрытых сессий:** После итерации по всем `entry`:
    *   Если `current_session_start` все еще установлен, это означает незакрытую сессию. Создать `work_session` с `start_time = current_session_start`, `end_time = None`, `status = 'incomplete'`. Добавить в `work_sessions`.
5.  **Определение типа дня:** Для каждой `work_session` определить `session_type` (`standard`, `weekend`, `holiday`) на основе даты сессии и списка праздников.
6.  **Возврат:** Вернуть список `work_sessions`.

#### 5.5.2. Алгоритм расчета заработной платы (work_sessions -> payrolls)

**Вход:** `employee_id`, `period_start`, `period_end`, список `work_sessions` для сотрудника за период, `hourly_rate` сотрудника, настройки должности (`standard_workday_hours`, `weekday_overtime_multiplier`, `holiday_rate_multiplier`, `holiday_overtime_rate_multiplier`).
**Выход:** Объект `payroll` для сотрудника за период.

**Шаги:**
1.  **Инициализация:**
    *   `total_weekday_standard_hours = 0`
    *   `total_weekday_overtime_hours = 0`
    *   `total_holiday_standard_hours = 0`
    *   `total_holiday_overtime_hours = 0`
    *   `total_gross_pay = 0`
2.  **Итерация по дням в расчетном периоде:**
    *   Для каждого дня `current_date` от `period_start` до `period_end`:
        *   Получить все `work_sessions` для `employee_id` и `current_date`.
        *   Суммировать `duration_hours` всех сессий за `current_date` в `daily_total_hours`.
        *   Определить `day_type` для `current_date` (`standard`, `weekend`, `holiday`) на основе `datetime.weekday()` и списка праздников.
        *   **Распределение часов:**
            *   `standard_hours_for_day = min(daily_total_hours, standard_workday_hours)`
            *   `overtime_hours_for_day = daily_total_hours - standard_hours_for_day`
        *   **Накопление по категориям:**
            *   Если `day_type == 'standard'` (будний день, не праздник):
                *   `total_weekday_standard_hours += standard_hours_for_day`
                *   `total_weekday_overtime_hours += overtime_hours_for_day`
            *   Если `day_type == 'weekend'` или `day_type == 'holiday'` (выходной или праздничный день):
                *   `total_holiday_standard_hours += standard_hours_for_day`
                *   `total_holiday_overtime_hours += overtime_hours_for_day`
3.  **Расчет общей заработной платы:**
    *   `pay_weekday_standard = total_weekday_standard_hours * hourly_rate`
    *   `pay_weekday_overtime = total_weekday_overtime_hours * hourly_rate * weekday_overtime_multiplier`
    *   `pay_holiday_standard = total_holiday_standard_hours * hourly_rate * holiday_rate_multiplier`
    *   `pay_holiday_overtime = total_holiday_overtime_hours * hourly_rate * holiday_overtime_rate_multiplier`
    *   `total_gross_pay = pay_weekday_standard + pay_weekday_overtime + pay_holiday_standard + pay_holiday_overtime`
4.  **Применение вычетов/бонусов (placeholder):**
    *   `net_pay = total_gross_pay - (вычеты) + (бонусы)` (Детализировать в будущем)
5.  **Создание объекта `payroll`:**
    *   `payroll = {`
    *   `employee_id: employee_id,`
    *   `period_start: period_start,`
    *   `period_end: period_end,`
    *   `weekday_standard_hours: total_weekday_standard_hours,`
    *   `weekday_overtime_hours: total_weekday_overtime_hours,`
    *   `holiday_standard_hours: total_holiday_standard_hours,`
    *   `holiday_overtime_hours: total_holiday_overtime_hours,`
    *   `total_gross_pay: total_gross_pay,`
    *   `net_pay: net_pay,`
    *   `calculation_date: current_timestamp`
    *   `}`
6.  **Возврат:** Объект `payroll`.

## 6. Сценарии Использования (Use Cases)

### 6.1. Режи Администратор: Добавление нового сотрудника

*   **Актер:** Администратор
*   **Предусловия:** Администратор авторизован в системе.
*   **Основной поток:**
    1.  Администратор открывает раздел "Управление сотрудниками".
    2.  Администратор нажимает кнопку "Добавить нового сотрудника".
    3.  Система отображает форму для ввода данных нового сотрудника (Полное имя, Должность, Почасовая ставка).
    4.  Администратор вводит полное имя сотрудника, выбирает существующую должность из выпадающего списка и вводит почасовую ставку.
    5.  Администратор нажимает кнопку "Сохранить".
    6.  Система валидирует введенные данные.
    7.  Система создает новую запись о сотруднике в таблице `employees` и присваивает ему уникальный `id`.
    8.  Система отображает сообщение об успешном добавлении сотрудника и обновляет список сотрудников.
*   **Альтернативные потоки:**
    *   **6.1a. Отмена добавления:** Администратор нажимает кнопку "Отмена" на форме добавления (шаг 4). Система закрывает форму без сохранения данных.
    *   **6.1b. Некорректные данные:** Если введенные данные не проходят валидацию (шаг 6), система отображает сообщения об ошибках рядом с соответствующими полями. Администратор может исправить данные и повторить попытку сохранения (возврат к шагу 4).
*   **Пост-условия:** В системе зарегистрирован новый сотрудник с указанными данными, или состояние системы не изменилось (если операция была отменена или произошла ошибка валидации).
*   **Правила валидации:**
    *   `full_name`: Обязательное поле, строка, не может быть пустым.
    *   `position_id`: Обязательное поле, должно соответствовать существующему `id` в таблице `positions`.
    *   `hourly_rate`: Обязательное поле, положительное число (REAL), больше 0.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Если при попытке сохранения произошла ошибка базы данных, система отображает сообщение об ошибке и предлагает повторить попытку или обратиться в поддержку.


### 6.2. Режи Администратор: Изменение действующего сотрудника(должность,ставка)

*   **Актер:** Администратор
*   **Предусловия:** Администратор авторизован в системе. В системе существуют записи о сотрудниках.
*   **Основной поток:**
    1.  Администратор открывает раздел "Управление сотрудниками".
    2.  Система отображает список сотрудников.
    3.  Администратор выбирает существующего сотрудника из списка для редактирования (например, двойным кликом или нажатием кнопки "Редактировать").
    4.  Система отображает форму редактирования с текущими данными сотрудника (полное имя, должность, почасовая ставка).
    5.  Администратор изменяет должность сотрудника, выбирая новую из выпадающего списка, и/или изменяет почасовую ставку. (Полное имя также может быть изменено, но это не является основной целью данного Use Case).
    6.  Администратор нажимает кнопку "Сохранить".
    7.  Система валидирует введенные данные.
    8.  Система обновляет запись о сотруднике в таблице `employees`.
    9.  Система отображает сообщение об успешном обновлении данных сотрудника и обновляет список сотрудников.
*   **Альтернативные потоки:**
    *   **6.2a. Отмена редактирования:** Администратор нажимает кнопку "Отмена" на форме редактирования (шаг 5). Система закрывает форму без сохранения изменений.
    *   **6.2b. Некорректные данные:** Если введенные данные не проходят валидацию (шаг 7), система отображает сообщения об ошибках рядом с соответствующими полями. Администратор может исправить данные и повторить попытку сохранения (возврат к шагу 5).
    *   **6.2c. Сотрудник не найден:** Если выбранный сотрудник по какой-либо причине не найден в БД (например, был удален другим администратором), система отображает сообщение об ошибке и обновляет список сотрудников.
*   **Пост-условия:** Данные выбранного сотрудника обновлены в системе, или состояние системы не изменилось (если операция была отменена или произошла ошибка валидации).
*   **Правила валидации:**
    *   `position_id`: Обязательное поле, должно соответствовать существующему `id` в таблице `positions`.
    *   `hourly_rate`: Обязательное поле, положительное число (REAL), больше 0.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Если при попытке сохранения произошла ошибка базы данных, система отображает сообщение об ошибке и предлагает повторить попытку или обратиться в поддержку.

### 6.3. Режим Администратор: Обработка логов и расчет ЗП за месяц без внесения внешних данных

*   **Актер:** Администратор
*   **Предусловия:** Администратор авторизован в системе. В системе настроены данные о сотрудниках и должностях. Доступен файл `1_attlog.dat` с данными о приходах/уходах.
*   **Основной поток:**
    1.  Администратор открывает раздел "Расчет заработной платы" или "Импорт данных".
    2.  Администратор выбирает файл `1_attlog.dat` для импорта.
    3.  Администратор указывает расчетный период (например, месяц).
    4.  Администратор нажимает кнопку "Запустить обработку и расчет".
    5.  **Система выполняет импорт данных из файла:**
        *   Парсит каждую строку файла `1_attlog.dat`, извлекая `employee_id`, дату и время.
        *   Валидирует формат каждой строки.
        *   Сохраняет сырые строки в `raw_log_data` с `import_batch_id` и `imported_at`.
        *   Сохраняет валидные события в `time_entries`.
    6.  **Система агрегирует `time_entries` в `work_sessions` для указанного периода:**
        *   Группирует события по сотруднику и дню.
        *   Определяет пары "вход-выход" для создания `work_sessions`.
        *   Применяет правила обработки граничных случаев (например, `min_break_duration`, переход через полночь, см. 5.1).
        *   Помечает незавершенные сессии (`incomplete`) или дни без меток.
        *   Сохраняет сформированные `work_sessions`.
    7.  **Система выполняет расчет заработной платы для всех сотрудников за указанный период:**
        *   Для каждого сотрудника и дня в периоде анализирует `work_sessions`.
        *   Определяет тип дня (рабочий, выходной, праздничный, см. 5.3).
        *   Рассчитывает 4 типа отработанного времени (будни норма, будни переработка, выходные норма, выходные переработка) с учетом `standard_workday_hours` и множителей из `positions` (см. 5.2).
        *   Суммирует часы и рассчитывает `total_gross_pay` на основе `hourly_rate` и множителей.
    8.  Система отображает **окно предварительного просмотра расчета** (как описано в 5.4 "Подтверждение Расчета").
    9.  Администратор просматривает результаты и нажимает кнопку "Подтвердить" / "Сохранить".
    10. Система создает новую запись в таблице `payrolls` и генерирует необходимые отчеты.
    11. Система отображает сообщение об успешном завершении операции.
*   **Альтернативные потоки:**
    *   **6.3a. Файл не найден/недоступен:** Если выбранный файл `1_attlog.dat` не найден или недоступен, система отображает ошибку.
    *   **6.3b. Ошибки парсинга/валидации:** Если в файле `1_attlog.dat` обнаружены некорректные строки, система может:
        *   Пропустить некорректные строки и продолжить импорт, отобразив предупреждение и список ошибок.
        *   Прервать импорт, отобразив ошибку. (Предпочтительно: пропустить и предупредить).
    *   **6.3c. Отсутствие данных о сотрудниках/должностях:** Если для `employee_id` из лога нет соответствующей записи в `employees` или `positions`, система помечает эти записи как "требующие внимания" и продолжает обработку для остальных. В окне предварительного просмотра отображается предупреждение.
    *   **6.3d. Отмена расчета:** Администратор нажимает кнопку "Отмена" в окне предварительного просмотра (шаг 9). Система отменяет сохранение расчета и генерацию отчетов.
*   **Пост-условия:** Данные из `1_attlog.dat` импортированы в `raw_log_data` и `time_entries`. Сформированы и сохранены `work_sessions`. Расчет заработной платы сохранен в `payrolls` и сгенерированы отчеты, ИЛИ состояние системы не изменилось (если операция была отменена или произошла ошибка).
*   **Правила валидации:**
    *   Выбранный файл должен быть `.dat`.
    *   Расчетный период должен быть корректным (дата начала <= дата окончания).
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Ошибки при записи в БД на любом этапе.
    *   **Ошибка расчета:** Непредвиденные ошибки в логике расчета.


### 6.4. Режи Администратор: Обработка логов и расчет ЗП за месяц с внесением внешних данных

*   **Актер:** Администратор
*   **Предусловия:** Администратор авторизован в системе. В системе настроены данные о сотрудниках и должностях. Доступен файл `1_attlog.dat` с данными о приходах/уходах.
*   **Основной поток:**
    1.  Администратор выполняет шаги 1-7 из Use Case 6.3 ("Обработка логов и расчет ЗП за месяц без внесения внешних данных").
    2.  Система идентифицирует дни с одной меткой (приход без ухода или наоборот) и дни без меток для сотрудников, которые должны были работать, и отображает их в интерфейсе для корректировки.

        *   **Указать причину отсутствия:** Выбрать из предопределенного списка ("Прогул", "Больничный", "Отпуск", "Административный").
        *   **Подтвердить смену:** Если метка одна, но смена считается завершенной (например, стандартная длительность рабочего дня).
    4.  После внесения корректировок, администратор нажимает кнопку "Пересчитать".

    6.  Система отображает обновленное **окно предварительного просмотра расчета**.
    7.  Администратор просматривает результаты и нажимает кнопку "Подтвердить" / "Сохранить".
    8.  Система создает новую запись в таблице `payrolls` и генерирует необходимые отчеты.
    9.  Система отображает сообщение об успешном завершении операции.
*   **Альтернативные потоки:**
    *   **6.4a. Отмена корректировок:** Администратор нажимает кнопку "Отмена" на форме корректировок (шаг 4). Система возвращается к предыдущему состоянию расчета без внесенных вручную изменений.
    *   **6.4b. Некорректные вручную введенные данные:** Если администратор вводит некорректные данные (например, время ухода раньше времени прихода), система отображает ошибку и требует исправления.
    *   **6.4c. Отмена расчета:** Администратор нажимает кнопку "Отмена" в окне предварительного просмотра (шаг 7). Система отменяет сохранение расчета и генерацию отчетов.
*   **Пост-условия:** Данные из `1_attlog.dat` импортированы. `work_sessions` и расчет заработной платы обновлены с учетом ручных корректировок. Расчет заработной платы сохранен в `payrolls` и сгенерированы отчеты, ИЛИ состояние системы не изменилось.
*   **Правила валидации:**
    *   Вручную введенные метки должны быть логически корректны (время прихода < время ухода).
    *   Причины отсутствия должны быть выбраны из предопределенного списка.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Ошибки при записи в БД.
    *   **Ошибка расчета:** Непредвиденные ошибки в логике пересчета.

### 6.5. Режи Администратор: Обработка логов и расчет ЗП за месяц с генерацией недостающий информации и редактировании после генерации

*   **Актер:** Администратор
*   **Предусловия:** Администратор авторизован в системе. В системе настроены данные о сотрудниках и должностях. Доступен файл `1_attlog.dat` с данными о приходах/уходах.
*   **Основной поток:**
    1.  Администратор выполняет шаги 1-7 из Use Case 6.3 ("Обработка логов и расчет ЗП за месяц без внесения внешних данных").
    2.  Система идентифицирует дни с одной меткой (приход без ухода или наоборот) и дни без меток для сотрудников, которые должны были работать.
    3.  Система предлагает администратору опцию "Автоматически сгенерировать недостающую информацию".
    4.  Администратор выбирает опцию "Автоматически сгенерировать недостающую информацию".
    5.  **Система генерирует недостающие метки/причины отсутствия:**
        *   Для дней с одной меткой: генерирует вторую метку, исходя из стандартной длительности рабочего дня для должности сотрудника.
        *   Для дней без меток: помечает как "Прогул" по умолчанию или согласно настроенным правилам.
        *   Помечает сгенерированные `work_sessions` как `auto_generated`.
    6.  Система отображает список сгенерированных корректировок и позволяет администратору просмотреть и при необходимости отредактировать их.
    7.  Администратор может вручную изменить сгенерированные метки или причины отсутствия.
    8.  После внесения (или подтверждения) корректировок, администратор нажимает кнопку "Пересчитать".
    9.  Система пересчитывает `work_sessions` и расчет заработной платы с учетом внесенных (или сгенерированных) данных.
    10. Система отображает обновленное **окно предварительного просмотра расчета**.
    11. Администратор просматривает результаты и нажимает кнопку "Подтвердить" / "Сохранить".
    12. Система создает новую запись в таблице `payrolls` и генерирует необходимые отчеты.
    13. Система отображает сообщение об успешном завершении операции.
*   **Альтернативные потоки:**
    *   **6.5a. Отмена генерации:** Администратор отменяет автоматическую генерацию и может перейти к ручному вводу (UC 6.4) или отменить операцию.
    *   **6.5b. Некорректные вручную введенные данные:** Если администратор вручную изменяет сгенерированные данные некорректно, система отображает ошибку и требует исправления.
    *   **6.5c. Отмена расчета:** Администратор нажимает кнопку "Отмена" в окне предварительного просмотра (шаг 11). Система отменяет сохранение расчета и генерацию отчетов.
*   **Пост-условия:** Данные из `1_attlog.dat` импортированы. `work_sessions` и расчет заработной платы обновлены с учетом сгенерированных и/или ручных корректировок. Расчет заработной платы сохранен в `payrolls` и сгенерированы отчеты, ИЛИ состояние системы не изменилось.
*   **Правила валидации:**
    *   Сгенерированные и вручную измененные метки должны быть логически корректны.
    *   Причины отсутствия должны быть выбраны из предопределенного списка.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Ошибки при записи в БД.
    *   **Ошибка расчета:** Непредвиденные ошибки в логике пересчета.

### 6.6. Режи Администратор: Обработка логов и расчет ЗП за месяц с редактированием записей работников удаление дат, меток и редактирование меток

*   **Актер:** Администратор
*   **Предусловия:** Администратор авторизован в системе. Данные о `time_entries` и `work_sessions` уже существуют в системе.
*   **Основной поток:**
    1.  Администратор открывает раздел "Табель учета рабочего времени" или "Просмотр рабочих сессий".
    2.  Администратор выбирает сотрудника и период для просмотра его рабочих записей.
    3.  Система отображает список `time_entries` и/или `work_sessions` для выбранного сотрудника и периода.
    4.  Администратор может выполнить следующие действия:
        *   **Редактировать метку:** Выбрать существующую `time_entry` и изменить ее `timestamp` или `entry_type`.
        *   **Добавить метку:** Ввести новую `time_entry` (например, если сотрудник забыл отметиться).
        *   **Удалить метку:** Выбрать существующую `time_entry` и удалить ее.
        *   **Редактировать рабочую сессию:** Выбрать `work_session` и изменить ее `start_time`, `end_time`, `duration_hours` или `status`.
        *   **Удалить рабочую сессию:** Выбрать `work_session` и удалить ее.
    5.  После внесения изменений, администратор нажимает кнопку "Сохранить изменения".
    6.  Система валидирует внесенные изменения.
    7.  Система обновляет соответствующие записи в таблицах `time_entries` и/или `work_sessions`.
    8.  Система пересчитывает `work_sessions` (если были изменены `time_entries`) и расчет заработной платы для затронутого периода.
    9.  Система отображает сообщение об успешном сохранении и обновляет отображаемые данные.
*   **Альтернативные потоки:**
    *   **6.6a. Отмена изменений:** Администратор нажимает кнопку "Отмена" до сохранения. Система отменяет все внесенные изменения.
    *   **6.6b. Некорректные данные:** Если внесенные вручную данные некорректны (например, время ухода раньше прихода, пересекающиеся сессии), система отображает ошибку и требует исправления.
*   **Пост-условия:** `time_entries` и/или `work_sessions` обновлены в соответствии с действиями администратора. Расчет заработной платы для затронутого периода пересчитан.
*   **Правила валидации:**
    *   `timestamp` для `time_entry` должен быть корректной датой/временем.
    *   `start_time` < `end_time` для `work_session`.
    *   `work_sessions` не должны пересекаться для одного сотрудника.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Ошибки при записи в БД.
    *   **Ошибка расчета:** Непредвиденные ошибки в логике пересчета.

### 6.7. Режим просмотра: Просмотр рабочего времени сотрудников

*   **Актер:** Администратор (в режиме просмотра)
*   **Предусловия:** Администратор авторизован в системе. В системе существуют данные о `work_sessions` для сотрудников.
*   **Основной поток:**
    1.  Администратор открывает раздел "Просмотр рабочего времени" или "Отчеты по рабочему времени".
    2.  Администратор выбирает сотрудника (или всех сотрудников) и указывает период для просмотра.
    3.  Администратор нажимает кнопку "Показать отчет".
    4.  Система извлекает данные о `work_sessions` для выбранных сотрудников и периода.
    5.  Система отображает агрегированный отчет по рабочему времени, который может включать:
        *   Общее количество отработанных часов за период.
        *   Разбивку по дням/неделям.
        *   Информацию о статусе сессий (завершенные, незавершенные, сгенерированные).
        *   (Важно: без информации о заработной плате в этом режиме).
*   **Альтернативные потоки:**
    *   **6.7a. Нет данных:** Если для выбранного сотрудника/периода нет данных о `work_sessions`, система отображает соответствующее сообщение.
    *   **6.7b. Фильтрация/Сортировка:** Администратор может применить фильтры (например, по типу сессии) или сортировку к отображаемым данным.
*   **Пост-условия:** Администратор просмотрел отчет по рабочему времени. Состояние системы не изменилось.
*   **Правила валидации:**
    *   Выбранный период должен быть корректным.
*   **Сценарии ошибок:**
    *   **Ошибка БД:** Ошибки при извлечении данных из БД.

## 9. Безопасность

Этот раздел описывает меры безопасности, применяемые в системе для защиты данных и контроля доступа.

### 9.1. Аутентификация и Авторизация

*   **Аутентификация:**
    *   **Хеширование паролей:** Пароли пользователей (администраторов) не хранятся в открытом виде. Используется криптографически стойкий алгоритм хеширования (например, `bcrypt` или `argon2`) с солью для защиты от атак по словарю и радужных таблиц.
    *   **Хранение:** Хеши паролей хранятся в базе данных.
*   **Авторизация (Управление доступом на основе ролей - RBAC):**
    *   **Роли:** Система поддерживает как минимум две роли: "Администратор" и "Просмотрщик".
    *   **Разграничение доступа:**
        *   **Администратор:** Полный доступ ко всем функциям системы, включая управление сотрудниками, импорт данных, расчет ЗП, редактирование данных.
        *   **Просмотрщик:** Доступ только к просмотру отчетов по рабочему времени (без данных о ЗП) и, возможно, к просмотру списка сотрудников без возможности редактирования.
    *   **Реализация:** Проверки прав доступа выполняются на уровне бизнес-логики перед выполнением операций.

### 9.2. Защита Данных

*   **Защита от SQL-инъекций:** Все запросы к базе данных формируются с использованием параметризованных запросов (prepared statements) или ORM, что предотвращает возможность SQL-инъекций.
*   **Целостность данных:** Обеспечивается за счет использования ограничений (constraints) в схеме БД (PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE).
*   **Шифрование данных:**
    *   **Данные в покое:** Для повышения безопасности конфиденциальные данные (например, почасовые ставки, итоговые суммы ЗП) могут быть зашифрованы в базе данных. Ключи шифрования хранятся отдельно и защищены. (Примечание: для SQLite это может потребовать использования расширений или файлового шифрования на уровне ОС).
    *   **Данные в движении:** Поскольку это десктопное приложение без сетевого взаимодействия, шифрование данных в движении не является первоочередной задачей.

### 9.3. Аудит и Логирование

*   **Журнал аудита (Audit Log):** Ведется запись всех критически важных действий администраторов, включая:
    *   Вход/выход из системы.
    *   Добавление, изменение, удаление сотрудников.
    *   Запуск импорта данных.
    *   Запуск расчета заработной платы.
    *   Внесение ручных корректировок в `time_entries` или `work_sessions`.
*   **Содержание записи аудита:** `id` пользователя, тип действия, дата/время, затронутая сущность/запись, старые и новые значения (если применимо).
*   **Хранение:** Журнал аудита хранится в отдельной таблице БД (`audit_log`) и защищен от несанкционированного изменения.

## 10. Обработка Ошибок и Логирование

Этот раздел описывает общую стратегию системы по обработке ошибок и ведению логов для обеспечения стабильности, отладки и мониторинга.

### 10.1. Стратегия Обработки Ошибок

*   **Типы ошибок:**
    *   **Ошибки валидации:** Возникают при некорректном вводе данных пользователем или при импорте. Обрабатываются путем предоставления обратной связи пользователю (сообщения об ошибках в UI).
    *   **Ошибки бизнес-логики:** Возникают при нарушении бизнес-правил (например, попытка сохранить пересекающиеся рабочие сессии). Обрабатываются путем предотвращения операции и информирования пользователя.
    *   **Ошибки данных/БД:** Возникают при проблемах с доступом к БД, повреждении данных, нарушении ограничений БД. Обрабатываются путем перехвата исключений, логирования и информирования пользователя о необходимости обратиться в поддержку.
    *   **Системные/Внутренние ошибки:** Непредвиденные ошибки в коде. Перехватываются, логируются с полным стеком вызовов, пользователю отображается общее сообщение об ошибке.
*   **Механизмы обработки:**
    *   **Исключения (Exceptions):** Использование стандартного механизма исключений Python для сигнализации об ошибках.
    *   **Централизованный обработчик:** Единая точка входа для обработки неперехваченных исключений, обеспечивающая корректное логирование и отображение сообщений пользователю.
    *   **Обратная связь пользователю:** Четкие и понятные сообщения об ошибках в пользовательском интерфейсе.
*   **Стратегии восстановления:**
    *   **Откат (Rollback):** Для операций, изменяющих состояние БД (например, импорт данных, сохранение расчета ЗП), в случае ошибки выполняется откат транзакции для сохранения целостности данных.
    *   **Повторная попытка (Retry):** Для временных ошибок (например, блокировка БД) может быть реализована ограниченная логика повторных попыток.

### 10.2. Стратегия Логирования

*   **Уровни логирования:** Используются стандартные уровни логирования (DEBUG, INFO, WARNING, ERROR, CRITICAL) для категоризации сообщений.
*   **Что логировать:**
    *   **Действия пользователя:** (См. 9.3 Аудит и Логирование).
    *   **Начало/завершение ключевых операций:** Импорт файлов, расчет ЗП.
    *   **Предупреждения:** Некорректные данные в файлах импорта, которые были пропущены.
    *   **Ошибки:** Все перехваченные исключения, ошибки БД, ошибки валидации с детальной информацией (сообщение, стек вызовов, контекст).
    *   **Производительность:** Время выполнения критических операций (опционально).
*   **Формат логов:** Логи форматируются для удобства чтения и парсинга (например, JSON или структурированный текст).
*   **Место хранения:** Логи хранятся в файлах на диске (например, в каталоге пользователя или в специальном каталоге приложения).
*   **Ротация логов:** Реализована ротация логов по размеру или по времени для предотвращения переполнения диска.
*   **Конфигурация:** Уровень логирования и параметры ротации настраиваются через конфигурационный файл.

## 11. Структура Проекта

Этот раздел описывает предлагаемую структуру каталогов и файлов проекта, обеспечивающую модульность, чистоту кода и удобство разработки.

### 11.1. Общая Структура Каталогов

```
tessera/
├── core/                # Основная бизнес-логика и модели
│   ├── models/          # ORM модели (сущности БД)
│   ├── services/        # Сервисы, реализующие бизнес-логику
│   ├── repositories/    # Абстракции для работы с БД (CRUD операции)
│   └── validators/      # Модули для валидации данных
├── ingestion/           # Модуль импорта данных
│   ├── parsers/         # Парсеры для различных форматов файлов (например, 1_attlog.dat)
│   └── adapters/        # Адаптеры для различных источников данных
├── reporting/           # Модуль генерации отчетов
│   ├── templates/       # Шаблоны отчетов (PDF, Markdown, Excel)
│   └── generators/      # Логика генерации отчетов
├── ui/                  # Пользовательский интерфейс (QT)
│   ├── widgets/         # Переиспользуемые UI компоненты
│   ├── windows/         # Основные окна приложения
│   └── controllers/     # Логика взаимодействия UI с Core
├── config/              # Файлы конфигурации (например, holidays.toml)
├── tests/               # Тесты (unit, integration, e2e)
│   ├── unit/
│   ├── integration/
│   └── e2e/
├── utils/               # Общие утилиты и вспомогательные функции
├── migrations/          # Скрипты миграции БД
├── main.py              # Точка входа в приложение
├── database.py          # Инициализация БД, подключение
└── README.md            # Описание проекта
```

### 11.2. Описание Модулей

*   **`core/`**: Содержит основную бизнес-логику системы.
    *   `models/`: Определения классов, которые мапятся на таблицы базы данных (ORM-модели).
    *   `services/`: Реализуют конкретные бизнес-операции (например, `EmployeeService`, `PayrollService`, `WorkSessionService`).
    *   `repositories/`: Предоставляют абстрактный интерфейс для взаимодействия с базой данных, скрывая детали реализации (например, `EmployeeRepository`).
    *   `validators/`: Содержат логику для проверки корректности данных перед их обработкой или сохранением.
*   **`ingestion/`**: Отвечает за получение и первичную обработку внешних данных.
    *   `parsers/`: Содержат логику для разбора различных форматов входных файлов.
    *   `adapters/`: Могут быть использованы для адаптации данных из разных источников к внутреннему формату системы.
*   **`reporting/`**: Отвечает за генерацию различных отчетов.
    *   `templates/`: Хранит шаблоны для создания отчетов в разных форматах.
    *   `generators/`: Содержит логику, которая берет данные и шаблоны для создания готовых отчетов.
*   **`ui/`**: Содержит все компоненты пользовательского интерфейса.
    *   `widgets/`: Небольшие, переиспользуемые элементы UI.
    *   `windows/`: Основные окна приложения.
    *   `controllers/`: Обрабатывают события UI и взаимодействуют с `core/services`.
*   **`config/`**: Хранит все конфигурационные файлы, такие как `holidays.toml`, настройки приложения и т.д.
*   **`tests/`**: Содержит все виды тестов для обеспечения качества кода.
*   **`utils/`**: Модуль для общих вспомогательных функций, которые не относятся к конкретной бизнес-логике.
*   **`migrations/`**: Скрипты для управления изменениями схемы базы данных.
*   **`main.py`**: Главный файл приложения, точка входа.
*   **`database.py`**: Модуль для инициализации соединения с базой данных и выполнения базовых операций.

## 12. Стратегия Тестирования

Этот раздел описывает подход к тестированию системы для обеспечения ее качества, надежности и соответствия требованиям.

### 12.1. Типы Тестирования

*   **Модульное тестирование (Unit Tests):**
    *   **Цель:** Проверка корректности работы отдельных функций, методов и классов в изоляции.
    *   **Покрытие:** Минимум 80% покрытия кода для критически важных модулей (бизнес-логика, алгоритмы расчета, парсеры).
    *   **Примеры:** Тесты для функций расчета часов, валидаторов, методов репозиториев.
*   **Интеграционное тестирование (Integration Tests):**
    *   **Цель:** Проверка взаимодействия между различными компонентами системы (например, Core Service с Repository и БД, Ingestion с Core).
    *   **Примеры:** Тестирование полного цикла импорта данных из файла в БД, тестирование расчета ЗП с использованием реальных данных из БД.
*   **Функциональное/Системное тестирование (Functional/System Tests):**
    *   **Цель:** Проверка соответствия системы функциональным требованиям, описанным в Use Cases.
    *   **Примеры:** Тестирование полного сценария добавления сотрудника через UI, запуск расчета ЗП и генерация отчета.
*   **Приемочное тестирование (Acceptance Tests):**
    *   **Цель:** Проверка системы конечными пользователями или представителями бизнеса на соответствие их ожиданиям.
*   **Тестирование пользовательского интерфейса (UI/E2E Tests):**
    *   **Цель:** Автоматизированная проверка взаимодействия пользователя с UI и корректности отображения данных.
    *   **Инструменты:** Могут использоваться фреймворки для автоматизации UI (например, `PyQt` имеет свои инструменты для тестирования, или сторонние библиотеки).

### 12.2. Инструменты и Подходы

*   **Фреймворк для тестирования:** `pytest` (для Python) как основной фреймворк для модульных и интеграционных тестов.
*   **Тестовые данные (Test Data Fixtures):** Использование фикстур для создания контролируемых и воспроизводимых тестовых данных.
*   **Мокирование (Mocking):** Использование моков и стабов для изоляции тестируемых компонентов и имитации внешних зависимостей (например, БД, файловой системы).
*   **Непрерывная интеграция (CI):** Интеграция тестов в процесс CI для автоматического запуска при каждом изменении кода.

### 12.3. Покрытие Кода (Code Coverage)

*   **Цель:** Поддержание высокого уровня покрытия кода тестами, особенно для критически важных частей системы.
*   **Инструменты:** `coverage.py` для измерения покрытия.
*   **Требование:** Минимум 80% покрытия для модулей `core/services`, `core/validators`, `ingestion/parsers`.
