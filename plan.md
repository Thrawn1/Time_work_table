# Архитектурный план проекта Time Tracker

Этот документ описывает архитектуру приложения, основанную на принципах Предметно-ориентированного проектирования (Domain-Driven Design, DDD) и Чистой Архитектуры. Цель — создать гибкую, масштабируемую и легко поддерживаемую систему.

## 1. Ключевые принципы

- **Разделение ответственностей (Separation of Concerns):** Код разделен на независимые слои, каждый со своей четкой задачей.
- **Низкая связанность (Loose Coupling):** Слои взаимодействуют друг с другом через абстрактные интерфейсы, а не конкретные реализации.
- **Высокая сплоченность (High Cohesion):** Код, относящийся к одной бизнес-задаче, сгруппирован вместе.
- **Зависимости направлены внутрь:** Внешние слои (инфраструктура, UI) зависят от внутреннего (домен), но не наоборот.

## 2. Структура директорий (`/src`)

Проект имеет плоскую структуру внутри `src` для упрощения импортов и навигации.

```
src/
├── application/      # 2. Слой Приложения (Use Cases)
├── domain/           # 1. Доменный слой (Бизнес-логика)
├── infrastructure/   # 3. Слой Инфраструктуры (Детали реализации)
└── presentation/     # 4. Слой Представления (UI, API)
```

---

## 3. Подробное описание слоев

### 3.1. Доменный слой (`/domain`)

Это ядро приложения. Он содержит всю бизнес-логику, правила и модели предметной области. Он не зависит ни от каких других слоев.

#### 3.1.1. Агрегаты (`/domain/aggregates`)

Агрегат — это кластер доменных объектов, который можно рассматривать как единое целое. Он защищает свои **инварианты** (бизнес-правила, которые всегда должны быть истинны).

- **`Employee` (Сотрудник)**
  - **Роль:** Мастер-запись о сотруднике.
  - **Содержит:** `EmployeeId`, `FullName` (ФИО), `SalaryRates` (ставки оплаты), `is_active` (статус).
  - **Правила:** Не хранит историю работы. Является источником правил расчета зарплаты (ставок).

- **`WorkPeriod` (Рабочий Период)**
  - **Роль:** Отвечает за учет рабочего времени сотрудника за определенный период (например, месяц).
  - **Содержит:** `EmployeeId` (ссылка), `period_start`, `period_end`, внутренний список `_work_days`.
  - **Правила:** Гарантирует, что отметки времени не выходят за рамки периода. Контролирует добавление и целостность рабочих дней (`WorkDay`) через публичные методы (`add_time_record`).

- **`Payroll` (Расчетный лист)**
  - **Роль:** Неизменяемый финансовый документ, "снимок" расчета зарплаты.
  - **Содержит:** `PayrollId`, `EmployeeId`, период, итоговые суммы и полный список компонентов (`PayrollComponent`), из которых сложился расчет.
  - **Правила:** Создается целиком и больше не меняется. Гарантирует целостность финансовых данных.

#### 3.1.2. Локальные сущности и Объекты-значения (`/domain/models`, `/domain/value_objects`)

- **Локальные сущности (`WorkDay`)**: Объекты с локальной идентичностью, управляемые агрегатом. `WorkDay` имеет смысл только внутри `WorkPeriod`.
- **Объекты-значения (Value Objects)**: Неизменяемые объекты, описывающие характеристику (`Money`, `FullName`, `TimeRecord`, `PayrollComponent`). У них нет ID, они равны, если равны их атрибуты.

#### 3.1.3. Доменные сервисы (`/domain/services`)

Содержат логику, которая не принадлежит ни одному агрегату, часто координируя взаимодействие между ними.

- **`SalaryCalculatorService`**: Принимает `Employee` и `WorkPeriod`, а также другие данные (премии), выполняет расчет и **возвращает новый агрегат `Payroll`**.
- **`WorkTimeCalculatorService`**: Принимает `WorkDay` и рассчитывает отработанное время, статус дня, переработки и т.д.

#### 3.1.4. Интерфейсы Репозиториев (`/domain/repositories`)

Абстрактные интерфейсы, определяющие, как домен получает и сохраняет агрегаты (`EmployeeRepository`, `WorkPeriodRepository`). Домен не знает, где хранятся данные (в БД, файлах или памяти).

### 3.2. Слой Приложения (`/application`)

- **Роль:** Оркестрация выполнения пользовательских сценариев (Use Cases). Не содержит бизнес-логики.
- **Пример (ProcessAttlogFileUseCase):**
  1. Получает команду (например, путь к файлу `.dat`).
  2. Вызывает парсер из слоя Инфраструктуры для получения "сырых" данных (меток времени).
  3. Использует Репозиторий для загрузки нужного агрегата `WorkPeriod` (или создает новый).
  4. Вызывает методы самого агрегата (`work_period.add_time_record(...)`) для обновления его состояния в соответствии с бизнес-правилами.
  5. Использует Репозиторий для сохранения измененного агрегата.

### 3.3. Слой Инфраструктуры (`/infrastructure`)

- **Роль:** Реализация интерфейсов, определенных в домене, и взаимодействие с внешним миром.
- **Компоненты:**
  - **`persistence`**: Конкретные реализации репозиториев (для PostgreSQL, SQLite, файловой системы).
  - **`file_parsers`**: Парсеры для `.dat`, `.csv` и других форматов. Преобразуют внешние данные в доменные объекты-значения.
  - **`notifications`**: Сервисы для отправки email, сообщений в Telegram и т.д.

### 3.4. Слой Представления (`/presentation`)

- **Роль:** Точка входа для пользователя или внешних систем.
- **Компоненты:**
  - **`cli`**: Команды и утилиты для интерфейса командной строки.
  - **`api`**: (На будущее) HTTP-эндпоинты для веб-интерфейса или интеграций.

2.  **Создание Use Case**: Реализовать в `/application/use_cases` сервис `ProcessAttlogFile`, который будет использовать парсер и репозиторий `WorkPeriodRepository` для обработки файла и обновления доменных агрегатов.
3.  **Реализация Репозиториев**: Создать начальные файловые реализации репозиториев в `/infrastructure/persistence/file_based`, которые будут сохранять и загружать агрегаты (например, в формате JSON или Pickle) для быстрой проверки работоспособности системы.
4.  **Развитие CLI**: Создать в `/presentation/cli` команду, которая будет запускать Use Case обработки файла.
5.  **Реализация Доменных Сервисов**: Написать логику для `WorkTimeCalculatorService` и `SalaryCalculatorService`.
