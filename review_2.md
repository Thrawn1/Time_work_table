## 4. Главные проблемы и недочёты (жёсткая часть)

### 4.1. Нет формальных контрактов сервисов и DTO

Ты много раз упоминаешь:

* `PayrollService`, `EmployeeService`, `TimeEntryService`, `SessionService`, `IngestionService`, которые живут в Application Layer и общаются с UI через DTO.

Но:

* Нигде **нет явного перечня методов** этих сервисов: сигнатур, входных/выходных типов.
* Нигде **не описаны DTO/модели**, которыми UI обменивается с Application: какие поля у `WorkSessionViewModel`, `PayrollPreview`, `EmployeeDetails`, какие nullable, какие вычисляемые.

Для архитектора это жирный минус:

* UI-разработчик (или ИИ-агент) будет сам придумывать структуры — и начнётся зоопарк.
* Тебе самому будет сложнее держать единый “контракт” между слоями.

👉 По-сеньорски здесь нужна отдельная глава вида: **“Публичные интерфейсы Application Layer”**, где в псевдо-Python/Type-hints перечислены:

* классы сервисов;
* их методы (с типами аргументов и возвращаемых DTO);
* сами DTO (минимальный набор).

Сейчас это самое большое белое пятно в документе.

---

### 4.2. Поведение системы при повторном импорте и изменениях после `confirmed` всё ещё не до конца жёсткое

Часть ты закрыл:

* Есть `import_batches` + дедуп по `raw_line_content`.
* Есть политика единственного `draft` на период/сотрудника и процесс корректировки через `corrected_payroll_id`.

Но остаются вопросы, которые не прописаны впрямую:

1. **Если после `confirmed` расчёта приходит новый лог за тот же период:**

   * Разрешено ли вообще импортировать?
   * Если да, то **обязаны** ли мы сразу гонять сценарий “Создать корректировку” или можно держать данные “неприменёнными”?

2. **Что именно запрещено/разрешено править после `confirmed` без запуска корректировки?**
   Ты даёшь корректировочный сценарий, но нет жесткого правила:
   “Любые изменения `time_entries / work_sessions / absences / payroll_bonuses` в периоде, по которому есть `confirmed` payroll, **должны** инициировать корректировку, а прямое редактирование запрещено”.

3. **Как ведёт себя агрегатор сессий при новых `time_entries`, если в этот день уже есть `completed`/`auto_generated` без `manual_edit`?**
   Ты явно описал только пропуск дней с `manual_edit`.

👉 Это не критическая дырка, но если смотреть именно как архитектор, я бы жёстко дописал:

* правила допустимых модификаций данных за “закрытые” периоды;
* поведение агрегации при повторном запуске после импорта свежих логов.

### 4.3. Автоисправления (`auto_generated`) описаны концептуально, но без границ

Ты вводишь Use Case “Автоматическая генерация данных” и статус `auto_generated`.

Но:

* Конкретные правила автоисправления приведены только в виде примера:
  “для сессии с одной меткой добавляет вторую через `standard_workday_hours`” — это пример, а не строгий алгоритм.
* Не описано:

  * ограничиваем ли мы вторую точку рамками дня (чтобы не улететь через полночь, что ты сам отдельно считаешь граничным случаем);
  * можно ли автоисправлением менять уже существующие `completed` сессии;
  * как фиксируются auto-изменения в UI (можно ли их откатить одним кликом).

Сейчас это выглядит как “магическая кнопка, которая что-то делает по не до конца определенным правилам”.

👉 Я бы:

* либо вынес автоисправления в отдельную мини-главу с чёткими правилами;
* либо прямо написал: “Автогенерация пока ограничена только кейсом `одна метка => достраиваем вторую до полноценного дня` и **никогда** не создаёт сессию через полночь”.
