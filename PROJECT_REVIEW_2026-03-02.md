## 2. Executive summary

Проект рабочий по базовому сценарию, но в текущем состоянии содержит несколько критичных технических рисков:

1. Небезопасная загрузка `pickle` с диска (возможность выполнения произвольного кода).
2. Ряд падений на валидных данных (отсутствие ставок для существующих сотрудников, отсутствие защит от `None`).
3. Красные тесты в ядре календарной логики после изменения производственного календаря.
4. Сильная связка бизнес-логики с интерактивным вводом и mutable-файлами данных, что делает поведение нестабильным и плохо тестируемым.

Также обнаружены ошибки в «классовой» ветке (`work_month.py`), которые дают неверные результаты и потенциально ломают функциональность при использовании этой ветки.

## 3. Подтвержденные findings (по убыванию критичности)

## 3.1 CRITICAL

### F-01: Небезопасная десериализация `pickle` из рабочей директории
**Где:**
- `main.py:30-33` (`temporary.pickle` читается через `pickle.load`)
- `analyze_data.py:298`, `analyze_data.py:337`, `analyze_data.py:357`, `analyze_data.py:377` (в этот файл пишутся данные)

**Проблема:**
- `pickle.load` выполняет десериализацию произвольных Python-объектов. Файл лежит в рабочем каталоге и не подписан/не валидируется.

**Риск:**
- При подмене `temporary.pickle` можно выполнить произвольный код при запуске приложения.

**Рекомендация:**
1. Убрать `pickle` для пользовательских/рабочих данных.
2. Перейти на JSON (в проекте уже есть `supporting_files/data_in_json.py`).
3. Если `pickle` остается временно: строгая валидация пути, прав, hash-подпись и ограничение источника файла.

## 3.2 HIGH

### F-02: Приложение запускается при импорте модуля
**Где:**
- `main.py:96` (`main()` вызывается без `if __name__ == "__main__":`)

**Проблема:**
- Любой импорт `main.py` запускает интерактивный поток и побочные эффекты.

**Риск:**
- Ломает переиспользование кода, мешает тестированию, усложняет сборку/интеграцию.

**Рекомендация:**
- Добавить guard:
  - `if __name__ == "__main__":`
  - `    main()`

### F-03: Падение при отсутствии данных за период или при ошибке чтения файла
**Где:**
- `main.py:40-41`
- `build_data_array.py:44-53`

**Проблема:**

**Подтверждение:**

**Риск:**

**Рекомендация:**
1. В `main.py` проверять `list_data is None` до вызова `build_data_array`.
2. В `build_data_array()` валидировать вход и бросать осмысленное исключение.

### F-04: Расчет зарплаты падает для существующих сотрудников без ставки
**Где:**
- `calculation_of_hours_and_wages.py:113` (`money_rate_all_employes[id]`)

**Рекомендация:**

### F-07: В `work_month.py` логика календаря некорректна
**Где:**
- `work_month.py:115`, `work_month.py:122` (`if line[1] == self.month`)
- `work_month.py:137-145` (мутация общего списка дней для всех сотрудников)

**Проблема 1:**
- Сравнение символа строки (`line[1]`) с `int` (`self.month`) всегда false.
- В итоге праздники/переносы фактически игнорируются.

**Проблема 2:**
- В `check_loss_days_in_work_month` один и тот же список "обязательных дней" мутируется по очереди для всех id.
- Итог для поздних сотрудников считается по уже "обрезанному" списку.

**Подтверждение:**
- Проверка показала одинаковые `loss_all_data_days` для разных id при разных входных данных.

**Риск:**
- Неверный расчет пропущенных дней в классовой ветке.

**Рекомендация:**
1. Парсить месяц корректно (`split('.')` -> int).
2. Для каждого сотрудника использовать копию эталонного списка.

### F-08: Качество текущего `data/1_attlog.dat` влияет на корректность результатов
**Где:**
- `data/1_attlog.dat:225` — выброс `2000-01-01 00:27:37` (id `7`)
- `data/1_attlog.dat` — 15 пар `(дата, id)` с одной отметкой (в основном id `7`)
- `data/1_attlog.dat:127`, `130`, `140` — три отметки у `(2026-02-16, id=11)`

**Проблема:**
- Входные данные содержат аномалии, а валидации входного потока нет.
- Алгоритм сжимает множественные отметки до min/max, промежуточные silently теряются.

**Риск:**
- Ложные недоработки/переработки, искажение отчетов.

**Рекомендация:**
1. Добавить этап валидатора входных событий (range дат, число отметок на день, сортировка/дубликаты).
2. Логировать и выносить "грязные" записи в отдельный отчет.

## 7. Резюме

Текущая версия может работать на части сценариев, но имеет:
- 1 критичный security-риск (`pickle`),
- несколько high-регрессий устойчивости (падения на валидных данных),
- красные тесты в календарном блоке,
- существенные пробелы в test coverage по критическим модулям.

Рекомендуется сначала закрыть блокеры из Шага 1, затем стабилизировать календарь и тестовую базу.
