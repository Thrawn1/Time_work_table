# Анализ проекта и рекомендации по улучшению

Дата: 5 сентября 2026 года.

## Главные выводы

В первую очередь следует исправить корректность начислений и защитить исходные данные и ручные исправления. Переписывание приложения, добавление GUI или переход на БД сейчас принесут меньше пользы, чем устранение ошибок в существующем расчетном потоке.

Наиболее существенные результаты проверки:

- Праздничные смены для ролей 1 и 4 не попадают в месячные начисления.
- Для роли 3 отпуск и прогул превращаются в обычный оплаченный рабочий день.
- Недоработка в будни удерживается с коэффициентом сверхурочных; даже положительное отработанное время может дать отрицательное начисление.
- Неполная смена в выходной оплачивается как полная, в том числе при единственной отметке.
- Сохраненная сессия может незаметно заменить указанные пользователем месяц и входной файл.
- Существующие 25 тестов проходят, но основные расчетные функции и построение отчетов ими не проверяются.

Приоритеты: **P1** - исправить до использования результатов для окончательного начисления зарплаты; **P2** - следующий этап надежности, безопасности и сопровождаемости; **P3** - удобство и оформление. Это инженерные приоритеты, не оценка соответствия трудовому законодательству.

## Область и методика

Исследована текущая рабочая копия, включая уже существовавшие незакоммиченные изменения. Ссылки на строки относятся к этому состоянию кода, а не к последнему коммиту. Исходники, настройки, рабочие данные и существующие изменения не редактировались; результат работы - только этот документ.

Проверены точка входа, модули `core`, обработчик ручного ввода времени, тесты, зависимости, сборочные PowerShell-скрипты и существующий план развития. Содержимое файла секретного ключа, персональных справочников сотрудников и ставок, рабочих БД, TOML и готовых отчетов не изучалось. Календарные справочники использовались штатными тестами без вывода их содержимого.

Полный существующий набор тестов запущен на Python 3.14:

```powershell
py -B -m pytest -q -p no:cacheprovider
```

Результат: **25 passed in 0.02s**. Команда `python` в текущем окружении ведет на неработающий Windows Store alias; доступный интерпретатор запускается через `py`.

Дополнительно выполнены изолированные проверки на синтетических сотрудниках, датах и ставках. Чтение/запись рабочих файлов и интерактивный ввод в этих проверках подменялись. Для проверки восстановления сессии вызван `main()` с подмененными конфигурацией, загрузкой состояния, генерацией файлов и удалением checkpoint. Обычный производственный запуск и сборка EXE не выполнялись; браузерная проверка HTML и открытие XLSX в Excel также не выполнялись.

В денежных примерах ниже используется условная **ставка 800**, которую текущая формула трактует как оплату восьмичасовой смены, и доплата за молоко 40. Это не реальные ставки сотрудников. Название поля `hourly_rate` не соответствует такой трактовке и требует уточнения.

## Подтвержденные проблемы P1

### 1. Праздничные смены теряются в расчетах и детализации

**Код:** [file_parser.py:81-84](../core/file_parser.py#L81-L84), [calculations.py:22-52](../core/calculations.py#L22-L52), [analysis.py:52-55](../core/analysis.py#L52-L55), [html_builder.py:112-119](../core/html_builder.py#L112-L119), [excel_builder.py:60-76](../core/excel_builder.py#L60-L76).

Календарь возвращает `holiday`, дневной расчет для ролей 1 и 4 сохраняет этот статус, но месячная агрегация знает только `work`, `weekend`, `vacation`, `truancy`. Поиск одиночных отметок и детализация отчетов также не поддерживают праздничную смену.

**Проверенный пример:** 1 января, роль 1, приход 08:00, уход 16:00. Дневной расчет содержит 8 часов; месячный итог содержит 0 рабочих и 0 выходных смен; начисление и молоко равны 0. В HTML вместо отметок выводится `holiday`, в Excel поля времени пусты. Одиночная праздничная отметка не предлагается к исправлению.

**Улучшение:** ввести явную обработку праздников во всей цепочке. До согласования коэффициента не выпускать окончательный расчет с молча отброшенным днем. Добавить сквозной тест от календарного статуса до часов, начисления и обоих отчетов.

### 2. Роль 3 теряет отпуск, прогул и категорию дня

**Код:** [calculations.py:30-33](../core/calculations.py#L30-L33), [calculations.py:105-108](../core/calculations.py#L105-L108), [analysis.py:160-168](../core/analysis.py#L160-L168).

Для любой записи сотрудника роли 3 возвращаются 8 часов и статус `work`, независимо от исходного статуса. При этом редактор разрешает вводить отпуск и прогул для этой роли.

**Проверенный пример:** `[dt, dt, 'truancy']` превращается в 1 рабочий день и начисление 800; количество прогулов становится нулевым. `vacation` аналогично перестает учитываться как отпуск. HTML-детализация может показывать исходный отпуск/прогул, тогда как месячные итоги считают рабочий день.

**Улучшение:** сначала обрабатывать статус дня, затем применять правила роли. Фиксированную длительность смены не использовать для подмены отсутствия работой. Отдельно закрепить правила оплаты отпуска и выходных для этой роли.

### 3. Недоработка удерживается по повышенной ставке

**Код:** [calculations.py:61-66](../core/calculations.py#L61-L66), [calculations.py:89-98](../core/calculations.py#L89-L98).

Отрицательная месячная переработка умножается на тот же коэффициент 1,5, что и положительная. При ставке 800 получается:

| Отработано в будний день | Начислено без молока |
| --- | ---: |
| 8 часов | 800 |
| 7 часов | 650 |
| 4 часа | 200 |
| 2 часа | -100 |

Последний результат следует из `800 + 1.5 * (800 / 8) * (2 - 8)`. Он воспроизводится на двух корректных отметках. Одиночная отметка дает нулевую длительность и начисление -400 без молока.

**Улучшение:** разделить фактически отработанное обычное время, недоработку и сверхурочные. Повышающий коэффициент применять только к соответствующей положительной величине. Правила удержаний и взаимозачета переработок между днями согласовать отдельно, а не выводить из знака `timedelta`.

### 4. Неполный выходной и одиночная отметка оплачиваются как полная смена

**Код:** [data_array.py:20-28](../core/data_array.py#L20-L28), [calculations.py:67-70](../core/calculations.py#L67-L70), [calculations.py:99-100](../core/calculations.py#L99-L100), [main.py:64-76](../main.py#L64-L76).

При агрегации выходных учитывается только положительная переработка, а недоработка отбрасывается. При этом каждая запись остается оплачиваемой сменой. Для первой отметки приход и уход намеренно заполняются одним временем, но такой незавершенный день не блокируется перед начислением.

**Проверенный пример:** в субботу 0, 2, 4, 7 и 8 часов дают одинаковые 1200 плюс 40 за молоко. Нулевая смена получается из одной отметки, которую можно оставить неисправленной при `--no-edit`.

**Улучшение:** хранить фактические часы и состояние полноты отметок; отделить проверку корректности от интерактивного редактирования. `--no-edit` должен пропускать диалог, но не контроль качества данных. Если бизнес гарантирует минимальную оплату за выход в выходной, оформить это отдельным явным правилом; одна отметка сама по себе не подтверждает отработанную смену.

### 5. Сотрудник без отметок за весь месяц исчезает из обработки

**Код:** [main.py:58-67](../main.py#L58-L67), [data_array.py:49-56](../core/data_array.py#L49-L56), [analysis.py:35-41](../core/analysis.py#L35-L41).

Участники расчета определяются только по ID, встретившимся в журнале. Если сотрудник есть в справочнике, но весь месяц отсутствовал, ему не предлагается внести отпуск или прогул и не создается отчет. Даже прямой вызов `search_missed_work_days` для такого сотрудника возвращает `0`.

**Проверенный пример:** в справочнике два сотрудника, отметки есть только у первого. Второй не попадает в список обработки; поиск пропусков для него сообщает об отсутствии проблем.

**Улучшение:** явно определять сотрудников расчетного периода с учетом приема, увольнения и исключений. Для активного сотрудника без отметок показывать отдельное предупреждение и позволять заполнить период. Не считать всех сотрудников исторического справочника автоматически работающими во все месяцы.

### 6. Сохраненная сессия подменяет параметры нового запуска

**Код:** [main.py:40-54](../main.py#L40-L54).

При наличии `temporary.pickle` программа без подтверждения загружает его, определяет период по первой дате и не читает новый входной файл. Аргументы `--year`, `--month`, `--file` при этом не определяют расчет.

**Проверенный пример:** запрошен июль 2026 года и `new.dat`, но checkpoint содержит июнь. Приложение использует июнь, число вызовов чтения нового источника равно 0.

**Улучшение:** сделать восстановление явным действием, например `--resume`; сохранять период, идентификатор/хеш источника и версию схемы. Проверять соответствие сессии параметрам запуска. Несовпадение должно приводить к понятному выбору пользователя или ошибке, а не к молчаливой подмене месяца.

### 7. Восстановление небезопасно, сохранение исправлений неатомарно

**Код:** [main.py:41-46](../main.py#L41-L46), [analysis.py:108-111](../core/analysis.py#L108-L111).

Здесь две отдельные проблемы:

- `pickle.load` может выполнить код из подмененного файла. Риск возникает при загрузке чужого или измененного checkpoint; сетевой путь атаки в проекте не обнаружен. Проверка содержимого после `load` не устраняет этот риск.
- Режим `wb` уничтожает предыдущую сохраненную версию до завершения новой записи. При сбое диска или прерывании процесса можно потерять ранее внесенные исправления. В изолированной проверке ошибки записи вместо полного checkpoint оставались частичные байты.

**Улучшение:** использовать неисполняемый формат с валидацией схемы, например JSON с ISO-датами. Записывать новое состояние во временный файл в том же каталоге и заменять основное через `os.replace` только после успешной записи; при ошибке сохранять предыдущую версию и явно сообщать о неуспехе. Предусмотреть контролируемый перенос уже существующих пользовательских сессий, но не автоматическое открытие произвольных старых pickle-файлов.

### 8. Ручной ввод может сохранить некорректные или выдуманные отметки

**Код:** [analysis.py:129-159](../core/analysis.py#L129-L159), [randomazer_time_value.py:13-70](../randomazer_time_value.py#L13-L70).

Проверенные сценарии:

- При сохраненном уходе 17:00 ввод прихода 18:00 подтверждается и сохраняется. Следующая проверка не находит ошибку, поскольку ищет только равенство отметок; расчет получает -1 час.
- Ввод времени, равного второй отметке, подтверждается, хотя смена остается незавершенной.
- `08 99 00` превращается в `08 17 00` при подмененном генераторе, возвращающем 17: ошибочные минуты не отклоняются, а заменяются случайными.
- `08 30 00 extra` отбрасывает все компоненты и запускает повторный ввод часа и случайное заполнение минут/секунд.
- `008 30 00` проходит числовую проверку, но вызывает `ValueError` при преобразовании в `datetime`.

**Улучшение:** разбирать ввод в числа, проверять диапазоны и нормализовать формат; проверять согласованность прихода и ухода до изменения данных. Ошибочный ввод отклонять с повторным запросом. Для ночных смен нужен отдельный явно поддержанный сценарий с датой ухода.

Случайное заполнение именно отсутствующих компонентов уже предусмотрено [планом проекта](plan), поэтому его наличие не объявляется само по себе ошибкой. Однако следует отличать отсутствие от опечатки, показывать итог перед подтверждением и отмечать происхождение восстановленного времени, чтобы оно не выглядело как исходное показание терминала.

## Подтвержденные проблемы P2

### 9. Некорректный импорт и неподдерживаемые роли не имеют безопасного завершения

**Код:** [file_parser.py:11-35](../core/file_parser.py#L11-L35), [data_array.py:15-17](../core/data_array.py#L15-L17), [calculations.py:19-33](../core/calculations.py#L19-L33), [html_builder.py:49-60](../core/html_builder.py#L49-L60), [excel_builder.py:15-20](../core/excel_builder.py#L15-L20), [main.py:48-54](../main.py#L48-L54).

Парсер молча пропускает строки, не соответствующие шаблону, но синтаксически подходящая строка с невозможной датой, например `2026-02-30`, вызывает необработанный `ValueError`. Неизвестные ID пропускаются с сообщением; если неизвестны все ID, исходный список непустой, но итоговая таблица пустая, и Excel-построитель падает с `IndexError`.

Для роли 2 дневной расчет не создает запись, месячный итог пуст, а построение HTML-итогов вызывает `KeyError`. Это проверено на синтетических данных; наличие сотрудников этой роли в рабочих справочниках не проверялось. Поддержка ролей 0 и 2 уже отмечена как незавершенная в [плане](plan).

**Улучшение:** до генерации файлов проверять период, справочники, поддерживаемые роли, непустой результат импорта и согласованность таблиц. Возвращать диагностику с номером строки и причиной отклонения; выводить количество прочитанных, принятых и отклоненных записей. Отсутствующие ставки и неизвестные роли не превращать в молчаливое нулевое начисление. Диапазон месяца задавать в `argparse`, год проверять до обращения к календарю.

### 10. Имена файлов HTML неуникальны и не ограничены каталогом отчетов

**Код:** [html_builder.py:9-15](../core/html_builder.py#L9-L15), [html_builder.py:84-85](../core/html_builder.py#L84-L85).

Имя файла строится только из ФИО и периода. Два сотрудника с одинаковыми именем и фамилией получают один путь; второй файл перезаписывает первый. Значение фамилии `../outside` формирует путь за пределами текущего каталога. Последнее - риск при недоверенном или ошибочно заполненном справочнике, а не утверждение о реальных ФИО.

**Улучшение:** включить ID сотрудника, очищать недопустимые символы и компоненты пути, проверять принадлежность итогового пути выделенному каталогу. Перезапись существующих отчетов сделать явной политикой. Проверять коллизии до записи первого файла.

### 11. Текст в отчетах может интерпретироваться как разметка или формула

**Код:** [html_builder.py:107-134](../core/html_builder.py#L107-L134), [excel_builder.py:56](../core/excel_builder.py#L56), [excel_builder.py:96](../core/excel_builder.py#L96).

Динамические значения вставляются в HTML без экранирования. На уровне рендерера синтетическое имя с `<script>` остается настоящим тегом. Полная эксплуатация через CLI на Windows не подтверждена: эти символы одновременно недопустимы в используемом имени HTML-файла.

В Excel синтетическое имя `=1+1` становится формулой: `openpyxl` присваивает ячейке тип `f`. Проверка проведена на ячейках в памяти, не запуском формулы в Excel.

**Улучшение:** применять `html.escape` ко всем динамическим текстовым значениям и записывать внешние текстовые поля XLSX явно как строки. Добавить регрессии на спецсимволы, амперсанд и ведущий `=`. Отдельная библиотека шаблонов для этого не обязательна.

### 12. Недоработка неправильно отображается, фильтр Excel обрезан

**Код:** [calculations.py:6-11](../core/calculations.py#L6-L11), [html_builder.py:54-56](../core/html_builder.py#L54-L56), [excel_builder.py:15](../core/excel_builder.py#L15).

`str_timedelta` форматирует отрицательные величины через округление часов вниз: -30 минут становятся `-1:30:00`, а -1 час 30 минут - `-2:30:00`. Это искажает HTML и консольные итоги, но непосредственно не меняет зарплату, которая считается через `total_seconds()`.

Фильтр Excel всегда равен `A1:G24`. Если записей больше 23, оставшаяся детализация не участвует в фильтрации: при выборе сотрудника хвост таблицы остается видимым.

**Улучшение:** отдельно извлекать знак длительности и форматировать ее абсолютное значение. Границу фильтра определять по последней строке детализации, не по константе и не по концу блока итогов.

### 13. Секрет сохраняется открытым текстом, режим без зарплаты неоднозначен

**Код:** [main.py:23-38](../main.py#L23-L38), [config.py:87-100](../core/config.py#L87-L100), [config.py:114-124](../core/config.py#L114-L124), [calculations.py:96-104](../core/calculations.py#L96-L104), [.gitignore](../.gitignore).

Ключ записывается в `_secret_key.tmp` и остается после завершения приложения. На момент проверки файл виден как untracked и не исключен из Git. Его содержимое не читалось. Передача ключа через `-k` также может оставлять его в истории команд и аргументах процесса.

Перестановка частей десятичной записи и умножение на ключ - обратимое преобразование, а не криптографическая защита ставок. Кроме того, некорректный ключ молча превращается в ноль. При `t`/нулевом ключе приложение продолжает формировать денежные поля: для одной смены роли 1 получено `(0.0, 40, 40.0)` за счет молока, хотя CLI описывает `t` как режим без зарплаты.

**Улучшение:** хранить ключ в памяти на время запуска, при интерактивном вводе использовать `getpass`; не считать текущее преобразование шифрованием. ### 2. Исправление P1 #3: Недоработка удерживается по повышенной ставке

**Проблема:** Отрицательная месячная переработка умножалась на коэффициент 1.5, как и положительная. При ставке 800 и 2-часовой смене получалось:

```
calculate_hours_per_day:  worked=2h, delta=-6h, abs_delta=6h, tag='недоработка'
calculate_hours_per_month: overwork_weekday = 0 - 6h = -6h
calculate_wages: 800*1 + 1.5*(800/28800)*(-21600) = 800 - 900 = -100
```

Зарплата становилась отрицательной. Это нарушение здравого смысла: за отработанные 2 часа работник должен получить что-то, а не потерять.

**Корневая причина:** В `calculate_hours_per_month` недоработка вычиталась из того же `overwork_weekday`, в который шла переработка. Затем в `calculate_wages` toute сумма умножалась на 1.5. Не было разделения на «сверхурочные» (с коэффициентом) и «недоработку» (без коэффициента).

**Решение:** Разделить `overwork_weekday` на две независимые величины:

- `overtime_weekday` — суммарная положительная переработка (только для `tag == 'переработка'`)
- `undertime_weekday` — суммарная недоработка (только для `tag == 'недоработка'`)

В `calculate_wages`:
- Коэффициент 1.5 применяется только к `overtime_weekday`
- `undertime_weekday` вычитается по обычной ставке `rate_per_second`

**Результат:**
```
2-часовая смена (ставка 800):
  overtime = 0, undertime = 6h
  зарплата = 800 - (800/28800) * 21600 = 200  ← положительная
```

**Сопутствующие изменения:**
- Формат кортежа summary изменён с `(total_work, overwork_weekday)` на `(total_work, overtime_weekday, undertime_weekday)`
- `html_builder.py`: добавлена колонка «Недоработка в будние дни» в итоговую таблицу
- `excel_builder.py`: добавлена колонка «Недоработка», сдвинуты колонки зарплаты/молока/итога
- Тесты обновлены: старый тест `test_role1_negative_overtime_gives_negative_salary` заменён на `test_role1_undertime_reduces_salary_correctly`, который проверяет положительную зарплату при недоработке

**Что НЕ изменено (оставлено на后续):**
- Правила взаимозачёта переработок между днями — требуют бизнес-решения
- Ночные смены — требуют отдельной модели
- Округление промежуточных сумм — не определено

### 3. Исправление P1 #1: Праздничные смены теряются в расчетах

**Проблема:** Календарь возвращал `holiday`, дневной расчет сохранял этот статус, но месячная агрегация знала только `work`, `weekend`, `vacation`, `truancy`. Праздничные дни молча отбрасывались — нулевые часы, нулевое начисление.

**Корневая причина:** В `calculate_hours_per_month` не было ветки для тега `holiday`.

**Решение:** Однострочное изменение в `calculations.py:53`:
```python
# Было:
elif tag_day == 'weekend':
# Стало:
elif tag_day in ('weekend', 'holiday'):
```

Праздники теперь считаются как выходные: 1.5x ставка + молоко.

### 4. Исправление P1 #2: Роль 3 теряет отпуск, прогул и категорию дня

**Проблема:** Для роли 3 (окладник) `calculate_hours_per_day` всегда возвращала `(0, 8h, '', 'work')` независимо от тега. Отпуск и прогул превращались в обычный рабочий день.

**Решение:** Перед возвратом проверять исходный тег:
```python
elif emp.role_id == 3:
    tag_day = marks[2]
    if tag_day in ('vacation', 'truancy'):
        result[date_key][emp_id] = (timedelta(0), timedelta(0), '', tag_day)
    else:
        result[date_key][emp_id] = (timedelta(0), timedelta(hours=8), '', 'work')
```

Отпуск/прогул сохраняют статус и считаются отдельно в месячном итоге.

### 5. Исправление P1 #4: Неполный выходной оплачивается как полная смена

**Проблема:** Каждая выходная смена оплачивалась как `1.5 * rate * count`, где `count` — количество смен. 0-часовая смена (одна отметка) и 2-часовая смена оплачивались одинаково: 1200 при ставке 800.

**Решение:** Три изменения:
1. **Хранение:** Выходные ячейки теперь `(delta, tag, worked, date_key)` — хранят фактическое время
2. **Агрегация:** Добавлены `undertime_weekend` и `total_worked_weekend`
3. **Зарплата:** `1.5 * rate_per_second * worked_seconds` вместо `1.5 * rate * count`

**Результат:**
```
0-часовая смена: 0.0 (было 1200)
2-часовая смена: 300.0 (было 1200)
8-часовая смена: 1200.0 (без изменений)
```

### 6. Исправление P1 #5: Сотрудник без отметок исчезает из обработки

**Проблема:** `get_all_employees_in_data` возвращала только ID из time_table. Сотрудник из справочника без ни одной отметки за месяц не попадал в обработку — ни отпуск, ни прогул не предлагались.

**Решение:** Два изменения:
1. `data_array.py`: `get_all_employees_in_data` возвращает `list(EMPLOYEES.keys())` — всех из справочника
2. `analysis.py`: `search_missed_work_days` возвращает все рабочие дни месяца для сотрудника без отметок (вместо 0)

### 7. Исправление P1 #6: Сессия подменяет параметры нового запуска

**Проблема:** При наличии `temporary.pickle` программа без подтверждения загружала его и игнорировала `--year`, `--month`, `--file`.

**Решение:** Добавлен флаг `--resume`. Без него pickle/json игнорируется с предупреждением.

### 8. Исправление P1 #7: pickle-безопасность и атомарность записи

**Проблема:**
- `pickle.load` может выполнить произвольный код из подмененного файла
- Запись `wb` уничтожает предыдущую версию до завершения новой — при сбое можно потерять данные

**Решение:** Новый модуль `core/session.py`:
- **Формат:** JSON с валидацией схемы (версия, типы полей, ISO-даты)
- **Атомарность:** Запись через `tempfile.mkstemp` + `os.replace` — предыдущий файл остаётся до успешной замены
- **Совместимость:** Старые pickle-файлы отвергаются с предупреждением
- **Диагностика:** Ошибки формата, несовпадение версий, поврежденные отметки — все пропускаются с сообщением

**Формат файла:**
```json
{
  "version": 1,
  "entries": {
    "2026-07-06": {
      "101": ["2026-07-06T16:00:00", "2026-07-06T08:00:00", "work"]
    }
  }
}
```

**Тесты:** 13 новых тестов в `tests/test_session.py`: round-trip, атомарность, валидация JSON, отклонение pickle, обработка поврежденных данных.
