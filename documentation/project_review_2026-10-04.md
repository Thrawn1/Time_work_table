# Ревью проекта — 4 октября 2026 года

## Итог

Код не менялся с ревью 2026-10-01: HEAD тот же (`fa4a3e0`), в рабочем дереве
только неотслеживаемый файл того ревью. Поэтому это ревью — **независимая
перепроверка** прошлого плюс то, чего в нём не было.

Расчётное ядро по-прежнему в порядке: формулы §4 и примеры §8 спецификации
сходятся, деньги на `Decimal`/`HALF_UP`, SQL параметризован, HTML экранируется.
Слабые места — на границах: что считается «настройкой» и что происходит, когда
настройка неверна или отсутствует.

Главное из нового: **опечатка в `--pay-dir` молча переключает месяц 2026+ на
старую модель** — другая зарплата, код возврата 0 (находка 1). Главное из
подтверждённого: коэффициент переработки без диапазона (находка 3) и две
независимые матрицы ролей (находка 5).

Из 26 пунктов ревью 10-01 все перечитаны по коду, шесть воспроизведены запуском,
в четырёх формулировки завышены (раздел «Поправки к ревью 10-01»).

Приоритеты: **P1** — неверные деньги без предупреждения, трейсбек вместо
ошибки; **P2** — расхождение со спецификацией, неверный вывод, ложные срабатывания
контроля; **P3** — гигиена и документация.

## P1

### 1. P1 — опечатка в `--pay-dir` (или пропавший файл БД) молча включает legacy

**Код:** [core/payroll.py:107–108](../core/payroll.py#L107-L108),
[core/pay_context.py:151](../core/pay_context.py#L151),
[core/pay_context.py:283](../core/pay_context.py#L283),
[main.py:81](../main.py#L81).

`new_regime_available()` возвращает `None`, если файла нет, и период считается
по legacy. Спецификация (§6) и README («ошибка настройки новой модели
фатальна, без fallback») требуют обратного, но исключение сделано именно для
самого частого сбоя — неверного пути.

**Воспроизведено** (июль 2026, один сотрудник, 23 будних дня по 8 ч, `-k 10000`,
в каталоге данных есть `wage_rates.dat`):

| Запуск | Режим | Итого |
|---|---|---|
| штатный `--pay-dir` | новая модель | 65 920,00 ₽ |
| `--pay-dir …\pay_directry.db` (опечатка) | legacy | 19 320,00 ₽ (при ставке 800 ₽/смена) |

Код возврата 0 в обоих случаях; единственный сигнал — строка «Режим модели:
legacy (действующих SQLite-условий на месяц нет)». Цифры legacy зависят от
синтетической ставки — важен сам переход. Если `wage_rates.dat` нет, запуск
упадёт громко; тихий вариант возможен именно в боевой конфигурации, где ставки
legacy лежат рядом.

**Исправление:** явно переданный `--pay-dir`, которого нет, — ошибка; для пути по
умолчанию и периода не раньше `DEFAULT_TRANSITION` отсутствие БД — тоже ошибка,
если legacy не запрошен отдельным флагом (`--legacy`). Печать выбранного режима
вынести в стартовый экран.

### 2. P1 — `pay_cli`: `sqlite3.Error` — трейсбек, а «просмотр» создаёт файл и ломает основной запуск

**Код:** [core/pay_cli.py:91–98](../core/pay_cli.py#L91-L98),
[core/pay_store.py:116–118](../core/pay_store.py#L116-L118).

Подтверждено запуском: `show`, `rules-history`, `export` на несуществующем пути
`--db` падают `OperationalError: no such table` **и оставляют на диске пустой
файл (0 байт)**. Это сильнее, чем «побочно» в ревью 10-01: после такого вызова
(например, `show` до `init` при пути по умолчанию `data/pay_directory.db`)
`new_regime_available()` видит существующий файл без таблиц и бросает `PayrollError` — основной запуск за любой
месяц 2026+ завершается кодом 1, пока файл не удалят вручную. Тихий legacy из
находки 1 при этом уже не включается.

**Исправление:** read-only команды открывают БД через `file:…?mode=ro` (или
проверяют `exists()` до `connect`); `except sqlite3.Error` в `main()` →
«справочник недоступен», код 1.

### 3. P1 — коэффициент переработки и норма смены без проверки диапазона

**Код:** [core/pay_toml.py:344–346](../core/pay_toml.py#L344-L346),
[core/pay_store.py:235–236](../core/pay_store.py#L235-L236),
[core/pay_validate.py:104–119](../core/pay_validate.py#L104-L119).

Подтверждено через `import_toml(..., dry_run=True)`: без ошибок принимаются
`overtime_coef = "15"`, `"1E+1000"`, `"0.0001"` и `shift_norm_hours = "0.001"`,
`"1E+30"`. Следствия:

- `"15"` вместо `"1.5"`: переработка 10 ч при D=20 — **56 250,00 вместо 5 625,00**;
- `"1E+1000"` проходит импорт, а `calculate_pay` падает
  `decimal.InvalidOperation` ([core/pay_calc.py:132](../core/pay_calc.py#L132));
  `build_bundle` его не ловит — трейсбек посреди расчёта;
- `shift_norm_hours = 0.001` превращает каждый отработанный час в переработку;
  `1E+30` (и `1E+1000`, где `float()` даёт `inf`) падает `OverflowError` в
  `timedelta(hours=…)` ([core/calculations.py:202](../core/calculations.py#L202)) —
  проверено, и его тоже никто не ловит.

Docstring `pay_toml.py:7` обещает «диапазоны сумм/коэффициентов/норм».

**Исправление:** в `pay_validate` — `0 < overtime_coef ≤ 3`, `0 < shift_norm ≤ 24`
(границы уточнить у владельца), одинаково для TOML и `set_role_rule`.

### 4. P1 — `--resume` и интерактивные правки не защищены от `OSError`/`EOFError`

**Код:** [core/session.py:333–338](../core/session.py#L333-L338),
[main.py:382–386](../main.py#L382-L386),
[core/analysis.py:230](../core/analysis.py#L230),
[core/analysis.py:412–417](../core/analysis.py#L412-L417).

- `load_session` ловит `JSONDecodeError`/`UnicodeDecodeError`, но не `OSError`:
  на Windows файл сессии, занятый антивирусом/OneDrive, даёт трейсбек вместо
  «сессия не читается» (соседний `load_session_with_journal` `OSError` ловит).
- `_read_valid_time` вызывает `input()` напрямую — закрытый stdin = `EOFError`
  (в `ui.ask_menu` этот случай обработан, здесь нет). Цикл `analyze_for_edit`
  в `main` не обёрнут, `save_session` может бросить `PermissionError`.

Уточнение к 10-01: рассинхрон «журнал откатили, отметки остались»
([core/analysis.py:414–417](../core/analysis.py#L414-L417)) последствий не
имеет — исключение пробрасывается и процесс завершается, память теряется, на диске
остаётся последний атомарный снимок. Дефект один: трейсбек вместо понятного
сообщения «сессия оставлена для `--resume`».

**Исправление:** `OSError` в `load_session`; общий `try` вокруг блока правок с
`sys.exit(1)`; `EOFError` в `_read_valid_time` трактовать как отмену.

## P2

### 5. P2 — две матрицы ролей: роль, известная только SQLite, не оплачивается

**Код:** [main.py:287–289](../main.py#L287-L289),
[core/data_array.py:90–120](../core/data_array.py#L90-L120),
[core/roles.py:62–75](../core/roles.py#L62-L75).

Подтверждено запуском: в SQLite заведена роль 9 с `participates=true`,
сотрудник назначен на неё. Результат: «Сотрудников в расчёте: 0», в дашборде
«Исключены из начислений: Тестов Тест (неизвестная роль 9)», пустые отчёты,
**код возврата 0**. Причина — `exclusion_reason` сверяется с DAT-матрицей
`DEFAULT_RULES` ещё до того, как `build_bundle` дойдёт до SQLite-правил. Это
противоречит §7 («SQLite — авторитет роли в new-режиме») и делает невозможным
добавление роли только через справочник — ради чего он и создавался.

Обратный случай (роль 0/4 с `participates=1` в БД) попадает в ведомость, но
`settlement_ids` его отсекает — состав различается между консолью и пакетом.

**Исправление:** в new-режиме решать участие по `rules_by_role`;
`exclusion_reason` принимает правила, DAT-матрица остаётся только для legacy.
Пустой состав при непустом файле отметок — ошибка, а не код 0.

### 6. P2 — одиночная отметка определяется точным равенством `go == come`

**Код:** [core/analysis.py:130](../core/analysis.py#L130).

Две отметки с разницей в секунды (двойное касание терминала) не считаются
одиночными. Воспроизведено: `08:00:00` и `08:00:07` без отметки ухода →
`worked = 0:00:07`, `delta = 7:59:53`, тег «недоработка», **предупреждения и
запроса на правку нет**; сумма уходит в недоработку, бонус полного месяца
блокируется по `fact < norm`. Настоящая одиночная отметка при этом проверялась
бы и предлагалась к правке.

Насколько это реально, зависит от настройки терминала (интервал подавления
повторов); приложение на это не полагается и порога не имеет.

**Исправление:** объединять отметки ближе порога (параметр, ориентир 1–5 мин)
при сборке `time_table`; порог — решение владельца.

### 7. P2 — аудит mid-month мёртв, `migrate --from` его нарушает (подтверждено)

**Код:** [core/payroll.py:250–258](../core/payroll.py#L250-L258),
[core/pay_store.py:678](../core/pay_store.py#L678).

`find_midmonth_violations` вызывается ровно один раз, результат копируется в
`_relevant`, который не читается; тестов у функции нет. Воспроизведено:
`migrate_from_dat(..., '2026-01-15')` проходит и создаёт назначение с середины
месяца, а аудит затем сообщает
`assignments.effective_from[1@2026-01-15] … дата не на границе месяца`
(запрещено §6; все остальные писатели требуют `require_month_start`).
Спецификация §11 при этом называет F06 «исправлено: отказ + аудит БД».

**Исправление:** `require_month_start(_check_date(...))` в `migrate_from_dat`;
использовать результат аудита с фильтром по периоду или удалить мёртвый код и
поправить §11.

### 8. P2 — день ровно с нормой подписан «недоработка» (подтверждено)

### 10. P2 — `--resume` не сверяет `salary_mode`

**Код:** запись — [main.py:339](../main.py#L339); чтения нет нигде.

Контекст сессии хранит `salary_mode`, но при возобновлении сверяются только

не останавливается.

**Исправление:** при расхождении — отказ с подсказкой, как для `db_path` и
календаря.

### 11. P3 — первая строка DAT-файла с BOM теряется

**Код:** [core/file_parser.py:37](../core/file_parser.py#L37).

### 13. P3 — ручной ввод времени подставляет случайные минуты/секунды

**Код:** [randomazer_time_value.py:75–88](../randomazer_time_value.py#L75-L88),

«внесено вручную» в отчётах.
