# Ревью проекта — 21 сентября 2026 года

обработки ошибок при чтении справочников**. Расчётное ядро в порядке: деньги

и не перезаписываются молча, сессия пишется атомарно и строго валидируется при
восстановлении. Ошибки не в формулах, а вокруг них.

Проверена рабочая копия ветки `refactor-named-day-structures` на коммите `238f9a3`
(`chore: reproducible build (allowlist, fail-fast), requirements-dev, README, gitignore`).

(`core/cli.py`, `core/payroll_service.py`) и три новых набора тестов.

Приоритеты:

## Подтверждённые проблемы

### 1. P1 — секретный ключ остаётся в каталоге результатов

**Код:** [core/config.py:185–187](../core/config.py#L185-L187),
[core/config.py:177–182](../core/config.py#L177-L182),
[main.py:37](../main.py#L37), [main.py:49](../main.py#L49).

`set_secret_key()` пишет ключ в файл, `main.py` кладёт этот файл в `--output-dir` —
туда же, где формируются Excel и HTML. Никто его не удаляет: `remove_session()`
в конце расчёта трогает только файлы сессии.

**Сценарий:** после успешного запуска каталог результатов содержит

```
result/_secret_key.tmp   ->   123.45
result/Июль_2026.xlsx
result/Иванов Иван_1_07_2026.html
```

То есть каталог, который пользователь архивирует и передаёт дальше, содержит ключ
расшифровки всех ставок. При падении расчёта (проблема 4) файл тоже остаётся.

Файл при этом служит каналом передачи значения между двумя функциями **одного
процесса**: `set_secret_key()` пишет, `load_wage_rates()` читает через
`_get_secret_key()`. Диск в этой цепочке не нужен.

**Исправление:** передавать ключ параметром — `load_wage_rates(key: Decimal)`.
Вызов ровно один, в [core/payroll_service.py:42](../core/payroll_service.py#L42);
`SECRET_FILE`, `set_secret_file()` и `_get_secret_key()` после этого удаляются.
Если файл по какой-то причине нужен — писать во временный каталог и удалять
в `finally`, но не в `--output-dir`.

### 2. P1 — «шифрование» ставок держится только на секретности ключа

**Код:** [core/config.py:144–164](../core/config.py#L144-L164).

`wage_rates.dat` хранит значение `S`, реальная ставка получается как `R = S * key`.
Это обфускация, а не шифрование: тот, кто знает оклад **одного** сотрудника,
вычисляет `key = R / S` и раскрывает все остальные ставки. При этом сам файл
отслеживается в git (проблема 3), а ключ лежит рядом с отчётами (проблема 1).

**Исправление:** отдельной задачи на криптографию не требуется — требуется
перестать считать файл защищённым и обращаться с ним как с секретом.

### 3. P1 — персональные данные и ставки в репозитории

**Код:** [.gitignore](../.gitignore).

В git отслеживаются `data/variable_data_for_app/wage_rates.dat` (ставки),
`id_employee.dat` (реальные ФИО), `company_data_real.toml`, `company.db`,
`line.db` (1.4 МБ), `line_new.db` (770 КБ), `2_attlog.dat` (776 КБ реальных
отметок). Каталог `.git` — 12 МБ, преимущественно за счёт этих данных.

`.gitignore` аккуратно закрывает `result/`, `*.pickle`, `_secret_key.tmp`,
`data/pay_directory.db` — но исходные справочники с ФИО и ставками не закрыты.

**Исправление:** вынести боевые справочники из репозитория, оставив
`*.dat.example` с синтетическими данными; тесты уже работают на `tmp_path` и от
боевых файлов не зависят. Чистка истории (`git filter-repo`) — отдельная
операция; если репозиторий куда-то публиковался, ставки следует считать
раскрытыми.

### 4. P1 — отсутствие `wage_rates.dat` роняет запуск трейсбеком

**Код:** [core/config.py:153](../core/config.py#L153),
[core/payroll_service.py:42](../core/payroll_service.py#L42).

**Сценарий:** запуск с ключом в legacy-режиме при отсутствующем файле ставок
падает **после** проверки, дашборда и (без `--no-edit`) после всех интерактивных
правок:

```
File "core\config.py", line 153, in load_wage_rates
    with open(WAGE_RATES_FILE, 'r', encoding='utf-8') as f:
FileNotFoundError: ...\variable_data_for_app\wage_rates.dat
```

Воспроизведено запуском приложения на синтетических данных.

`payroll_service` уже умеет выдавать вежливую диагностику про нулевые ставки
([core/payroll_service.py:44–48](../core/payroll_service.py#L44-L48)), но только
когда файл существует. Комментарий в
[tests/test_app_flow.py:64](../tests/test_app_flow.py#L64) подтверждает, что
покрыт лишь режим учёта без зарплаты, где ставки не читаются; сценарий
«зарплата без файла ставок» не проверяется.

**Исправление:** ловить `FileNotFoundError` рядом с `PayrollError` и
`sqlite3.Error`, проверять доступность справочника **до** анализа и правок,
завершаться с понятным сообщением.

### 5. P1 — загрузка справочников без обработки ошибок

**Код:** [core/config.py:105–116](../core/config.py#L105-L116),
[core/config.py:119–141](../core/config.py#L119-L141),
[core/config.py:144–164](../core/config.py#L144-L164),
[core/config.py:167–174](../core/config.py#L167-L174).

`_load_roles`, `_load_employees`, `load_wage_rates` и
`_load_settlement_exceptions` выполняют `int(parts[0])`, `parts[1].strip('[]')`,
`rate_parts[1] + '.' + rate_parts[0]` без защиты. Лишняя скобка, непарный
разделитель, случайный BOM или пустая строка с пробелом дают `IndexError` или
`ValueError` с трейсбеком вместо указания на файл и строку.

Контраст с импортом DAT заметный: `read_file_data_with_errors`
([core/file_parser.py:44–67](../core/file_parser.py#L44-L67)) выдаёт номер строки,
причину, лимит вывода и продолжает расчёт. Справочники правятся руками чаще,
чем DAT, и заслуживают той же диагностики.

Побочно: `parts = line.split()` в `_load_employees` молча теряет составные
фамилии — «Салтыков Щедрин Иван» разбирается как фамилия `Салтыков`, имя `Щедрин`.

### 6. P2 — производственный календарь не учитывает год

**Код:** [core/file_parser.py:85–98](../core/file_parser.py#L85-L98),
[core/pay_calendar.py:30–40](../core/pay_calendar.py#L30-L40),
[core/analysis.py:25–40](../core/analysis.py#L25-L40).

`holidays.dat` и `postponed_working_days.dat` хранят даты в формате `ДД.ММ`,
год подставляется расчётный. Набор один на все годы, причём
`postponed_working_days.dat` содержит **одну** запись (`01.11`).

`working_days_in_month` на боевом календаре, месяцы 1–12:

```
2024  14 20 21 22 22 19 23 22 21 23 20 21
2025  15 20 21 22 21 20 23 21 22 23 20 22
2026  15 19 21 22 19 21 23 21 22 22 21 22
```

Январь 2024 и 2025 по производственному календарю РФ — 17 рабочих дней,
здесь 14 и 15. Расхождение молчаливое, предупреждения нет.

Для новой модели риск ограничен датой перехода 2026-01
([core/pay_store.py:30](../core/pay_store.py#L30)), но `D` попадает прямо в
знаменатель `R_day = M / D` ([core/pay_calc.py:83](../core/pay_calc.py#L83)).
`generation_of_lists_of_days` использует тот же календарь **для любого года**,
поэтому анализ пропусков за 2024–2025 показывает несуществующие рабочие дни.

**Исправление:** формат `ДД.ММ.ГГГГ` или отдельный файл на год, плюс явная
ошибка при отсутствии календаря на расчётный год вместо подстановки чужого.
Это же закрывает пункт «воспроизводимость новой ведомости» из
`refactoring_2026-09-15.md`: в `versions_snapshot()` сейчас сохраняется только
число `D`, без дат праздников и переносов.

### 7. P2 — HTML-отчёты невалидны и без объявления кодировки

**Код:** [core/html_builder.py:114–138](../core/html_builder.py#L114-L138).

`_write_html_file()` оборачивает генераторы строк во внешний `<tr>`, а те
возвращают собственные `<tr>`. В сгенерированном файле:

```html
    <tbody>
      <tr>
        <tr>
          <td>Иванов Иван</td>
```

Кроме того, отсутствуют `<!DOCTYPE html>`, `<head>` и `<meta charset="utf-8">`.
Файл пишется в UTF-8, но при открытии с диска в русской локали браузер вправе
выбрать cp1251 и показать нечитаемый текст.

Проблема уже отмечена в `refactoring_2026-09-15.md` как нерешённая; настоящее
ревью фиксирует, что она в силе.

### 8. P2 — переход на явные `employees` выполнен наполовину

`main.py` последовательно передаёт `_STAFF` через все этапы, но пять мест по пути

Ещё симптом — `import core.data_array as _self` и `getattr(_self, 'EMPLOYEES', None)`

к `EMPLOYEES` было бы достаточно. Здесь форма кода продиктована тестом.

Это развитие пункта «единый источник правил новой модели» из
`refactoring_2026-09-15.md` с указанием конкретных мест обрыва.

### 9. P2 — 65 обращений вида `getattr(x, 'field', x[N])`

**Код:** [core/calculations.py:33–134](../core/calculations.py#L33-L134),
[core/day_models.py](../core/day_models.py), `excel_builder`, `html_builder`, `ui`.

Распределение: `excel_builder` — 17, `html_builder` — 17, `calculations` — 11
(плюс десять функций-адаптеров `_mark_go`, `_sum_work` и прочих), `ui` — 10.

Каждое такое обращение вычисляет `x[N]` **всегда**, даже когда поле присутствует:
Python считает аргументы до вызова `getattr`. На `DayWork` отрабатывают и
`__getattr__`, и `__getitem__`. Плюс `core/day_models.py` содержит около 200 строк
`__len__` / `__iter__` / `__getitem__` / `__eq__`, существующих только ради
совместимости с позиционным доступом.

**Исправление** (дополняет пункт «закончить переход к именованным моделям»):
нормализовать структуры в `DayMark` / `DayWork` на границе входа — `build_data_array`
и `load_session` уже создают датаклассы, — затем снимать shim'ы послойно, начиная
с `excel_builder` и `html_builder`: на них приходится 34 из 65, и они ближе всего
к выходу из системы.
